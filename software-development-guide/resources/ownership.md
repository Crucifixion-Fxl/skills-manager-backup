# 业务 / 系统 / 职能 → 负责人

> 🚨 **重要：本表是业务域级别的 owner 总结，不到具体需求任务粒度。**
>
> 公司没有"仓库主负责人"概念 — 一个仓可能多业务域共用，一个业务域可能跨多仓。
> 也不要把 ownership 等同于"5 月某需求的 owner"，需求每月变，业务域 owner 相对稳定。
>
> **三层结构**：
> - **业务层**（前台 / App）：直接产生用户价值的业务域
> - **系统层**（平台 / 基础设施）：支撑业务的横向能力
> - **职能层**（组织 / 角色）：跨业务的职能团队
>
> **Agent 使用规则**（必须遵守）：
> - 用户问"X 仓谁负责"时：先反问 / 推断"具体业务 / 系统 / 职能"，再答 owner
> - 不要回答"X 仓的主负责人是 Y" 这种句式
> - 不要把"5 月某需求 owner"当成业务域 owner（具体需求看 monthly plan）
> - 必须显式说"按业务域总结，X 由 Y 牵头"
> - 标"待补"的项必须答"未明确，建议飞书 @SPM 或 @架构师 王齐成 确认"
>
> **数据来源**：
> - 业务域归属：综合 `weekly-reports/software/2026-05-monthly-plan.md` 长期 owner
> - 飞书：https://a4x-paas.feishu.cn/wiki/F25ywb6ajiQEoDkelkUc2MrvnSf
> - 具体需求 owner（每月变）：直接看最新 monthly plan
>
> **Refresh**：每季度 review 一次（业务域结构相对稳定）
>
> **"待补"项处理 SLA**：
> - 兜底 owner：所有"待补"业务域 / 系统 / 职能在确认人之前，**SPM tiancailaxi 兜底**（lattice scope）或 **架构师 王齐成 兜底**（跨项目）
> - 计划完成时间：本 skill 在 1 个月内（2026-06-07 前）由 SPM review 一轮，将所有"待补"替换为具体负责人或显式标注"无负责人 / 业务暂停"
> - 反馈方式：发现"待补"可直接 PR 编辑本文件 + 飞书 @SPM 确认

## 找谁咨询的逻辑

```
Step 1: 确定问题归属的"业务 / 系统 / 职能"
   - 业务问题（如 Library 入口设计）→ 业务层（视频域 / 设置域）
   - 系统问题（如埋点查询）→ 系统层（数据系统 / 可观测性）
   - 流程问题（如 TDD / 上线规范）→ 职能层（架构师 / SRE）

Step 2: 查本表 → 找业务域 / 系统 / 职能的牵头人

Step 3: 信度判断
   - 表中明确人名 → 直接联系
   - 标"待补" → 飞书 @tiancailaxi（SPM）或 @王齐成（架构师）

Step 4: 紧急 / 线上故障
   - lattice scope 客户端 + 集成相关后端：飞书 @tiancailaxi（SPM）
   - 上线提审：按 App 找对应值班人
   - 跨业务域：飞书 @王齐成（架构师）
```
