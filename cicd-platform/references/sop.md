## 入口与角色

- 列表：`https://cicd.addx.live/#/task/list`
- 详情：`https://cicd.addx.live/#/task/<task-id>/detail`
- 登录：GitLab OAuth。未登录会跳转到 `/#/login?redirect=/task/list`。
- UI：Vue + Ant Design。优先用 snapshot 的可访问名称与 ref；CSS 兜底使用 `.ant-btn`、`.ant-modal`、`.ant-form-item`、`.ant-select`。

角色动作：

| 动作 | 角色 |
|---|---|
| 查看上线单 | admin / rd / qa / op / pm |
| 创建、编辑上线单 | admin / rd / op |
| 添加项目、Review Apollo、上传 Apollo 验证 | admin / rd |
| 完成测试、灰度验证、验收 | admin / qa |
| 自动化校验、Apollo Pre/Prod、审批 | admin / op |
| 部署、取消部署、回滚版本 | admin / rd / op |
| 特批 | admin / pm |
| 作废 | admin / op |
| 挂起、恢复、跳步、工作流回退 | admin |

权限不足表现为按钮不可见或 disabled。不要改角色、伪造请求或调用 API 绕过。

## 状态与环境

上线单步骤：

| 状态 | 页面步骤 | 正常下一动作 |
|---|---|---|
| 1 | 新建 | 添加项目、PRE 部署、完成测试 |
| 2 | 测试 | 自动化校验 |
| 3 | 校验 | Apollo Prod（如有）、审批 |
| 4 | 审批 | GRAY 部署与灰度验证 |
| 5 | 灰度 | PROD 部署、Apollo 验证上传、验收 |
| 6 | 完成 | 只读复核 |

环境映射：

| 页面 | API env | 地区 |
|---|---|---|
| 中国 PRE / GRAY / PROD | `pre` / `gray` / `prod` | CN |
| 美国 PRE / GRAY / PROD | `pre-us` / `gray-us` / `prod-us` | US |
| 欧洲 PRE / GRAY / PROD | `pre-eu` / `gray-eu` / `prod-eu` | EU |

部署状态：`1=成功`、`2=失败`、`3=进行中`、`4=中止`。

## 查询上线单

1. 用户给出 URL 时直接打开；只给 ID 时构造 `/#/task/<id>/detail`。
2. snapshot 并记录：ID、`[Apollo]`/`[快]`/`[废]`/特批/挂起标记、当前步骤、说明、测试范围、SQL、Apollo、预计时间。
3. 对每个项目记录 `ProjectName`、Git branch、commit，以及各环境部署状态、部署人、部署时间、镜像 tag。
4. 需要日志时点击对应环境卡片的 `日志`，等待内容稳定后提取末尾错误与 Jenkins 链接。
5. 只回答查询时不要触发任何推进、部署或配置按钮。

## 创建或编辑上线单

创建入口位于 `/#/task/list` 的 `创建`：

1. 点击 `创建`，填写 `上线时间`、`上线说明`、`测试范围`、`上线日志`。
2. 按事实勾选 `SQL`、`Apollo变更`；有 Apollo 时必填 `Apollo变更描述`。
3. 模式必须由用户意图决定：
   - `创建`：普通上线单。
   - `快捷上线单`：仅无 SQL、无 Apollo 时可选。
   - `Apollo上线单`：仅 Apollo 变更且无 SQL 时可选。
4. 提交前回读全部字段。创建后从列表获取新 ID，打开详情验证。

编辑仅在状态 1 且上线单有效时开放，字段与创建一致。不要为了编辑而回退步骤。

## 添加项目与选择版本

1. 在详情点击 `添加项目`，从下拉中选择精确项目名，点击 `添加`。
2. 页面刷新后验证项目卡片出现；不要把 `/project` 管理页当作添加入口。
3. PRE 首次部署若弹出 branch 选择，选择用户指定 branch，并记录页面解析出的 commit。
4. 若项目已有 Git branch/commit，弹窗会沿用现有值。发现与用户要求不一致时停止。
5. GRAY/PROD 不提供临时换分支；必须沿用上线单已记录版本。

## 推进上线单

按页面按钮和状态推进：

1. `完成测试`：QA 确认测试范围完成后推进到测试状态。
2. `校验`：OP 触发自动化校验；等待结果，不要把启动成功当作校验通过。
3. `审批`：只在校验步骤通过后推进。
4. `灰度验证`：确认目标地区 GRAY 部署和业务验证完成后推进。
5. `验收`：确认 PROD 部署、监控与必要 Apollo 验证完成后关闭上线单。

每步前重新读取所有项目环境；多项目上线单不能只看一个项目就推进。

## 部署、取消与回滚

部署：

1. 找到正确项目卡片和地区环境卡片，确认按钮 enabled。
2. 记录当前 commit/tag 和目标 commit；生产动作还要核对上线单步骤与观察人/验证计划。
3. 点击一次 `部署`；PRE 若出现 branch 弹窗，选择后再次核对项目、环境、Tag。
4. 状态进入 `进行中` 后每 10 秒刷新；必要时查看 `日志`，直到成功/失败/中止。

取消：

1. 仅运行中且页面出现 `取消` 时执行。
2. 部分项目在不可取消名单中；没有按钮就停止。
3. 取消后等待状态变为 `中止`，确认下游任务不再运行。

回滚：

1. 进入成功部署卡片的 `配置项 → 回滚`。
2. 页面语义是恢复到上一次成功部署版本；先记录当前和目标版本。
3. 点击回滚后按部署流程轮询，验证最终 commit/tag。

## 灰度操作总门禁

只对支持灰度且非只读项目执行。每次灰度操作先完成同一套基线读取：

1. 打开目标项目、目标地区成功部署卡片的 `配置项 → 灰度配置`。
2. 记录 `开启/关闭`、线上有效实际 gray ratio、分流策略、完整白名单、完整黑名单，以及是否存在正在运行/已完成的预扩容。
3. 把 PROD 卡片输入换算成实际值：`实际 gray = 100 - PROD 输入`；GRAY 卡片输入就是实际 gray。后续比较一律使用**实际 gray 比例**。
4. 判定是否扩量：
   - 当前关闭，目标开启且实际 gray > 0：扩量。
   - 目标实际 gray > 当前线上有效实际 gray：扩量。
   - 实际比例相同/降低，或仅改名单：非比例扩量。
5. 确认项目不在灰度只读列表；页面提示与 `iot-service` 共享 Apollo 配置时只读，不写。

CN 页面提示 TKE 无 APISIX 灰度时不做预扩容或缩容，也不尝试绕过。US/EU 的任何扩量必须先完成预扩容。

## 灰度开关

开启灰度：

1. 读取当前有效比例；输入用户目标比例并换算实际 gray。
2. 若目标实际 gray > 当前有效比例，进入“灰度比例调整与预扩容”，预扩容成功后才能保存切流。
3. 若目标实际 gray 为 0，不视为放量；直接保存后回读开关和比例。
4. 完成信号：重新打开配置，确认 `enabled=true`、实际比例和名单均与目标一致。

关闭灰度：

1. 关闭 `灰度模式`，保持其它字段可审计，不顺手清空名单。
2. 点击 `确定` 保存，等待成功。
3. 重新打开配置，确认 `enabled=false`，线上有效 gray 流量为 0。
4. 只有完成第 3 步后，才允许执行缩容。

## 灰度比例调整与预扩容

降量或比例不变：

1. 确认目标实际 gray ≤ 当前线上有效实际 gray。
2. 页面提示无需预扩容后，直接点击 `确定` 保存。
3. 重新打开配置，回读实际比例。

扩量硬门禁（US/EU）：

1. 在表单中设置目标比例，但**不要先点确定切流**。
2. 点击 `灰度放量`。确认弹窗必须明确：目标项目/地区/namespace、页面输入值、换算后的 `gray.ratio`，且本步“只预扩容、不切流量”。
3. 点击 `开始预扩容` 后，状态必须进入 running；每 10 秒读取预扩容状态，必要时打开 Jenkins 实时进度。
4. running 时禁止点击 `确定`，也禁止重复触发预扩容。
5. failed 时停止，保存错误与 Jenkins 日志；不得切流，不得把失败当作容量就绪。
6. success 时核对 `预扩容 target gray.ratio ≥ 当前表单目标实际 gray`。用户若在预扩容后继续提高目标，必须针对新目标重新预扩容。
7. 只有 success 且 target 覆盖目标时，点击 `确定(放量切流量)`。
8. 保存后重新打开配置，验证 `enabled=true`、实际 gray ratio 和名单；再查看业务监控确认流量已按目标进入 gray。

预扩容完成只是“容量就绪”，不是“已经切流”。最终报告必须分别说明预扩容状态和流量配置状态。

## 灰度白名单与黑名单

名单输入是逗号分隔的用户 ID，按集合修改：

1. 读取并保存完整现有列表；去除首尾空格，以精确 ID 去重。
2. 用户说“添加”时，在现有列表上并集合并；用户说“移除”时只删除精确匹配项；只有明确说“替换/覆盖”才重建整份列表。
3. 提交前展示 `新增 / 删除 / 保留`，以及调整后的完整名单数量；发现空字符串、重复 ID 或误删项时停止。
4. 只改白名单/黑名单且实际比例不升时无需预扩容，直接保存并回读。
5. 同一次操作如果还开启灰度或提高实际比例，先按扩量硬门禁完成预扩容，再一次性保存比例和名单并切流。
6. 完成信号：重新打开配置，逐项核对完整白名单/黑名单，不能只看成功提示。

## 灰度缩容

1. 先完成“关闭灰度”并回读 `enabled=false`、gray 流量为 0。
2. 点击 `缩容`，确认动作只把 gray 的 KEDA `minReplicaCount` 恢复到基线，不负责收流量。
3. 等待 `缩容已触发`，有 Jenkins 链接时跟踪到完成。
4. 缩容失败时保留关闭灰度状态，记录日志，不重新打开流量。

## Apollo 流程

1. RD 点击 `Review Apollo`，检查 Review 变更，点击 `批准`。
2. OP 点击 `发布PRE环境Apollo`，再次比较 Review 与当前变更；若有新变更，关闭弹窗并重新 Review。
3. 在校验步骤且 Pre 发布成功后，OP 才可 `发布PROD环境Apollo`。
4. 灰度/生产验证后，RD 可上传截图和验证结果描述。
5. 每次发布后重新打开日志或步骤记录，确认发布状态、时间和操作人。

## 管理员操作

- `挂起`：填写审计原因；冻结推进、部署、灰度与审批。
- `恢复`：恢复后重新读取所有页面状态，不自动继续之前动作。
- `跳过当前步骤`：仅新建/测试/校验；必须填写原因，不能跳灰度或验收。
- `回退步骤`：选择更早目标状态并填原因。它只重置平台状态与门禁，不撤销部署/Apollo。
- `特批`、`作废`：从列表操作；作废后该上线单默认只读。

## 失败处理与验收

1. UI 报错：保存错误全文、当前 URL、任务 ID、动作；重新读取状态再决定是否重试。
2. 网络超时：先检查状态接口/页面是否已有新记录，避免重复 POST。
3. 部署失败：打开日志，提取首个根因和末尾状态；需要时转 Jenkins/ArgoCD 排障。
4. Apollo 变更漂移：重新 Review，不绕过 disabled 发布按钮。
5. 成功验收至少包含：页面最终状态、commit/tag、操作时间/操作人，以及上线单 URL。
