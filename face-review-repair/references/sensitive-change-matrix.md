# 敏感修改矩阵

当评审修复涉及运行时行为或共享基础设施时，必须阅读本参考。矩阵规定最低证据要求，各仓库可以提出更高要求。

## 风险等级

| 等级 | 定义 | 自动化策略 |
|:--|:--|:--|
| `mechanical` | 格式、文案、import、本地常量提取、生成文件刷新 | 完成针对性检查后可自动修复 |
| `behavior-sensitive` | 控制流、校验、状态变化、异常处理、重试、超时、功能开关 | 必须增加保护业务行为的测试 |
| `critical-boundary` | 事务、数据源、鉴权与租户隔离、结构与 migration、资金、队列与事件、并发、公共 API | 禁止盲目自动修复；必须提供集成证据并由负责人评审 |

diff 行数、评审者身份，以及意见是否由 AI 提出，都不能降低风险等级。

## 分类矩阵

| 类别 | 高风险信号 | 最低证据要求 |
|:--|:--|:--|
| 事务 | `@Transactional`、事务管理器、传播级别、隔离级别、回滚规则、`TransactionTemplate` | 提交与回滚集成测试、异常路径、事务所有者确认 |
| 数据源路由 | `@DS`、`AbstractRoutingDataSource`、上下文持有者的 `push/set/clear/poll`、数据源键或配置 | 两个可区分的数据库或 schema、实际读写目标断言、清理和线程复用测试 |
| 鉴权与租户 | 鉴权中间件、JWT claims、租户/用户/设备 ID、权限门禁 | 有权限、无权限、跨租户三个方向的测试 |
| 公共 API | 路由、protobuf/OpenAPI、请求响应字段、状态码或错误码 | 契约测试、调用方兼容性、生成产物同步 |
| 持久化与结构 | SQL、migration、ORM 映射、索引、默认值、可空性 | migration 或结构测试、历史和新数据兼容、回滚或恢复方案 |
| 缓存 | 缓存键、命名空间、TTL、失效、降级 | 命中、未命中、过期、失效测试及租户隔离 |
| 队列与事件 | topic、key、生产消费顺序、ack、重试/DLQ、去重 | 重复、重放、顺序、失败恢复和幂等测试 |
| 重试与超时 | 重试次数、退避、deadline、熔断 | 超时和重试耗尽测试、重复副作用检查 |
| 并发与生命周期 | 锁、异步任务、线程或协程、监听器、订阅、清理 | 竞争和生命周期测试、取消、dispose 与资源清理 |
| 功能或配置门禁 | 功能开关、本地部署开关、环境模板、默认值和降级值 | 目标环境中默认、ON、OFF 和失败模式的契约测试 |
| 外部副作用 | 支付、邮件或推送、设备命令、第三方写入 | 使用沙箱或 fake 集成验证幂等和重试 |
| 可观测性与安全 | 日志、trace、指标、PII 或密钥处理 | 上报与脱敏测试，diff 和产物中不得出现密钥 |

## 事务和数据源规则

### 禁止模式

```java
@Transactional
public void execute(...) {
    DynamicDataSourceContextHolder.push(target);
    repository.save(...);
}
```

事务拦截器通常会在进入方法体之前获取并绑定连接。之后修改路由键并不会替换该连接。

### 推荐边界

```text
RoutingFacade（无事务）
  -> 选择目标数据源
  -> 通过代理调用 TargetDataSourceService
  -> TargetDataSourceService 启动匹配的事务
  -> 执行 repository 操作
```

还需要验证：

- 调用必须穿过代理边界，不能使用 `this.method()`。
- 同时使用数据源和事务注解时，数据源切面必须先于事务切面执行。
- 被选中的事务管理器必须属于被选中的数据源。
- 路由上下文必须在 `finally` 中清理。
- 不得假设一个本地事务可以原子覆盖两个独立数据库。
- 需要跨库一致性时，应显式采用 outbox、saga 等方案。

### 最小集成用例

使用结构相同但标识数据不同的两个独立目标：

| 用例 | 断言 |
|:--|:--|
| 路由 A | 只在 A 中发生读写 |
| 路由 B | 只在 B 中发生读写 |
| 回滚 | 目标数据库没有提交写入 |
| 路由过程中异常 | 上下文已清理 |
| 复用线程上的下一任务 | 使用自己请求的目标或默认目标 |
| 嵌套服务调用 | 事务与目标数据源仍符合设计 |

`verify(contextHolder).push("B")` 之类的 mock 断言，不能证明 JDBC 实际使用了 B。

## 评审修复 diff 检查清单

修改后必须明确检查 diff 是否新增、删除或移动了：

```text
注解
门禁和降级值
数据库、缓存或队列调用
外部副作用
异常转换和 catch 块
重试和超时配置
资源清理
功能或配置默认值
公共字段和路由
事务或异步边界
```

发现任何非预期语义变化时，必须撤销该修复，或退回到“修改前建立证据保护”步骤重新处理。

## 建议的静态门禁

使用动态路由的仓库应增加确定性的 CI 规则，例如：

- Semgrep：检测 `@Transactional` 方法中的上下文持有者切换。
- ArchUnit：事务服务包不得依赖路由上下文持有者。
- ArchUnit：路由入口类不得标记 `@Transactional`。
- 静态检查：禁止通过 `this` 调用带有 `@DS` 或 `@Transactional` 的方法。
- CODEOWNERS：覆盖路由、事务管理器、migration、鉴权和队列基础设施。

AI 评审只作为语义判断的建议来源。确定性的 lint 和集成测试才是阻断门禁。
