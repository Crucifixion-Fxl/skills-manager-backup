# Eval-driven Review

## 目标

评价人在不同工作类型中是否先定义、检查并改进“什么算成功”，并给出有证据的下一步习惯建议。评价的是可观察的工作方式，不是人格、绩效或团队排名。

## 先判断任务阶段

- **探索/共同设计**：目标和约束仍在形成。使用 prose eval；检查问题框架、约束增量、候选取舍、事实核验和冻结决定。
- **可行性验证**：核心未知是某项能力能否成立。先定义最小实验、成功/失败信号和退出条件。
- **实现**：目标已经冻结。检查是否在实现前定义 oracle，是否观察到有意义的 red/green，以及验证是否位于真实风险层。
- **真实使用/运行**：检查现场差异是否回灌为 fixture、grader 或 evidence contract，并能重跑。

一个长会话可以跨阶段。评审必须指出阶段切换，不能用 whole-session 单标签覆盖所有阶段。

## 评价维度

### 1. Eval 是否在关键行动前出现

寻找人在设计或实现前讨论成功条件、失败条件、对照样本、真实环境或验收方法的证据。事后补测试不等于无价值，但要准确标为 eval-after。

### 2. Oracle 是否足够真实

判断依据是否只证明“代码执行了”，还是证明用户旅程、业务数据、权限边界或真实执行层成立。测试数量不能代替 oracle 质量。

### 3. 问题是否先反馈给 Eval

出现真实问题后，是否先问原 evaluator 为什么没有发现；是否形成“现场差异 → eval gap → 新 fixture → 重跑”的链路。

### 4. 人是否提供不可替代的判断

记录人的价值选择、组织约束和对候选方案的取舍。不要把 AI 无法从首轮输入推断的要求描述成 AI 执行失败。

### 5. 对话是否收敛

有效对话每轮产生 state delta。无效循环表现为同一约束被遗忘、相同失败反复出现、没有新增证据或决定。

### 6. 流程摩擦是否可观测

同时扫描 CI/CD 等待与重跑、埋点缺失或错误、环境/权限阻塞、工具反复失败、交接等待和重复手工操作。每个 friction 必须还原场景，链接 scene locator，并记录可观测信号（如 pipeline queue/job duration、retry 次数、cache miss、重复操作次数）、影响和下一个 evaluator/自动化动作。

严格区分“指标为 0”、“埋点未上报”和“查询/链路阻塞”。没有可审计的数值或状态证据时，只能标为 `needs-evidence`，不得凭聊天长度、单次报错或空仪表盘判定高摩擦。

## 报告要求

先用 3-5 条普通语言写结论，再用代表性任务场景解释。每条需要强化的建议必须链接到至少一个 finding，并说明下次可执行的动作。另列“流程 friction”表，展示 category、`observed|needs-evidence`、信号、影响与建议的评估/自动化。不要输出综合分数；分别描述强证据、有限证据和无法判断的部分。

至少包含一个“这不是问题”的判断，例如：开放设计阶段没有代码测试不等于缺乏 Eval-driven 习惯。这样可以防止指标反客为主。
