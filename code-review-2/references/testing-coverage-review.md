# 测试覆盖度系统 review 方法

用于 code-review Step 2（内容质量审查）和 Step 3（端到端一致性）之间深入挖掘"测试表面存在但实际无效"类问题。

**适用时机**：
- 当变更涉及 `docs/testing/**` 测试策略或 scenarios
- 当要评估整个测试体系（非单个 MR 的局部）
- 当怀疑 "测试写了但没效" / "测试基础设施可能静默成功"

**核心思想**：Code Review 先判断 **测试代码存在 + 断言指向产品 AC + fixture/setup 能进入目标分支**。CI 是否实际执行属于独立的合并门禁；只有明确进行 CI 门禁审计时才额外核对，不以 Pipeline 当前状态阻塞 Code Review。

---

## 1. 测试内容对账法：doc ↔ code ↔ assertions

任何 scenarios/testing 文档声称的测试，Code Review 默认在以下 3 处对账：
1. **文档**：`docs/testing/scenarios/**/*.md` 引用的文件名
2. **代码**：`admin/tests/` / `hub/e2e/` / `server/internal/**/*_test.go` 下真实文件
3. **断言**：测试 body 的断言确实覆盖产品 AC，而不是只有启动、写入或可见性浅断言

`.gitlab-ci.yml` 是否调度这些测试属于第 6 节的可选 CI 门禁审计，不是普通 Code Review 的 Pipeline 结果门禁。

### 1.1 Scenarios-to-Code 孤儿引用量化

```bash
# 从 scenarios 抽取声称的 test filename
grep -rohE "[a-z-]+\.(spec|test)\.(ts|js)" docs/testing/scenarios/ | sort -u > /tmp/claimed.txt

# glob 实际文件
find admin/tests hub/e2e -name "*.spec.ts" -o -name "*.test.ts" -o -name "*.spec.js" | xargs -n1 basename | sort -u > /tmp/actual.txt

# diff → 孤儿引用
diff /tmp/claimed.txt /tmp/actual.txt
```

**典型发现**：scenarios 声称 25+ `kbtv-*.test.ts / ecosystem-*.spec.ts / nature-timeline-*.spec.ts`，实际**70% 不存在**。文档是 wish-list 不是现实。

### 1.2 代码存在但 CI 不执行

```bash
# Flutter widget test 存在数
find packages naturehood_app -name "*_test.dart" | wc -l

# CI 是否调 flutter test
grep -E "flutter test" .gitlab-ci.yml | wc -l
# 0 → 所有 widget test CI 零执行
```

**典型发现**：
- Flutter `*_test.dart` **46 个文件**，CI **0 调用**
- hub vitest `__tests__/` **20 tests**，CI **0 调用**
- server/internal/handler `*_test.go` contract test **41 用例**，CI `test-l2` 只跑 `./internal/logic/...` → 41 用例全漏

### 1.3 CI 跑但断言为浅 "nothing test"

```bash
# 找 test 函数里仅做 `expect(...toBeVisible())` / `assert.NoError(err)` 类浅断言
grep -rE "toBeVisible\(\)\s*$" admin/tests/l3-browser/*.ts
```

**典型发现**：`admin-feature.test.ts` 5 个 test，仅断言 `.ant-table` 可见，不验证 "click feature → post 出现在 feed 首位"（scenarios 设计的真实 AC）。

## 2. 二维分析矩阵：业务模块 × (测试代码 / 可选 CI 门禁)

report 时**分别**列出两维度：

| 业务模块 | 层级 | 测试代码层面（写得够不够）| CI 门禁层面（仅在明确审计时记录；不重复阻塞 Code Review）|
|:---|:---|:---|:---|
| Explore | L1 | `server/internal/logic/explore/` 15 `*_test.go`，多数 1-5 test | CI 跑 ./internal/logic/... ✓ |
| Explore | L2-1 | `handler/explore/contract_test.go` 20 用例 ✓ | CI `test-l2` **漏 handler 目录** ❌ |
| Explore | L3-Backend | scenarios 定义降级场景，无 Go 代码真用 WireMock | 0 个 job 调度 |
| Explore | L3-App | `explore-feed.test.ts` 31 用例**全是 API**测试 | CI 跑，但不驱动 Flutter UI |
| ... | | | |

**好处**：
- 读者清楚区分 "测试代码该写没写" 和 "代码有了但 CI 没跑"
- 修复路径分工：前者是 dev task，后者是 CI config task
- 避免把所有问题笼统归为"测试不足"

**最终 SUMMARY 应含**：
1. A 区：按业务模块（Explore / Ecosystem / Collection / NT / PostCard+Hub / KBTV / rec-engine / Admin / CDN / Flutter App）—— 每模块一张 L1-L4 × (代码/CI) 表
2. B 区：跨模块基础设施（CI / 测试代码 / 文档追溯 / 产品配置）

## 3. 产品 bug vs 测试 bug 分离

review 产出里要明确标注：哪些 finding 补 test 就行，哪些 **补 test 没用——产品代码根本不实现 AC**。

### 产品级 bug 识别信号

- Scenarios 说 "Then 内容从 feed 移除"，但 logic 代码只 `INSERT INTO explore_reports`，没写 `explore_hides` → **AC 一半未实现**
- Featured Tab `SELECT ... WHERE is_featured=TRUE` 不过滤 `review_status='approved'` → **审核打回的 postcard 仍展示**
- rec-engine 在 prod overlay 不存在但 CI 持续 build image → **生产从未部署**
- TODO `// PaywallLauncher integration` 留在 prod 代码里 → **US AC "点锁图标跳 Paywall" 未实现**
- Migration 声称 "auto-generated by scripts/foo.py" 但 py 脚本不存在 → **手工维护伪装自动化**

### 分类后的补救 roadmap 分工

- 🔴 产品 bug：issue 归 feature owner / PM，补代码
- 🟠 测试缺：issue 归 QA / dev，补 test
- 🟡 CI 门禁：issue 归 DevOps / platform，修 `.gitlab-ci.yml`
- 🟡 文档漂移：issue 归 docs owner，同步 spec 与 code

## 4. Spec ↔ 代码机械核对

自动可执行的一致性检查。可做成 CI lint。

### 4.1 `flutter-semantics.md` 声明 vs 代码实现

```bash
# Spec 列的 explore- label 列表
grep -oE "explore-[a-z-]+" docs/testing/flutter-semantics.md | sort -u > /tmp/spec-labels.txt

# 代码真实现的
grep -rohE "['\"]explore-[a-z-]+" packages/explore_feature/lib/ | sort -u | tr -d "'\"" > /tmp/code-labels.txt

diff /tmp/spec-labels.txt /tmp/code-labels.txt
```

**典型发现**：声明 10，代码 5；drift 50%。

### 4.2 `api-contract.md` 声明 vs handler 存在

```bash
# 声明的 handler 数（按 GET/POST/PUT/DELETE/PATCH 开头表行计数）
grep -cE "\| \`(GET|POST|PUT|DELETE|PATCH) " docs/testing/scenarios/tech/api-contract.md

# 实际 handler 文件数
find server/internal/handler -name "*Handler.go" | wc -l
```

**典型发现**：22 / 51 = 43% 覆盖率。

### 4.3 `types.go` 声明 "DO NOT EDIT" vs 实际 diff

```bash
# 如果文件头含 "DO NOT EDIT" 但 git log 显示被非 goctl 改动过
git log --oneline server/internal/types/types.go | head
# ↓ 应该只有 goctl regen 提交；若有手写 admin type commit → 违反
```

## 5. 状态机 / 分支覆盖量化

### 5.1 `switch action` 的 case 数 vs 已测 case

```bash
# logic 文件里 switch 的 case
grep -E '^\s*case "' server/internal/logic/admin/updatePostLogic.go | wc -l
# = 6 (approve/feature/reject/takedown/unfeature/restore)

# 对应 _test.go 里覆盖的 case
grep -E "Action:\s*\"(approve|feature|reject|takedown|unfeature|restore)\"" server/internal/logic/admin/*_test.go | wc -l
# = 2 (仅 feature + unfeature) → 4 分支裸奔
```

### 5.2 AC 拆解到 L2-2 assertion

US AC 若有 "Then X 并 Y"（compound），L2-2 test 必须有对应 X 和 Y 两条独立 assertion。典型反模式：

```go
// US-EX-04 AC: "Then 内容被标记待审核 并 从用户信息流中移除"
// 当前 reportLogic_test 只测 X：
var count int
db.QueryRow("SELECT COUNT(*) FROM explore_reports WHERE ...").Scan(&count)
if count != 1 { t.Fatal("expected 1 report") }
// 缺 Y 断言：feed 查询应不再返回该 post
```

→ 测 write 不测 read。US AC 两端必须都断。这是 vacuous test 的第三种形态（详见 §10）。

## 6. 可选：CI 门禁完整性检查（不阻塞 Code Review）

本节只在用户明确要求测试体系/CI 门禁审计，或本次 diff 直接修改 CI 配置时启用。它的发现归 CI/platform 责任域，不能因为当前 Pipeline 失败、尚未完成或未被轮询而改变 Code Review 结论。

### 6.1 CI job 清单 vs 应跑的测试清单

```bash
# CI 里出现的 test 调用
grep -nE "go test|flutter test|vitest|npm test|playwright test" .gitlab-ci.yml
```

比对：
- 所有 `_test.go` 在 `./internal/logic/...` 和 `./internal/handler/...` 和 `./internal/middleware/...` 是否都被某个 job 覆盖
- 所有 Flutter `*_test.dart` 是否被某 job 覆盖
- 所有 vitest 目录是否被 npm test 调用

### 6.2 硬 sleep 统计（flake 源）

```bash
grep -rcE "time\.Sleep|waitForTimeout" server/ rec-engine/ admin/tests/ hub/e2e/ 2>/dev/null
```

53 处 sleep = 53 潜在 flake 源。

### 6.3 `os.Exit(0)` 和 `t.Skipf` 静默成功

```bash
grep -rnE "os\.Exit\(0\)|t\.Skipf" server/ rec-engine/ --include='*.go' | grep -v _test.go
```

找 test 基础设施里的"连不上就假装成功"模式。CI 服务不 ready 时 GREEN = 静默 FALSE。

## 7. 循环推进模式 `/loop 20m`

单次 review 难全面挖。建议：

1. **首轮**：doc 摸排（scenarios / strategy.md / api-contract.md）+ 分层清单（L1-L4 哪些有、哪些没）
2. **后续每 20 分钟 loop**，聚焦一个角度（每次 ~5-10 条 finding）：
   - （仅 CI 门禁审计）CI 管道逐 job 审
   - Dockerfile / docker-compose / k8s overlay
   - migration 010 后续每个 .sql file
   - packages/ 每个 Dart package test ratio
   - scenarios 孤儿引用
   - spec vs code 机械对账
   - deep link / Universal Link / Semantics / ErrorBoundary / Sentry
   - 脚本 (dev-*.sh / seed-*.sh)
3. **累计 findings 写 `§N` 编号**，与具体代码引用（file:line）对齐
4. **每 5-8 个 loop 产出 1 次 SUMMARY rebuild**，按业务模块 + B 区基础设施双轴

### 收敛条件
- 每 loop 新增 findings < 5 条 **且** 全是 documentation drift / 局部优化 → 收束
- 找到的都已是 "notes 级别" 非 Critical → 停循环

## 8. 产出物结构（建议）

```
docs/review-YYYY-MM-DD/
├── SUMMARY.md                    # Executive summary
│   ├── 一句话结论
│   ├── Top N 风险（critical 优先）
│   ├── A 区 按业务模块
│   ├── B 区 跨模块 CI/测试代码/文档/产品
│   ├── 1 分钟 / 1 小时 / 1 天 / 1 周 补救 roadmap
│   └── 累计指标（finding 数 / 产品 bug 数 / 零接入观测面）
└── testing-strategy-gaps.md      # 按 §N 编号的 finding 详情
    ├── §1-§N 每条含 file:line / 现状 / 影响 / 修复
    └── 按 loop 累加，rebuild SUMMARY 时交叉引用
```

**commit 策略**：每个 loop 一个 commit，commit message 列本轮新加 `§N-§M` 的核心发现。review 分支可独立（`review/YYYY-MM-DD-topic`）或与代码同分支。

## 9. 反模式 / 避坑

| 陷阱 | 后果 | 规避 |
|:---|:---|:---|
| 把所有 finding 归为 "测试不足" | 掩盖真正的产品 bug | 分类 🔴 产品 / 🟠 测试 / 🟡 CI / 🟡 文档 |
| 只看 scenarios 文档不核代码 | 文档可能说谎（§159 / §244） | 每条 scenario 必对应 `find` 验证 |
| 只跑 scenarios 链接的 test 文件名 | 漏了 doc 未登记但代码已有的 test | 双向 diff：doc→code + code→doc |
| 把浅断言当"已测" | 看似覆盖率高 | 抽 test body 看断言类型（write-only? page.goto only?） |
| 只做静态审查 | 可能漏 "CI 明明跑了但 os.Exit(0) 吞掉失败" | 抽 1-2 个 test 在 worktree 真跑一次验证行为 |
| Plan 超长 (>600 line) | 无人读 | scenarios 和 plans 拆子文档 + 索引 |

## 10. Vacuous Test 识别（深度审查 — 非静态可见）

比"测试代码存在"更隐蔽的一层：测试**代码写了**、**CI 跑了**、**断言也看似正确**，但被测分支实际从未执行。CI 跑绿 ≠ 功能验证。

### 10.1 三种典型形态（按成因）

| 形态 | 典型 fingerprint | 真实案例 |
|:-----|:----------------|:---------|
| **A. Config/Fixture 漏字段** | `TestMain` 初始化 config 时漏某个阈值字段，生产默认零值让判断分支永远不触发 | Explore hide 阈值测试 —— `HideReportThreshold` 没配，feedLogic 的阈值分支根本没跑，测试是"seed 本身就没插 feed" 的假绿 |
| **B. Seed 规模未达触发阈值** | 被测分支有 fast-path / minimum-size gate，seed 数据规模低于 gate 就走不到 | `TestFeedLogic_SeenSetDedup_Redis` —— pool 只 seed 2 条，`BloomFilterMinPosts=5` fast-path 直接 return，dedup 代码从未执行 |
| **C. 只断 write 不断 read** | `INSERT` 后只 `SELECT COUNT(*)` 断写入了一行，不断用户可见的后续读取效果 | `reportLogic_test` —— 只断 `explore_reports` 有 1 行，没断 feed 不再返回该 post；真实 bug 是 reportLogic 漏 insert `explore_hides`，测试完全没捕到 |

### 10.2 review 侧识别手段

1. **读 TestMain / setup_test.go**：被测 config 字段是否完整初始化、是否与 production default 对齐
2. **读 test body 的 seed 部分**：seed 规模、数值、状态是否达到被测分支的触发阈值（对照 production code 的 if/fast-path 边界）
3. **读 assertion**：compound AC "X 并 Y" 是否都断了；只出现 `SELECT COUNT(*) FROM ... WHERE ... = 1` 而无后续 "读取/查询" 断言 → 高概率 write-only
4. **问作者**："merge 前做过 fail-loud 验证吗？把 production code 的关键行注释掉，这个测试会 fail 吗？"如果没做过 —— 🔴 补做

### 10.3 自动化初筛（grep 级）

```bash
# 找只有 COUNT(*) = N 断言、没有后续 SELECT 查询的 write-only 嫌疑
grep -rA 3 "SELECT COUNT" server/internal/logic/**/*_test.go \
  | grep -B 1 "t.Fatal\|require.Equal" | head -50

# 找 seed 规模明显偏少（seed 2 条）但代码有 fast-path 阈值（>=5）的测试
grep -rE "for i := 0; i < [1-4];" server/internal/**/*_test.go
# 配合 grep production code 的 MinXxx/ThresholdXxx 常量对比

# 找 TestMain 只设了一两个 config 字段的
grep -B 2 -A 20 "func TestMain" server/internal/**/*_test.go \
  | grep -c "Config{"  # 设字段越少，漏字段越可能
```

### 10.4 发现后的修复链

不是"加一条新测试就完事"：

1. **修旧 test**：补全 fixture / config / seed 让被测分支真的进入
2. **加前置断言（sanity check）**：`require.Greater(t, len(pool), BloomFilterMinPosts)` / `require.NotZero(t, cfg.HideReportThreshold)`，一旦 fixture 再漂移立即 fail
3. **故意破坏验证**：在 production code 里把被测分支改为 `if false` / 注释掉关键行，确认测试 **真的 fail** → 再还原
4. **audit 邻居测试**：同一 `_test.go` 的其他 case 是否有同类 copy-paste 陷阱（往往批量存在）
5. **更新 SSOT fixture**：如果根因是 fixture 文件（tier-config.test.json 等）与 production 漂移，修 fixture 并加 CI lint 比对字段完整性

### 10.5 与 §6.3 CI 静默成功的区分

| 反模式 | 故障位置 | CI 表现 | 识别方式 |
|:-------|:---------|:-------|:---------|
| §6.3 静默成功 | 测试 **执行** 时 infra 不可达，被 `os.Exit(0)` 吞掉 | 看似绿 | grep `os.Exit(0)` / `t.Skipf` |
| §10 vacuous | 测试 **执行成功**，但被测分支压根没进 | 真绿 | 读 fixture / seed / assertion 三方对齐 |

CI 静默成功靠 grep 静态可查；vacuous test 必须 **读 test body + 对照 production code 的分支条件**，grep 只能初筛。

## 11. Checklist: 一轮完整的测试覆盖度 review

- [ ] scenarios/*.md 声称的 `.spec/.test` 文件名和实际 file glob 对账
- [ ] strategy.md §8 追溯矩阵每个 US 行，至少一列（L3-App / L3-Admin）打勾，且勾对应的 test 真实存在
- [ ] handler / logic src 文件数 vs 对应 test 文件数（file-level coverage）
- [ ] handler / logic test 里的 assertion 是否覆盖 US AC 的 compound 部分（"write + read"）
- [ ] 状态机 switch case 数 vs test case 数
- [ ] Request types validation tag 是否齐全 vs logic if-statement 散落
- [ ] （可选 CI 门禁审计）CI 每个 test job 的 go test 命令覆盖哪些 package
- [ ] （可选 CI 门禁审计）CI 是否跑 Flutter test / Vitest / Playwright / Trivy / gosec 等 non-Go 链
- [ ] `testutil.NewTestDB` / `t.Skipf` 是否会静默 passing
- [ ] **Vacuous test 自检**（§10）：TestMain config 字段是否完整、seed 规模是否达被测分支阈值、compound AC 是否 write+read 双断、新测试是否做过 fail-loud 验证
- [ ] Migration `.up.sql` 命名一致性 + CI apply 脚本行为（吞错 / 顺序 / 幂等）
- [ ] Seed script SSOT（seed-ci.sh vs seed-dev-data.sh drift）
- [ ] Spec vs code 机械对账：Semantics label / api-contract handler / types.go drift
- [ ] 产品 bug 分离：哪些是 "补 test 也没用，得补代码"
- [ ] Onboarding 物理阻挡栈（submodule / dev-*.sh / .env / GitLab token / pub_cache）
- [ ] 观测面清单：Sentry / OTel / Prom / Grafana / Alert / runbook 的有/无

本 checklist 的测试代码/断言/fixture 项触发 → 产出一条 `§N` finding；可选 CI 门禁项单独标为 CI/platform finding，不改变 Code Review 结论。
