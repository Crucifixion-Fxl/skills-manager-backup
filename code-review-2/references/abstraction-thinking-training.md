# 抽象思维训练：从 if/else 到领域模型

> 本文用于员工培训：解释为什么工程师需要训练抽象思维，以及如何把这种能力落到需求分析、代码实现、重构和 Code Review 中。

## 一句话结论

**[HWPR]** 核心判断

人的思维复杂度是有限的，AI 对隐式路径和跨分支不变量的稳定追踪也有限。所以工程训练的目标不是记住更多分支，而是把低层条件压缩成高层业务概念，把局部补丁沉淀为可维护的模型、规则和边界。

我们不追求消灭 `if/else`。我们追求的是：

- 让代码表达业务结构，而不是记录历史补丁。
- 让规则有归属，而不是散落在多个入口。
- 让状态和变化轴可见，而不是靠人和 AI 在脑中模拟。
- 让重构服务于交付效率、缺陷控制和长期演进，而不是服务于“代码优雅”。

**[AWOR]** 本文的阅读路径

1. 先看问题：为什么只做当前需求会让系统变慢、bug 变多。
2. 再看机制：为什么人和 AI 都不擅长大量 `if/else`。
3. 再看理论：这些现象背后的认知科学和软件工程支撑。
4. 再看方法：如何判断该局部重构、整体重构，还是暂时保持简单。
5. 最后看训练：如何通过命名、变化轴识别、调研和 Code Review 培养抽象能力。

## 1. 问题：系统为什么越来越难改

### 1.1 需求惯性：只为满足某一个需求

很多复杂系统不是因为工程师不会写代码而变差，而是因为团队长期处在“做需求”的惯性里：每次只问“这条需求怎么最快满足”，很少问“这条需求暴露了系统缺少什么能力”。

这会带来几个后果：

- 需求被实现成一次性分支，而不是沉淀为稳定规则。
- 相同业务概念在不同需求里被重复命名、重复判断、重复落库。
- 每次新增需求都看似很小，但都增加一个新的例外路径。
- 代码越来越像需求历史记录，而不是当前业务模型。
- 新人理解系统时，必须理解过去每一次临时决策。

典型思维差异如下：

| 需求惯性 | 抽象思维 |
|----------|----------|
| “产品要这个 case，加个 if。” | “这个 case 属于哪类规则？” |
| “这次先 hardcode，后面再说。” | “这个变化轴以后还会不会扩展？” |
| “这个接口临时特殊处理一下。” | “这是调用方差异、状态差异，还是权限差异？” |
| “测当前需求能过就行。” | “新增规则后，哪些旧规则不能被破坏？” |
| “需求做完了。” | “系统能力是否更清楚了？” |

好的工程实现应该同时交付两件事：

1. 满足当前需求。
2. 把当前需求背后的业务概念、规则归属或变化轴沉淀进系统。

这不意味着每个需求都要做大设计。更实际的训练要求是：即使先用简单实现，也要能说清楚“这是一次性例外，还是一个新规则的开始”。如果是新规则的开始，就至少给它一个名字、一个归属位置和一组测试。

### 1.2 为什么很多 if/else 是 smell

`if/else` 本身没有问题。坏味道通常来自这些情况：

- 分支嵌套过深，读者必须同时记住多个前置条件。
- 同一个条件或状态判断在多个文件重复出现。
- 一个函数同时做校验、状态判断、数据写入、外部调用和错误处理。
- `switch action/status/type` 的每个分支都在改多个资源，实际已经是隐式状态机。
- handler 通过字符串匹配错误消息决定 HTTP 状态码。
- 布尔字段越来越多，组合后形成隐藏状态，例如 `is_featured + review_status + allow_community`。

问题不在于“代码里有 if”，而在于 if 后面缺少名字、规则归属和变化边界。

### 1.3 为什么 bug 越来越多、效率越来越低

只为当前需求写代码，会让规则散落在多个入口。下一次改动时，工程师不知道某个分支是不是仍然有效，也不知道新需求会不会破坏旧例外。结果就是：

- 修改范围不可预测。
- 测试组合越来越多。
- 异常路径越来越难覆盖。
- 新人上手成本越来越高。
- AI 辅助修改时也更容易漏掉历史分支。

这会形成一个低效循环：

```text
新需求 -> 局部补丁 -> 更多隐式路径 -> 更难理解 -> 更多 bug -> 更慢交付 -> 更倾向继续补丁
```

抽象和重构要打断的正是这个循环。

## 2. 机制：为什么人和 AI 都不擅长大量 if/else

大量 `if/else` 的问题不只是“看起来乱”，而是它把理解任务变成了路径模拟任务。

### 2.1 人的问题：工作记忆装不下路径组合

人读代码时，会在脑中维护一组临时上下文：

```text
当前满足哪些前置条件？
哪些变量被改过？
当前状态是否合法？
这个 else 对应的是哪一个 if？
这个异常路径会不会跳过事务、日志或补偿？
```

分支少时，这种模拟还能完成；分支多时，路径数量快速增长，人的工作记忆会被耗尽。此时读者很容易出现几类错误：

- 忘记某个前置条件。
- 把互斥条件当成可同时发生。
- 忽略某条分支里的副作用。
- 只验证主路径，漏掉异常路径。
- 以为两个 case 相似，实际状态边界不同。

所以人不是不懂 `if/else` 语法，而是不擅长长期可靠地模拟大量隐式路径。

### 2.2 AI 的问题：上下文窗口不等于可靠推理状态

AI 也不擅长处理很多临时分支，但原因和人不完全一样。LLM 擅长根据上下文做模式归纳、语义补全和局部转换；大量 `if/else` 要求它做的是另一类任务：

```text
精确追踪每条路径
记住远处条件和当前分支的关系
判断条件是否互斥、重复或遗漏
维护跨分支不变量
预测修改一个 case 对其他 case 的影响
```

这些任务更接近符号执行、模型检查和穷举测试，而不是自然语言补全。即使上下文窗口足够大，AI 也可能在以下地方出错：

- 看到了所有代码，但没有稳定维护所有状态组合。
- 修改了当前分支，却破坏了另一个远处的例外分支。
- 认为相似分支可以合并，但漏掉关键业务差异。
- 按已有模式补全新 case，却没有发现旧抽象已经不适用。
- 对罕见路径、异常路径和历史兼容逻辑判断不足。

这就是为什么“把很多 if/else 丢给 AI 修一下”经常效果不稳定。AI 可以辅助重构，但前提是人先把变化轴、状态、规则和不变量表达清楚。

### 2.3 共同解法：把路径模拟变成概念判断

对人和 AI 来说，更友好的代码都具备同一个特征：它把低层路径压缩成有名字的概念。

```text
不好：读者和 AI 都要模拟 12 个条件组合。
较好：用 canCancel、isEligible、isTerminalState 命名关键判断。
更好：用 Policy、State Machine、Transition Table 表达规则边界。
```

抽象的作用不是让代码更“高级”，而是减少人和 AI 必须同时追踪的临时状态。好的抽象会让问题从“这 12 条分支分别会怎样”变成“取消规则、状态迁移、权限策略分别是什么”。

## 3. 学术视角：这些理论如何解释工程退化

### 3.1 有限理性与局部最优

Herbert Simon 的有限理性认为，人不是在无限信息和无限计算能力下做最优决策，而是在时间、信息和认知资源受限的条件下做“足够好”的决策。这正好解释了“做需求”的惯性。

工程师在排期压力下很容易选择局部最优：

```text
当前需求最快通过验收 -> 加一个局部分支
当前问题最快绕过去 -> hardcode 一个例外
当前接口最快兼容 -> 特判一个调用方
```

单次看，这些选择都合理；长期看，它们把复杂度转移到了未来。抽象思维的作用，是在局部交付之外保留一个系统性问题：“这次修改是否改变了规则、状态、流程或领域概念？”

### 3.2 工作记忆、组块化与专家差异

工作记忆研究说明，人能同时稳定处理的信息单元有限。专家和新手的差异，不是专家能记住无限细节，而是专家会把细节组织成更大的“组块”。

代码里的命名函数、领域对象、状态机、policy，本质上都是组块化工具：

```text
低层细节：status == paid && !shipped && role == buyer
高层组块：order.CanBeCancelledBy(user)
```

如果代码没有这些组块，读者就必须反复回到低层条件组合。维护者越多、需求越久，团队整体认知负荷越高。

### 3.3 认知负荷理论

认知负荷理论可以解释为什么设计差的代码会拖慢团队。读代码时真正有价值的认知资源，应该用于理解业务规则、状态边界和设计取舍；而坏代码会制造大量外在负荷，例如：

- 追踪多层嵌套条件。
- 在多个文件里寻找同一规则的重复实现。
- 猜测布尔组合背后的真实状态。
- 通过错误字符串推断业务语义。
- 在脑中模拟事务、副作用和异常路径。

抽象不是为了减少所有复杂度，而是把复杂度从“路径追踪”转移到“概念理解”。前者难以复用，后者可以被团队共享。

### 3.4 圈复杂度与路径爆炸

McCabe 的圈复杂度指出，分支会增加程序中独立执行路径的数量。虽然这个指标不能单独判断代码好坏，但它揭示了一个事实：分支越多，测试和理解路径越多。

真正危险的不是一个 `if`，而是多个维度组合：

```text
用户类型 3 种 x 订单状态 5 种 x 渠道 4 种 x 地区 6 种 = 360 种组合
```

如果这些维度没有被建模，代码会变成条件组合；如果它们被识别为规则、状态、策略或上下文，测试就可以围绕每个变化轴设计，而不是盲目枚举所有路径。

### 3.5 信息隐藏与模块化

Parnas 的模块化思想强调，模块应该围绕“可能变化的设计决策”来隐藏信息。也就是说，好的模块边界不是按代码长相切分，而是按变化来源切分。

当业务规则散落在 controller、service、job、handler 里时，规则本身没有归属。需求变化时，修改者无法判断应该改哪里，也无法确认哪里漏改。这就是信息隐藏失败。

更好的做法是把变化封装到明确位置：

- 取消规则属于 `CancellationPolicy`。
- 订单状态迁移属于 `OrderTransition`。
- 价格计算属于 `PricingPolicy`。
- 权限判断属于 `AuthorizationPolicy`。
- 跨上下文协作属于 workflow 或 application service。

### 3.6 软件演化与技术债利息

Lehman 的软件演化研究指出，长期使用的软件系统会持续变化；如果不主动控制复杂度，复杂度会随着演化增长。Brooks 也区分了本质复杂度与偶然复杂度：业务本身的复杂度无法消灭，但实现方式制造的复杂度可以减少。

技术债的“利息”正体现在这里：

```text
第一次 hardcode：省 2 小时
第二次兼容：多花 1 小时找旧逻辑
第三次改动：多花 1 天补漏测
第四次上线：出现回归 bug
```

所以，抽象训练不是审美训练，而是成本控制训练。它的目标是减少偶然复杂度，让团队把认知资源花在业务本质复杂度上。

### 3.7 DDD 与共同语言

DDD 的学术与工程价值在于降低“业务语言”和“代码语言”之间的翻译成本。团队讨论的是“可取消订单”“退款中状态”“企业客户计价规则”，代码里也应该出现这些概念。

如果代码只有 `if status == 3 && type == 2 && flag == true`，每个维护者都要重新翻译一次业务含义。翻译次数越多，误解和 bug 越多。共同语言让团队把知识固化在模型、命名和测试里。

## 4. 判断：局部重构、整体重构，还是保持简单

### 4.1 先判断变化轴

看到复杂分支时，不要直接套设计模式。先判断变化轴。

| 变化轴 | 常见症状 | 更合适的抽象 |
|--------|----------|--------------|
| 前置条件和异常路径 | 主流程被多层嵌套淹没 | Guard clause、命名判断函数 |
| 按类型变化 | `if user.type == ...` 到处出现 | Strategy、map dispatch、多态 |
| 按状态变化 | `switch status/action` 改多个字段 | 状态机、Transition、领域事件 |
| 按业务规则变化 | 规则经常新增、组合、开关 | Policy、规则表、规则数组 |
| 按流程步骤变化 | 一个函数串起多步外部调用 | Pipeline、Workflow、Saga |
| 按业务概念变化 | 多处复制业务判断，术语不一致 | DDD Entity、Value Object、Bounded Context |

抽象的顺序应该从低风险开始：

1. 给复杂条件命名。
2. 用 guard clause 拉平主流程。
3. 抽出重复规则。
4. 识别变化轴。
5. 只有当规则确实复杂或持续变化时，再引入 Strategy、State Machine、Policy 或 DDD 模型。

### 4.2 什么时候需要整体重构

当复杂度还局限在一个函数或一个规则里时，局部重构通常足够：命名判断、拆函数、guard clause、抽 policy，都可以解决问题。

但当问题扩散到多个入口、多个状态、多个调用方和多次历史需求时，继续局部修补就会失效。原因是局部修改只能改变某一条路径，不能重新定义系统的规则边界。

典型信号包括：

- 同一个业务规则在 controller、service、job、consumer 中重复出现。
- 每次需求都要在多个地方补同一个 case。
- 状态字段、布尔字段和错误字符串共同决定行为，但没有统一状态模型。
- 测试只能覆盖当前需求，无法证明旧规则没有被破坏。
- AI 或 reviewer 能看懂单段代码，却无法判断全局影响。
- “这次先特殊处理”已经发生过很多次，且没人知道哪些特殊处理还能删除。

这时需要整体重构，不是因为代码“不优雅”，而是因为系统已经缺少可维护的认知结构。整体重构的目标也不是大规模改写，而是重新建立几个关键东西：

1. 统一业务概念：同一个概念只有一个名字。
2. 统一规则归属：一条规则只在一个明确位置表达。
3. 统一状态模型：合法状态、非法状态、迁移条件和副作用可见。
4. 统一变化轴：新增 case 时知道应该扩展哪个 policy、strategy、transition 或 workflow。
5. 统一测试边界：测试围绕规则和状态，而不是围绕历史补丁。

### 4.3 什么时候不该抽象

抽象不是越多越好。以下情况应保持简单：

| 信号 | 判断 |
|------|------|
| 只有一个简单条件 | 保持 `if`，不要引入模式。 |
| 变化方向不明确 | 先命名、拆函数，延迟引入大抽象。 |
| 抽象命名比原代码更难懂 | 抽象失败，应退回或改名。 |
| 只是为了消灭 if/else | 动机不成立。 |
| 需要读 5 个文件才理解一条规则 | 可能过度设计。 |

## 5. 方法：DDD 和调研如何帮助抽象

### 5.1 DDD 的作用

DDD 的价值不是让代码更“面向对象”，而是把业务复杂度从流程判断提升成领域模型。

过程式代码通常这样表达：

```go
if order.Status == "paid" && !order.Shipped && user.Role == "buyer" {
    // cancel
}
```

领域模型应该让读者看到业务语义：

```go
if order.CanBeCancelledBy(user) {
    order.Cancel(reason)
}
```

当规则继续复杂，可以再引入 policy：

```go
cancellationPolicy.AssertCanCancel(order, user)
order.Cancel(reason)
```

DDD 最适合业务规则复杂、状态流转多、团队对概念理解不一致、需求经常变化的系统。简单 CRUD、一次性脚本、稳定配置页不需要硬套 DDD。

### 5.2 为什么人不主动学习抽象概念

很多工程师不是不愿意学习抽象，而是工作环境会不断强化“先把当前需求做完”的行为。

常见原因包括：

- 交付压力让人优先选择眼前可见的最短路径。
- 抽象能力的收益通常滞后，bug 减少和效率提升要到后续需求才显现。
- 很多人缺少成熟系统的参照，只能在自己的代码里原地摸索。
- 团队 review 更关注功能是否通过，较少追问模型、边界和规则归属。
- 过去被过度设计伤害过，于是把所有抽象都等同于“绕”。
- 需求文档只描述 case，不描述规则、状态和变化轴。
- 缺少复盘机制，没人把“这次 bug 是哪条隐式规则造成的”沉淀出来。

所以抽象思维不是靠讲道理自然长出来的。它需要训练材料、外部样例、review 反馈和真实重构经验。

### 5.3 用调研学习别人怎么抽象

学习抽象概念最有效的方式之一，是调研成熟产品、开源项目和行业方案如何处理同类问题。抽象不是凭空发明，很多时候是从外部系统中观察出来的。

调研时不要只看“别人有什么功能”，还要看“别人把问题抽成了什么概念”：

| 调研问题 | 要观察的抽象 |
|----------|--------------|
| 竞品如何描述这个功能？ | 领域词汇、用户心智、能力边界 |
| 开源项目如何组织模块？ | 模块边界、接口设计、扩展点 |
| 成熟系统如何处理状态？ | 状态机、transition、非法迁移 |
| 规则如何配置和测试？ | Policy、规则表、decision table |
| 异常和兼容逻辑放在哪里？ | 错误类型、补偿流程、fallback |
| 新增一个 case 要改哪里？ | 变化轴和扩展点 |

内部可以使用 `skills/product-tech-research` 做这种调研。它的关键价值不是“找资料”，而是把外部事实转成对本系统的设计启发：

```text
别人怎么命名这个概念？
别人把规则放在哪一层？
别人如何限制状态迁移？
别人开放了哪些扩展点？
别人避免了哪些我们正在踩的坑？
```

当团队对抽象方向没有把握时，不要只在会议里争论“要不要 DDD”“要不要策略模式”。更好的方式是先调研 3 类外部参照：

1. 竞品产品体验：看用户视角如何理解这个能力。
2. 开源实现：看工程上如何拆模块、定义接口和测试边界。
3. 技术趋势/最佳实践：看行业里已经形成了哪些通用模型。

调研结论应该进入 `docs/product-tech-research/`，作为后续 User Story、架构设计和重构方案的输入。这样抽象就不再是个人偏好，而是有外部证据和业务语境支撑的工程判断。

## 6. 训练：如何培养抽象思维

### 6.1 命名训练

要求自己看到复杂条件时先回答：“这个判断在业务上叫什么？”

```go
// Before
if order.Status == "paid" && !order.Shipped && user.Role == "buyer" {
    cancelOrder(order)
}

// After
if canBuyerCancelOrder(order, user) {
    cancelOrder(order)
}
```

这一步看似简单，但它已经把条件细节压缩成业务含义。

### 6.2 主流程训练

把异常路径提前返回，让主流程浮出来。

```go
if user == nil {
    return ErrMissingUser
}
if order == nil {
    return ErrMissingOrder
}
if !canBuyerCancelOrder(order, user) {
    return ErrCannotCancel
}

return cancelOrder(order)
```

这类训练适合刚从过程式代码转向设计思维的人，收益直接，风险低。

### 6.3 变化轴训练

拿一段分支代码，标注每个条件属于哪类变化：

```text
用户类型变化？
订单状态变化？
支付渠道变化？
地区规则变化？
异常处理变化？
```

如果分支混合了多种变化轴，通常说明函数职责过重。

### 6.4 需求翻译训练

拿到需求后，先不要直接写代码，先把需求翻译成三句话：

```text
用户要完成什么业务动作？
这条需求改变了哪条规则、状态或流程？
这类变化以后还会不会继续出现？
```

再决定实现层级：

- 如果只是一次性展示差异，可以保持简单条件。
- 如果是可重复规则，至少抽成命名函数或 policy。
- 如果涉及状态流转，优先明确 transition 和合法/非法迁移。
- 如果涉及多个概念边界，先补领域词汇和责任归属。

训练目标是让工程师从“接需求 -> 写代码”升级为“接需求 -> 识别变化 -> 选择抽象 -> 写代码”。

### 6.5 三版实现训练

同一个需求写三版，再比较取舍：

```text
版本 A：直接 if/else
版本 B：命名函数 + guard clause
版本 C：Strategy / Policy / State Machine / DDD
```

比较四个问题：

- 哪个最容易读？
- 新增一个 case 要改哪里？
- 哪个测试最清楚？
- 哪个抽象过度了？

训练目标不是背模式，而是建立判断力。

### 6.6 调研训练

对一个复杂业务模块，要求工程师使用 `product-tech-research` 或等价方式调研外部参照，并输出 5 个结论：

1. 外部系统如何命名核心概念。
2. 外部系统如何拆分模块边界。
3. 外部系统如何表达规则和状态。
4. 外部系统如何测试关键变化轴。
5. 哪些做法适合我们，哪些不适合我们。

调研训练的目标，是让抽象判断不只来自个人经验，也来自成熟系统的可验证参照。

### 6.7 Code Review 问题清单

Review 复杂分支时，固定问这些问题：

- 这次需求是在补一个 case，还是在引入一类规则？
- 这个实现只是满足当前需求，还是让系统多了一个清晰能力？
- 这个条件表达的业务概念叫什么？
- 这个判断会不会在别处重复？
- 这是类型分支、状态分支、规则分支，还是流程分支？
- 这个分支是否同时修改多个资源？是否需要事务或状态机？
- 新增一个状态、动作、渠道或规则时，需要改几个文件？
- 当前抽象是在帮助理解，还是只多绕了一层？
- 如果 reviewer 和 AI 都需要穷举很多路径才能理解，这里是否应该改成命名判断、decision table、state machine、policy 或更明确的测试？

## 7. 落地：团队如何形成习惯

### 7.1 该抽象的信号

| 信号 | 判断 |
|------|------|
| 嵌套超过 2 层 | 优先考虑 guard clause 或拆函数。 |
| 同一条件重复 3 次以上 | 需要命名函数、Policy 或领域方法。 |
| `switch action/status` 每个分支都改 DB | 通常是隐式状态机，需要 Transition/事务。 |
| handler 按错误字符串判断响应码 | 需要 typed error。 |
| 一个函数超过 200 行且多职责 | 需要按流程步骤或领域职责拆分。 |
| 测试用例随分支指数增长 | 需要重新识别变化轴。 |
| 加一个业务规则要改多个模块 | 需要集中规则归属。 |
| 每个需求都新增局部分支 | 需要识别背后的能力、规则或领域概念。 |

### 7.2 团队落地方式

1. Code Review 不说“这里 if else 太多”，而是指出“这里缺少哪个业务概念”。
2. 对新人先训练命名和 guard clause，不急着讲设计模式。
3. 对复杂业务模块建立领域词汇表，避免同一个概念在不同文件有不同名字。
4. 对状态流转建立状态表或 transition table，并要求测试覆盖每条合法/非法迁移。
5. 对重复规则建立 policy，并用单元测试锁住边界。
6. 对需求评审增加一个工程问题：“这条需求是在扩展已有能力，还是暴露了缺失的能力？”
7. 对抽象方向不确定的模块，先做 product-tech research，再写 User Story、架构设计或重构方案。
