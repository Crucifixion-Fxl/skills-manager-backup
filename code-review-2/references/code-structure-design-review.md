# 代码结构与新增逻辑必要性评审

由现有代码结构与质量审查员执行；系统级架构、公共 API 和数据模型仍由架构审查员负责。
命名、类型安全、错误处理等通用清单沿用 [SKILL.md](../SKILL.md)「代码质量与工程规范」，
这里仅补充新增逻辑的必要性、复用判断和证据要求。

## 适用范围与检查方法

控制流、职责、依赖或抽象变化时，按**同一业务行为或不变量**合并检查，
不要为共同实现该行为的每个 helper 重复检索。纯机械改动一行说明“无结构增量”及依据。
行为兼容性另按 [行为覆盖规则](behavior-coverage-review.md) 选择简要或详细核验。

1. 从验收、同期契约和直接调用链确定新增行为；删除它是否仍能满足明确需求？
2. 提取触发入口、输入/前置条件、写入目标、状态/事件、副作用及业务不变量，
   用这些锚点搜索当前模块、直接依赖和公共能力。名称不同不代表语义不同；只比较直接候选，
   取得足够证据即停止，不扩大为全仓结构审计。
3. 比较候选的输入输出、权限/租户、事务/锁/幂等、错误/重试/降级、生命周期、性能及 owner。
   判断应复用、扩展还是独立；不能因为共同调用底层库，就把新增 registry/policy 规则算成直接复用。
4. 核对职责和依赖方向；抽象是否隔离实际变化，或仅增加跳转与装配？
   两份规则是否必须共同修改，漏改一处有什么具体后果？代码形似或想象中的未来需求不足以要求抽象。

## 三个判断分别成立

| 判断 | 允许结论与依据 |
|---|---|
| 行为必要性 | **必要**：验收/既有契约要求；**不必要**：删除不损失验收能力；**未决**：需求本身不足以判定；**不适用**：无新增行为 |
| 实现复用判定 | **应直接复用**：既有能力已完整满足相同契约；**应局部扩展**：既有 owner 和扩展点明确；**允许独立实现**：关键语义或所有权约束不同；**未决**：缺少比较契约/owner 所需证据；**不适用**：机械改动或无实现选择 |
| 证据状态 | **无 finding**；**confirmed P0/P1/P2**：满足下方证据要求；**设计依据待说明**：缺需求、语义契约或 owner 依据，记 pending；**实现正确性待核验**：前两项可判定，但缺运行/部署/生成结果，记 pending |

行为必要不代表实现合理；应复用也不代表行为不必要。缺少运行、部署或 codegen 结果，
默认只影响实现正确性，不能把前两项自动改成未决。若明文要求生成物同步且 HEAD 已确认缺失，
应报告该明确违约，而非“尚未验证”。

例如：验收要求新增 feature-flagged alias，registry 的 owner/扩展点明确，但生成结果未取得，
结论是“必要 / 应局部扩展 / 实现正确性待核验”。

## Finding 的证据与归因

Confirmed 结构问题必须同时给出：

- 候选 HEAD 的 `file:line`，及被比较的既有实现、明确边界或调用图/测试支持的基线；
- 代码事实支持的反例和结构后果，例如同一业务规则必须多处同步、依赖方向被反转，
  或一次变化必须修改无关模块；提出复用前也要尝试用权限、事务、数据源或 owner 差异证伪；
- 本次引入/扩大的因果与 diff 位置；若属既有债，按主 Skill 的 pre-existing 规则处理，
  不要求当前 MR 顺手重构。

若“该输入合法”“该行为必须支持”等关键前提没有契约/不变量证据，代码复现只证明实际行为，
不能证明它违约。按主 Skill 的证据门槛记 pending/unverified，不将猜测降为 P2 finding。

P0 按主 Skill 的影响证据门槛；当前可触发的功能错误与仅有重复维护成本分别按其已证明影响
判断 P1/P2，不由“已确认”直接推出 P0。当前行为正确时，应明确结构建议的维护后果和取舍。
两处边界都需要校验，不等于应删除一处校验；共享策略定义与合并调用边界应分别判断。

## 输出

最终报告只在内容质量章节汇总一次，不重复输出角色模板与覆盖表：

- 有 finding：给出必要性、复用选择、比较证据、反例和归因；级别沿用主 Skill。
- 无 finding：最多三行说明必要性、复用选择及证据；机械改动只写一行。
- 缺设计/owner 依据：写“设计依据待说明”和最小待确认项；仅缺运行结果：写“实现正确性待核验”和最小验证项。
- pending 不计 confirmed 问题数或评分，也不替代适用的安全、测试或发布证据门禁。
