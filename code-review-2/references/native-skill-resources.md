# Code Review 的隔离安装资源归属

本 Skill 的审查方法、必读材料与专项激活条件，以同一源码版本的 `SKILL.md`
及其 references 为正本。安装工具只负责保留、打包和校验这些依赖，不重新定义
审查门禁。资源可用也不代表调用方获得审批、评论或其他写入权限；执行职责仍按
[执行边界](execution-boundary.md) 与可信调用方契约核验。

## 从源码识别依赖

- 保留本 Skill 自身的完整目录和规范相对路径；不能把入口目录平铺后假定跨目录
  引用仍然有效。
- 默认 MR 流程在 Step 0.0 先读取
  [Issue 生命周期契约](../../../collaboration/gitlab-issue-sop/references/lifecycle-binding.md)。
  远程 MR 的 TDD Level 观测读取
  [TDD Level 定义](../../testing-strategy/references/tdd-level-assessment.md)；
  必须能读取该定义，不改变观测项的非门禁语义。
- 安全、固件、部署、架构/目录、大文件及独立 QA 委派等材料是否必需，由同版本
  方法中对应触发条件决定。调用方不得将一个基础包解释为支持全部专项，也不得
  因未打包某材料而跳过已触发的要求。
- 选中的依赖还可能链接其他资源；安装声明需要覆盖实际可达的传递引用。项目内
  证据属于被审仓库，必须逐项辨认，不能为消除断链而复制无关业务文件或宽泛豁免。

这些是依赖识别规则，不是所有源码版本的固定文件清单。新增引用、调整必读步骤或
专项条件时，必须在对应方法正本修改，并复核隔离分发需要的声明；不能只修改
运行实例的安装清单来改变审查含义。

## 三方职责

| Owner | 维护内容 |
|---|---|
| `code-review` | 共用审查方法、资源引用与必读/条件依赖含义 |
| `buzz-agent-setup` | 通用安装、显式依赖打包、内容与发现入口校验机制 |
| 调用方运行仓 | 具体 Agent、固定源码版本、该版本的依赖快照、包摘要、发布及回滚配置 |

运行仓的固定 profile 是对已审源码版本的安装快照，不是另一份审查规则。升级时由
运行 owner 对照目标源码重新审查快照，冻结新摘要，再按已有授权发布；本说明不
自动同步任何运行实例，也不指定生产源码 SHA、文件数量或本机路径。

包构造、安装成功、实际加载、真实独立审查与写入回读分别验收。通用安装成功不能
替代调用方自己的业务验收，源码更新也不能冒充已有实例已经安装。
