# GitLab 仓库接入飞书 MR 审批

## Description

公司「代码合并审批」服务让人离开电脑时在飞书里审批、合并 MR，是 GitLab 的延伸而非门禁：
GitLab 原生合并照常可用。所有仓库共用已部署服务，入口：
https://gitlab-feishu-approval.addx.live/projects

一次申请对应一个仓库和一个准确的目标分支。获批后，服务按触发规则发现该分支**启用后新建**的 MR，
通常 1 分钟内、最长约 10 分钟创建飞书待审批。用户不需要安装服务、配置 Webhook、提供 Open ID 或修改 CI。

页面只接受本组织飞书客户端原生登录和本人 GitLab 授权，没有面向 Skill 的 PAT 或服务账号。
因此默认交付方式是**生成预填链接**，由用户在飞书中打开、选人、核对并提交；
只有宿主提供能读取并操作飞书窗口的工具时，才代填提交。
控件、接口与故障对照见 [界面和接口参考](references/api-reference.md)；认证与源码入口见 [SaaS 接入](references/saas-access.md)。

## Rules

### 1. 收齐配置，区分两类审批人

先复用会话里用户已给的信息，只把缺失或有歧义的项集中问一次：

| 信息 | 要求 |
|---|---|
| 仓库地址与目标分支 | `https://gitlab.addx.ai/组织/仓库` 与实际存在的分支名。不把 MR、tree 页面或模糊分支当仓库；只有短名时先核对完整路径。 |
| MR 审批人 | 1–20 位本组织在职成员，可给姓名、别名或拼音。AND 时顺序即审批先后，最后一人负责合并。可以尚未绑定 GitLab（首次打开待办时绑定）。 |
| MR 审批方式 | OR：任意一人通过；AND：按顺序全部通过。未指定时询问，不擅自把多人变成 OR。 |
| 本次接入申请的审批人 | 一位对该仓库有 Maintainer / Owner 权限的在职成员，与 MR 审批人分开确认，不自动取名单第一人或当前用户。尚未绑定 GitLab 也可选：对方在飞书待办中先绑定，批准时核验权限。 |
| 触发条件 | 「添加指定标签后」或「全部 MR」，都只送审非草稿 MR。说按标签但没给名称时用 `feishu-approval` 并在摘要中写明；首次接入未说明时询问，修改时保留原规则。 |
| 作者优先 | 作者有合并权限时优先交给作者。首次接入时询问开或关；修改时保留原值，用户要求时可改，只影响之后新建的流程。 |

只给仓库、分支、MR 审批人和 OR/AND 时，还缺接入审批人；首次接入还缺作者优先和触发方式。

### 2. 默认交付：预填链接

参数齐全（或用户只要链接）时，生成链接让用户在飞书中打开：

1. 拼业务地址：`https://gitlab-feishu-approval.addx.live/projects?repository=<仓库URL>&branch=<分支>&mode=OR|AND&trigger=label|all&label=<标签>&author_first=0|1`。每个值做 URL 编码；没确定的参数直接省略，不猜。
2. 包成飞书端内链接：`https://applink.feishu.cn/client/web_url/open?mode=window&url=<上一步整条地址再 URL 编码>`。
3. 交付：链接，加不超过五行的填表摘要（仓库＋分支、MR 审批人与顺序、OR/AND、触发方式和准确标签、作者优先、接入审批人）。说明人员只能在页面里搜索选择，链接不含人员；请用户核对后点「提交飞书接入审批」，把「查看本次申请」链接发回来。
4. 页面读取配置后会显示「部分设置已按链接预填，请核对后提交」。没有这句提示说明服务版本还不支持预填，请用户按摘要手动填写。

链接只预填表单，不代表已提交。用户发回申请链接前，只说「已生成填表链接，尚未提交」。

### 3. 宿主能操作飞书窗口时代填

仅当宿主有读取并操作飞书窗口的工具，且用户明确要求代为提交时执行：

1. 在飞书窗口打开入口（可用上面的预填链接），复用已有会话；页面通过固定入口 `/auth/feishu/client` 原生验证。需要用户授权或绑定 GitLab（「绑定 / 更新 GitLab 授权」）时交用户本人完成。只有看见「接入 MR 审批」表单才继续。
2. 点「读取项目配置」，等到显示规范仓库名、分支和「尚未接入 / 已启用 v… / 已停用」。已有配置时保留用户没要求改的项，展示旧 → 新差异。
3. 「添加审批人」里按姓名、别名或拼音搜索并选实际结果；重名或多候选时向用户核对，不选第一项。名单后标注「无合并权限」的人仍可审批，但合并要转交有权限的人；向用户说明，用户决定是否保留。
4. 「选择审批人」指定接入审批人。显示「尚未绑定 GitLab」可以继续；提示不是 Maintainer / Owner 时不能提交。
5. 触发标签下方提示「项目中还没有标签」时，告诉用户需要有标签管理权限的人先在 GitLab 创建该标签。
6. 用五行摘要核对。用户已明确要求提交、各项明确且与页面一致时点「提交飞书接入审批」一次，不重复索要同一授权。

每次操作后重新读取页面，不复用旧元素编号，不绕过禁用按钮或权限预检，不改 DOM，不直接调用接口。
只有页面出现「申请已提交」和「查看本次申请」链接才算提交成功；读取该链接，确认是服务源站 `/enrollments/` 路径，再回读详情核对配置。
提交超时或显示「上次提交结果待确认」时，先点「检查上次提交的申请」：存在就复用；明确不存在且页面允许才用原编号、原配置重试；仍不确定就报告「结果待确认」。不清会话存储、不换编号、不连点提交。

### 4. 修改、停用与撤回

- 修改审批人、OR/AND、触发规则或作者优先：都走新的接入申请；获批前旧配置继续生效，获批后只影响新建的流程，在途 MR 保留原快照。旧配置显示「全部 MR（旧配置，含草稿）」时，改为新规则会变成只送审非草稿，需向用户说明。
- 停用分支：项目 Maintainer / Owner 在接入页读取配置后点「停用此分支的审批」，立即生效，无需飞书审批；在途流程不受影响。之后再提交并获批申请即可重新启用。不是 Maintainer 时告诉用户找谁处理。
- 撤回申请：申请人在申请详情页点「撤回申请」，飞书待办随之关闭。接入审批人暂时无法处理时，可撤回后改交他人。同一分支另一份申请获批时，其余待审批申请会自动关闭。

### 5. 交付与接入后验证

提交成功后交付：仓库＋分支、MR 审批规则和触发条件、接入审批人、申请链接，状态写「已提交，等待飞书审批」。
提醒接入审批人在飞书「审批 → 待审批」处理。只有回读项目配置显示预期的「已启用 v…」才能说已启用；
终态详情不再显示，看到「审批已结束」或 HTTP 410 不能当成已通过。

验收要在启用后新建一条目标分支匹配的 MR：

- 标签模式：先不加标签，应没有待办；在 MR 的 Labels 中加上准确的标签（区分大小写），并确认 MR 不是草稿，应在 10 分钟内出现飞书待办。
- 启用前已创建的 MR 不会补发，不要为催促旧 MR 重复提交申请。
- 被拒绝的 MR 推送新提交、或关闭后重新打开时，会自动发起新一轮审批（待办标题注明轮次）。
- 用户只授权配置接入时，不顺带创建测试 MR、不修改 MR 标签。

服务后台用接入批准人的授权只读发现新 MR；批准人失去权限时，暂由名单中的维护者代读，接入页会提示更换批准人。
合并、关闭、Pipeline 操作始终使用实际点击者本人的授权。授权失效或待办投递待重试时，先读取状态，不重复申请。

### 6. 边界

- 密码、验证码、OAuth code、Cookie、CSRF 和令牌只留在正常的飞书和服务流程里，不读取、打印、导出或复制到 CLI。
- 不索取 App Secret、Vault token 或 Open ID；不用管理员 PAT、其他应用凭证或他人身份代办。
- 本 Skill 不点「同意并启用此配置」、拒绝、转交，也不审批或合并任何 MR；这些不在提交申请的授权范围内。
- 不得宣称原生登录能证明设备身份，或宣称本服务会拦截 GitLab 原生合并。

## Examples

### Good

用户：把 `https://gitlab.addx.ai/TEAM/service-example` 的 `main` 接入；MR 审批人甘布、测试同事，OR；接入申请交指定维护者；关闭作者优先，按标签触发。

执行：参数已齐，生成预填链接（`mode=OR&trigger=label&label=feishu-approval&author_first=0`）。
交付五行摘要，说明人员需在页面搜索选择，链接不代表已提交，请用户提交后发回申请链接。

用户：已启用的这个分支换成甲 → 乙两级审批，作者优先也打开。

执行：说明作者优先可以修改，只影响之后新建的 MR。补问接入审批人；生成 `mode=AND&author_first=1` 的预填链接，摘要写明审批顺序和旧 → 新差异。

### Bad

- 只生成了链接，就说「已提交」或「已启用」。
- 用户只给了 MR 审批人，就把名单第一人当接入审批人。
- 复制 Cookie、使用旧回调或管理员 token 直接调接口，绕过本人登录和选人校验。
- 看到终态页面就说「已经通过」；为催促启用前的旧 MR 重复提交申请。
