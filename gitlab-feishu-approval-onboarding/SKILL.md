# GitLab 仓库接入飞书 MR 审批

## Description

首次接入/变更扫描与日常认证入口见 [SaaS 接入](references/saas-access.md)；已有平台业务契约与授权门禁仍在本 Skill 维护。

操作公司「代码合并审批」服务的项目接入页：
https://gitlab-feishu-approval.addx.live/projects

所有仓库共用已部署的服务。一次申请针对一个仓库和一个准确的目标分支，
获批后按已批准的触发规则发现该分支的 MR 并创建飞书待审批。用户不需要安装服务、
配置 Webhook、提供 Open ID 或修改仓库 CI。

接入方式为 T3-Browser：本组织飞书客户端原生登录与本人 GitLab OAuth，使用宿主已提供的
飞书客户端界面工具操作实际页面；仅能控制普通浏览器的工具不能完成登录后的代填。
表单为原生 HTML，无侧边栏；入口 `/projects`，
申请详情 `/enrollments/{id}`。没有面向 Skill 的 PAT/服务账号登录方式。
页面与故障对照见 [界面和接口参考](references/api-reference.md)。

标签触发依赖服务新版本。必须在实际页面看到「何时发起 MR 审批」再配置；
旧页面缺少该字段时，不把已有“全部 MR”当作标签触发，不以接口或脚本绕过，不提交不符合用户要求的申请。

## Rules

### 1. 收齐配置，区分两类审批人

先复用本次会话中用户已给出的信息；只问缺失或有歧义的项，集中问一次：

| 信息 | 要求 |
|---|---|
| 仓库地址与目标分支 | `https://gitlab.addx.ai/组织/仓库` 与实际存在的分支名。不得把 MR、tree 页面或模糊分支当仓库配置；只有短名时先核对完整路径。 |
| MR 审批人 | 1–20 位本组织在职成员，可给姓名、别名或拼音。AND 顺序就是审批先后顺序。 |
| MR 审批方式 | OR：任意一人通过；AND：按名单顺序全部通过，最后一人负责合并。未指定时询问，不擅自把多人变成 OR。 |
| 本次接入申请的审批人 | 一位本组织在职成员，已绑定本人 GitLab，且对该仓库有 Maintainer / Owner 权限；与 MR 审批人分开确认，不自动取名单第一人或当前登录人。 |
| 触发条件 | 「添加指定标签后」或「全部 MR」。用户明确说按标签但未指定名称时使用 `feishu-approval` 并在摘要展示；首次接入未说明方式时询问，已有配置保留原规则。 |
| 作者优先 | 首次接入时明确选择开启或关闭，首次批准后永久固定。已有配置直接读取固定值，不能替用户更改。 |

用户只给仓库、分支、MR 审批人和 OR/AND 时，还缺本次接入审批人；首次接入还需作者优先和触发方式选择。
登录并读取配置可先进行，只有提交依赖这些信息全部确定。

### 2. 使用用户自己的登录会话

1. 在本组织飞书中打开上面的 HTTPS 入口，优先复用当前任务已授权的飞书窗口。普通浏览器或桌面审批内嵌页显示「在飞书中打开」时，使用该可见入口转到飞书窗口，再重新读取窗口状态。
2. 页面通过固定入口 `/auth/feishu/client` 自动验证本人身份并返回原页面；已有有效会话会直接继续。若出现「在飞书中重新验证」，点击后重新读取页面。不要使用已停用的浏览器 OAuth 登录或回调，不手工构造授权码。首次授权需要用户操作时交用户完成。
3. 需要 GitLab 授权时，点「绑定 / 更新 GitLab 授权」，让用户登录自己的 GitLab。
4. 返回原标签页后重新读取页面。只有看见「接入 MR 审批」表单才继续；不要凭旧截图操作。

登录是用户的一次性操作，能复用会话就不重复登录。密码、验证码、OAuth code、
Cookie、CSRF 和令牌留在正常飞书网页/服务流程内；不要读取、打印、导出或复制到 CLI。
不索取 App Secret、Vault token，不用管理员 PAT、其他飞书应用的 Open ID 或他人身份代办。
没有能读取和操作飞书窗口的工具，或原生身份验证未完成时，交付填表摘要和入口，说明尚未提交。
仅打开外部浏览器或触发飞书跳转不证明登录成功，不编造 CLI 或认证捷径。

### 3. 先读当前配置，再填名单

1. 填「代码仓库地址」「目标合并分支」，点「读取项目配置」。等待显示规范仓库名、分支，以及「尚未接入」或「已启用 v…」。页面报错时先按参考处理，不能假定仓库不存在。
2. 核对「何时发起 MR 审批」和「触发标签」，按用户要求设置。已有配置时，保留用户未要求修改的内容，展示旧 → 新差异。修改仍是新的接入审批申请；通过前旧配置继续使用，通过后只影响新建流程，正在审批的 MR 不变。
3. 点「添加审批人」，在「姓名、别名或拼音」里搜索并选择实际结果。支持单字、飞书别名、完整拼音；如 `甘` / `ganbu`，或 `run` 匹配姓名中读音为 run 的汉字。最多返回 20 人；重名或多候选不能直接选第一项，向用户核对可见姓名。GitLab 用户名搜不到时改用飞书姓名，不按同名或邮箱推断绑定。
4. 按用户顺序添加 MR 审批人并设置 OR/AND。可选择「尚未绑定 GitLab」的 MR 审批人，对方首次处理时自行绑定；能被搜到或选中不代表拥有合并权限。
5. 设置首次接入的作者优先；已有配置的此选项为禁用状态，保留不动。点「本次接入申请的审批人」下的「选择审批人」，搜索指定人员并等待权限预检通过。

若旧配置显示「全部 MR（旧配置，含草稿）」，更新为新“全部 MR”会改为非草稿才送审；用户要求其他不变时先明确这一差异，不能隐瞒额外改变。

每次操作后读取最新页面，不缓存旧的元素编号，不绕过禁用按钮。若切换标签页导致表单清空，
重新读取配置并重填；不能认为内存中的旧名单仍然已填写。
接入审批人未绑定、非在职或无项目管理权限时不可提交，不能通过修改 DOM 或直接请求跳过校验。

### 4. 提交一次，核对真实回执

提交前用最多五行向用户展示：仓库＋分支及版本变化、MR 名单与 OR/AND 顺序、触发方式和准确标签、接入审批人、作者优先。
用户已经明确要求提交、各项明确且与页面一致时，继续点「提交飞书接入审批」，不重复索要同一授权。
用户只要求预览/草稿时停在填表摘要；缺项、重名或出现未经授权的配置变化时先澄清。
始终遵守宿主对敏感操作的确认要求，本 Skill 不替代该要求。

只有页面出现「申请已提交」和「查看本次申请」链接才报告提交成功。
读取该链接，确认仍是服务 HTTPS 源站的 `/enrollments/` 路径，再回读详情核对配置、接入审批人和版本。
发现回执与本次配置不一致时停止，不把旧申请作为本次成功结果。
网页回执只证明申请已受理，不证明飞书已经送达，更不证明配置已启用。
本 Skill 不点「同意并启用此配置」、拒绝、转交或任何具体 MR 的合并按钮；这些不属于提交申请的授权。

若提交超时或显示「上次提交结果待确认」，先用页面「检查上次提交的申请」核对已有申请。
保留当前登录用户对应的原申请编号；不要清空会话存储、改编号或连点提交。
原申请不存在且页面允许重试时沿用原编号和原配置；无法判断时报告“结果待确认”。
切换登录账号后不能带入原账号的申请编号、配置或人员列表。

### 5. 交付与接入后验证

成功后给用户：仓库＋分支、MR 审批规则和触发条件、接入审批人、申请链接，以及状态“已提交，等待飞书审批”。
提醒指定审批人在飞书「审批 → 待审批」处理。只有回读项目配置显示预期的「已启用 v…」，才能说已启用；
终态详情不再展示，不能把“审批已结束”或 HTTP 410 单独理解为已通过。

接入后测试要在首次启用之后创建一条目标分支匹配的新 MR。按标签模式先不加标签，应无待办；在 GitLab MR 的 Labels 中添加已批准的准确标签，非草稿才触发。若标签还不存在，交有该仓库标签管理权限的人创建；不换成近似标签或借管理员账号。用户只授权配置接入时，不顺带创建测试 MR 或修改 MR 标签。

标签可创建时添加或后补，区分大小写、完整匹配；带标签草稿要标记为就绪。已创建审批不因移除标签撤销；重复加标签不重复送审。修改规则只影响尚未创建的流程，且保留首次接入的 MR 时间范围。

后台轮询发现并异步投递，通常几十秒，
繁忙时更久；接入前已有 MR 不补发，已结束再重开的同一 MR 不自动创建第二次流程。
开启作者优先时，作者未绑定/授权失效会等待绑定；已绑定且有实际合并权限才交作者，否则走配置名单。
后台使用接入批准人的授权只读发现，合并/关闭/Pipeline 操作始终使用实际点击者授权。
授权失效或飞书投递待重试时先查询状态，不重复申请来催送。

当前只负责这一服务的接入。普通浏览器没有正常建立登录会话的入口，业务数据仍需本组织身份和资源权限。
不得宣称原生登录能证明设备身份或阻止已授权用户主动导出有效会话，也不得宣称此服务强制拦截 GitLab 原生合并。

## Examples

### Good

用户：帮我把 `https://gitlab.addx.ai/TEAM/service-example` 的 `main` 接入；MR 审批人甘布、测试同事，OR；接入申请交指定维护者；关闭作者优先，按标签触发，请提交。

执行：读取仓库和分支及标签控件 → 填 feishu-approval → 姓名/别名搜索并消除歧义 → 接入审批人权限预检 → 核对五行摘要 → 提交一次 → 回读本次申请。
交付：“已提交，等待指定维护者在飞书审批”，附真实链接。示例人员必须来自本次真实搜索，不能写死 ID。

用户：把已启用的这个分支换成甲 → 乙两级审批，其他保持不变。

执行：先读取旧配置和永久固定的作者优先值，确认接入审批人；清楚展示名单与 OR → AND 的变化，提交替换申请。
旧配置在获批前继续有效，现有 MR 流程保持不变。

### Bad

- 用户要求按标签，但旧页面没有触发控件，仍提交全量审批配置并声称成功。
- 用户只给 MR 审批人，就把名单第一人当成接入审批人并默认开启作者优先。
- 用管理员 GitLab token 或导出的 Cookie 直接调用接口，绕过本人登录和选人校验。
- 看到“已提交”就说“已经上线”；看到终态页面就说“已经通过”。
- 接入前的旧 MR 没有待办，于是重复提交申请；或为了改变作者优先而删除重建配置。
