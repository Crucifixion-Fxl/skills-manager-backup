# tool-exploration

AI 工具探索代理 — 在指定环境中通过「读文档 → 动手测 → 遇阻搜索 → 反思优化」的闭环，系统性掌握工具/系统/SDK 的真实用法，并输出可复用的探索成果。

## Description

当用户指定一个学习目标（工具、SDK、系统、API、框架等）和对应的文档/环境时，本 Skill 驱动 AI 进入自主学习模式：

1. **阅读文档** — 建立初始知识框架
2. **动手实验** — 在真实环境中逐一验证文档描述，发现隐性知识
3. **遇阻自救** — 遇到报错或文档未覆盖的场景时，先 WebSearch 找社区方案，再结合实际环境调整
4. **反思沉淀** — 记录验证结果、文档缺陷、最佳实践和待完善项

最终产出：
- `learning-notes.md` — 结构化学习笔记（验证通过的用法 + 踩坑记录 + 最佳实践）
- `gaps.md` — 文档缺陷与待完善清单
- （可选）直接优化目标 Skill/文档/配置，或将成果转化为新 Skill

适用场景：
- 学习一个新工具/SDK/API 的实际用法
- 验证文档描述与真实行为是否一致
- 发现文档未覆盖的边界情况和隐性知识
- 为后续编写 Skill 或文档积累一手经验

## Rules

### Rule 0 — 安全边界与自主决策

#### 红线

| 禁止 | 原因 |
|------|------|
| 修改/删除生产环境数据 | 学习过程只做只读探索或在隔离环境中实验 |
| 暴露或记录真实凭据到笔记中 | 笔记可能被分享，凭据必须脱敏 |
| 跳过文档直接盲试 | 先读文档再动手，避免低效的随机尝试 |

**核心原则**：学习过程默认只做 GET/读取/查询操作。任何写入操作（POST/PUT/DELETE、文件修改、配置变更）须先告知用户并获得确认。

#### 自主运行模式

当 AI 在独立窗口/`-p` 模式/无人值守环境中运行时，**不得阻塞等待用户回复**。遇到需要决策的节点：

1. 选择最安全、最合理的默认路径继续
2. 将决策记录到笔记中，标注 `[自主决策]` 便于用户事后审阅
3. 遇到需要凭据/权限才能继续的环节 → 先降级为文档学习，将实操标记为「待凭据就绪」

判断方式：如果运行在非交互模式（`-p` 等），自动进入自主模式；交互模式下若 30 秒无回复也进入自主模式。

#### 节奏控制

根据学习目标的复杂度自适应调节节奏：

| 复杂度 | 判断标准 | 节奏策略 |
|--------|---------|---------|
| **轻量**（CLI 工具、单一 SDK） | 功能模块 ≤ 5 个 | 快节奏：跳过框架确认，直接进入实验；每模块 1-2 个实验 |
| **中等**（REST API、中型系统） | 功能模块 6-15 个 | 正常节奏：输出框架后继续推进；每模块 2-3 个实验 |
| **重量级**（平台、多子系统） | 功能模块 > 15 个 | 深度节奏：可分批学习，每批聚焦 3-5 个模块；每模块 3-5 个实验 |

**原则：宁可慢一点学全，不要快但漏掉关键细节。** 小工具可以加速流程，但复杂系统必须逐模块深入。

#### 兔子洞控制

学习过程中容易越挖越深偏离主线。每进入一个新话题前自检：

- **这个话题和当前学习模块直接相关吗？** 不相关 → 记一条「延伸阅读」到笔记末尾，立刻拉回主线
- **已经在同一个子话题上花了超过 3 次实验吗？** → 强制小结当前发现，跳到下一个模块
- **发现了一个有趣但非核心的功能？** → 记录到 gaps.md 的「功能建议」，不当场深入
- **连续 WebSearch 超过 3 次仍无结果？** → 标记为未解决，回到主线，不要死磕

#### 信息冲突仲裁

大部分情况以源码为准，遇到信息冲突时先动手测试再下结论：

```
动手测试结果 > 源码行为 > 官方文档 > 社区博客
```

遇到矛盾不要靠猜 — 写个最小实验跑一下就知道谁对。记录冲突本身就是有价值的发现，在笔记中标注 `[信息冲突]`，列出各方说法、实测结果和最终裁决依据。

#### 笔记语言

跟随用户的语言。用户用中文就中文输出，用英文就英文输出。引用原文术语/命令/代码时保留原文不翻译。

### Rule 1 — Phase 1: 接收学习目标与环境

#### 前置检查

1. **增量学习**：先检查输出目录下是否已有 `learning-notes.md`。如果有 → 读取已有笔记，在此基础上继续学习（补充新模块、更新过时内容），**不要覆盖重写**
2. **版本标注**：在笔记元信息中记录工具版本号（`<tool> --version` / npm 版本 / API 版本），防止笔记过时后误导
3. **从现有代码学习**：如果用户当前项目中已在使用该工具（Grep 搜索 import/require/use），先看项目里的实际用法作为学习锚点，再对照文档查漏补缺

收到用户请求后，明确以下信息。**用户未提供的项不阻塞，自行推断并标注**：

```
【学习任务卡】
- 学习目标：<工具/SDK/系统名称>
- 文档来源：<URL / 本地路径 / 飞书文档 / 无（自行查找）>
- 实验环境：<本地 CLI / staging API / sandbox / Docker / 浏览器 / 无>
- 学习范围：<全面学习 / 聚焦某个功能 / 验证特定问题>
- 输出位置：<用户指定路径 / 默认 ~/Documents/learning-notes/<工具名>/>
```

如果用户没有提供文档：
1. 先 WebSearch 查找官方文档
2. 检查是否有 `--help`、`man`、Swagger 等自带文档
3. 搜索 GitHub README、社区教程

### Rule 2 — Phase 2: 阅读文档，建立知识框架

#### Step 2.1: 通读文档

根据文档类型选择读取方式：
- **本地文件**：直接 Read
- **Web URL**：WebFetch 获取内容
- **飞书文档**：按 `feishu-channel-rules` 使用已批准 profile 执行
  `"$APPROVED_NODE" "$APPROVED_LARK_CLI_ENTRY" --profile <approved-profile> docs +fetch --as user --doc <飞书文档URL>`；失败时不回退到其他应用
- **CLI 工具**：运行 `<tool> --help`、`<tool> help <subcommand>`
- **API 文档**：访问 Swagger/OpenAPI endpoint

**并行探索策略**：当文档分散在多个来源时（官方文档 + GitHub + 社区教程），使用 Agent subagent 并行获取不同来源，主线程负责串联和决策。例如：
- Subagent A → 获取官方 API 文档
- Subagent B → 获取 GitHub 上的 SDK/MCP/n8n 节点源码
- 主线程 → 综合两个来源建立知识框架

#### Step 2.2: 提炼知识框架

通读后输出知识框架，**长度根据复杂度自适应**：

- 轻量工具（≤ 5 模块）：10-20 行，直接列表
- 中等系统（6-15 模块）：20-50 行，分类列表 + 表格
- 重量级平台（> 15 模块）：50-100 行，分层表格 + 模块关系图

```markdown
## 知识框架：<工具名>

### 核心概念
- <概念1>：<一句话解释>
- <概念2>：<一句话解释>

### 功能模块
1. <模块A> — <用途>
2. <模块B> — <用途>

### 待验证问题
- [ ] <文档声称 X，需要实际验证>
- [ ] <文档未提及 Y 场景，需要探索>
- [ ] <概念 Z 的边界条件不清楚>
```

交互模式下可请用户确认框架优先级；**自主模式下直接继续，按 [核心功能 → 常用功能 → 边缘功能] 排序推进**。

### Rule 3 — Phase 3: 动手实验（核心循环）

#### 前置检查：凭据与环境降级

在进入实验前，先检查实验环境是否就绪：

```
凭据/环境检查：
  有凭据 + 有环境 → 全量实验模式（文档验证 + API 实测）
  无凭据 / 无环境 → 降级实验模式：
    1. 先完成全部文档分析（概念理解、API 端点梳理、数据模型分析）
    2. 用 WebSearch 搜索社区的实测经验作为间接验证
    3. 标注每个待验证项为 [需实测]，输出「凭据就绪后的实验清单」
    4. 如果有公开的 sandbox/playground → 尝试使用
```

**不因缺少凭据而停下。降级模式同样有价值 — 文档分析 + 社区经验已能覆盖 60-70% 的学习目标。**

#### Step 3.1: 设计实验

针对当前模块，设计由浅入深的实验（数量按节奏控制）：

```
实验计划：<模块名>
1. [基础] <验证文档中最基本的用法>
2. [进阶] <测试参数组合或高级功能>
3. [边界] <测试异常输入、空值、超大数据等>
4. [集成] <与其他模块的交互>
```

#### Step 3.2: 逐一执行实验

每个实验按以下模式执行：

```
--- 实验 #N: <实验标题> ---
命令/操作: <实际执行的命令或 API 调用>
预期结果: <根据文档预期应该发生什么>
实际结果: <真实输出>
结论: <符合预期 / 与文档不符 / 发现新知识>
```

**关键行为**：
- 每次只执行一个实验，观察完整输出后再进行下一个
- 如果实际结果与文档不符 → 记录为文档缺陷
- 如果发现文档未提及的行为 → 记录为隐性知识
- 如果发现更优的用法 → 记录为最佳实践

#### Step 3.3: 遇到障碍时的自救流程

当实验中遇到报错、异常行为或文档空白时，按以下优先级解决：

```
遇阻自救流水线：

1. 读错误信息 → 理解根因
   ↓ 无法理解
2. 查文档的 FAQ / Troubleshooting 章节
   ↓ 文档没有覆盖
3. WebSearch "<工具名> + 错误信息关键词"
   ↓ 搜索到方案
4. 验证搜索到的方案是否适用当前环境
   ↓ 方案不适用 或 搜索无结果
5. WebSearch 扩大搜索范围（GitHub Issues、Stack Overflow、论坛）
   ↓ 仍无法解决
6. 记录为「未解决问题」，跳过继续下一个实验
   → 最终汇总所有未解决问题交给用户
```

**每次 WebSearch 后必须**：
- 记录搜索关键词和找到的方案来源
- 在实际环境中验证方案是否有效
- 如果方案有效 → 记录为"社区方案（已验证）"
- 如果方案无效 → 记录为"社区方案（不适用），原因：XXX"

### Rule 4 — Phase 4: 反思与优化

每完成一个模块的实验后，进行反思：

#### Step 4.1: 模块小结

```markdown
### 模块小结：<模块名>

**已验证用法** (N 项)
- <用法1>：<验证结论>

**文档缺陷** (N 项)
- <缺陷1>：文档说 X，实际是 Y

**隐性知识** (N 项)
- <知识1>：文档未提及，但实际使用中发现 ...

**最佳实践** (N 项)
- <实践1>：比文档推荐的方式更好，因为 ...

**未解决问题** (N 项)
- <问题1>：<现象 + 已尝试的方案>
```

#### Step 4.2: 优化已学内容

基于实验结果，尝试优化：
- 发现更简洁的命令组合 → 替换原有步骤
- 发现参数默认值与文档不符 → 标注实际默认值
- 发现性能差异大的写法 → 标注推荐写法
- 发现常见陷阱 → 提炼为"避坑指南"

### Rule 5 — Phase 5: 输出与持久化

**即时写入，边学边存。** 不要等全部模块学完才写文件 — 每完成一个模块就立即追加到笔记中。

#### 即时写入策略

```
时机                          动作
─────────────────────────────────────────────────
Phase 2 知识框架输出后        → 创建 learning-notes.md，写入框架和元信息
每完成一个模块的实验          → 追加该模块的小结到 learning-notes.md
每发现一个文档缺陷            → 追加到 gaps.md
全部模块完成后                → 补充「最佳实践」「避坑指南」「未解决问题」等总结章节
```

**为什么即时写入**：
- 防止上下文过长导致早期实验细节丢失
- 中途中断（超时/用户取消）也能保留已完成的成果
- 用户可以实时查看进度（打开文件即可看到最新内容）

#### 输出位置

默认路径：`~/Documents/learning-notes/<工具名>/`（用户指定时用用户路径）

```
~/Documents/learning-notes/<工具名>/
├── learning-notes.md      # 结构化学习笔记
└── gaps.md                # 文档缺陷与待完善清单
```

#### 产出物 3: 成果转化（完成后主动询问）

学习完成后，主动向用户提供后续选项：

1. **转化为 Skill** → 联动 `tool-skill-creator`，基于学习笔记直接生成 SKILL.md
2. **优化现有 Skill** → 如果学习目标对应已有 Skill，直接修正错误、补充遗漏
3. **保存到 memory** → 将关键隐性知识（文档查不到的）写入 auto-memory 供未来对话使用
4. **仅保存笔记** → 不做额外转化，笔记本身就是成果

自主模式下默认选择「仅保存笔记」，不自动执行转化操作。

### Rule 6 — 大型工程/文档的应对策略

当学习目标触发以下任一条件时，启用大型工程策略（详见 [references/large-project-strategies.md](references/large-project-strategies.md)）：

| 信号 | 判定 | 对应策略 |
|------|------|---------|
| 单文件 > 2000 行 | 大文件 | 策略 2：分段消化 |
| 目录树 > 100 文件 | 大工程 | 策略 1：目录先行 + 策略 4：采样法 |
| API 端点 > 50 个 | 大 API 面 | 策略 3：分批探索 |
| 文档 > 20 页 | 海量文档 | 策略 5：目录优先 |
| 子系统 > 5 个、GB 级代码 | 超大项目 | 策略 6：多 subagent 并行（最多 5 个） |
| 功能依赖 UI 交互 | Web 系统 | 策略 7：agent-browser 黑盒探索 |

**核心原则：先广后深，先骨架后血肉。永远先建立全局地图，再按优先级逐区域深入。**

### Rule 7 — 持续学习模式（可选）

如果用户希望 AI 持续深入学习，可以进入迭代模式：

```
循环：
  1. 检查 gaps.md 中的未解决项
  2. 针对未解决项设计新实验
  3. 执行实验 → 更新 learning-notes.md
  4. WebSearch 最新社区动态（版本更新、新特性、已知 bug）
  5. 将新发现追加到笔记中
  6. 询问用户是否继续或结束
```

### Rule 8 — 多工具联合学习

当学习目标涉及多个工具的协作（如 ArgoCD + Helm + K8s），按以下策略：

1. 先单独学习每个工具的基础用法
2. 然后设计跨工具的集成实验
3. 重点记录工具间的数据流和依赖关系
4. 在笔记中用流程图描述工具协作链路

## Examples

### Bad

```
用户："学习一下 cmux 的用法"
AI：直接凭记忆回答 cmux 的功能 → 很多参数和行为是猜的 → 用户照做后报错
```

```
用户："帮我搞清楚这个 API 怎么用"
AI：读了文档后直接输出总结 → 没有实际调用验证 → 文档过时，参数已变更，用户踩坑
```

```
用户："学习 Terraform"
AI：在用户的生产环境执行 terraform apply → 创建了不需要的资源 → 产生费用
```

```
用户（独立窗口）："学习飞书项目 API"
AI：输出知识框架后问"你有插件凭证吗？" → 没人回复 → 一直等 → 浪费时间什么都没输出
```

```
用户："学习这个 monorepo 的架构"
AI：cat 每个文件 → 上下文爆炸 → 后面的文件全部截断 → 学了个寂寞
```

### Good

