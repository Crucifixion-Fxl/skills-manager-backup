# 大型工程/文档的应对策略

> 被 SKILL.md Rule 6 引用。当学习目标触发大型工程判断标准时，查阅本文件获取详细策略。

## 判断标准

| 信号 | 判定 |
|------|------|
| 单文件 > 2000 行 | 大文件，需分段读取 |
| 目录树 > 100 个文件 | 大工程，需采样探索 |
| API 端点 > 50 个 | 大 API 面，需分批学习 |
| 文档页数 > 20 页 | 海量文档，需目录优先 |

## 策略 1：目录先行，按需深入

```
第一层：目录级扫描（Glob + ls）
  → 理解整体结构、识别核心模块 vs 辅助模块
  → 输出目录地图（每个目录一句话说明用途）

第二层：入口文件精读
  → README.md、index.ts/main.go/app.py 等入口
  → package.json / Cargo.toml / go.mod 了解依赖
  → 配置文件（.env.example、config/）了解可配置项

第三层：按优先级深入具体模块
  → 核心模块全读，辅助模块只读接口/导出
```

## 策略 2：大文件分段消化

对于单个大文件（> 2000 行）：

1. **先读头尾**：`Read(offset=0, limit=100)` 看文件头 + `Read(offset=末尾-50, limit=50)` 看结尾
2. **用 Grep 定位关键段落**：搜索 `export`、`class`、`def`、`##` 等结构标记，建立段落索引
3. **按段精读**：只读与当前学习模块相关的段落，跳过无关代码
4. **不要一次性读完整个文件** — 分 3-5 次读取，每次聚焦一个主题

## 策略 3：大 API 面分批探索

API 端点 > 50 个时：

1. **先获取全量端点列表**（Swagger / `--help` / 目录扫描），只记录路径和方法，不读细节
2. **按领域分组**：用户管理、数据操作、配置管理、监控...
3. **每批学习一个领域**（5-10 个端点），学完输出该领域的小结
4. **用 subagent 并行探索不同领域** — 主线程分配任务，subagent 各自深入一个领域后汇报

## 策略 4：大型 monorepo 采样法

面对 monorepo（多包/多服务）：

1. **识别包清单**：读 `package.json` workspaces / `Cargo.toml` members / `go.work`
2. **按依赖关系排序**：先学被其他包依赖最多的核心包
3. **每个包只看**：README + 导出接口（`index.ts` / `lib.rs` / `__init__.py`）+ 测试文件（看用法示例）
4. **跳过**：`node_modules/`、`vendor/`、`dist/`、`build/`、生成代码、lock 文件

## 策略 5：海量文档目录优先

文档 > 20 页时：

1. **先读目录/大纲** — 很多文档站有 sidebar / TOC，优先获取
2. **标记必读 vs 可跳过** — 入门指南、核心概念、API 参考必读；changelog、迁移指南、贡献指南可跳过
3. **用 WebFetch 只抓必读页面**，不要盲目抓全站

## 策略 6：超大项目多 subagent 并行扫描

面对超大型项目（如嵌入式固件源码、内核级代码库、数 GB 级 monorepo），单线程探索效率极低。启用多 subagent 并行模式（**最多 5 个同时运行**）：

```
Phase A — 主线程：10 分钟内完成全局骨架
  1. Glob 扫描顶层目录结构（maxdepth=2）
  2. 读构建系统入口（Makefile / CMakeLists.txt / build.gradle / meson.build）
  3. 读项目 README + ARCHITECTURE.md（如有）
  4. 识别子系统/模块边界，划分为 N 个探索区域（N ≤ 5）
  5. 输出「全局骨架地图」— 每个子系统一句话 + 预估重要度

Phase B — 分发 subagent 并行深入（最多 5 个同时）
  主线程为每个 subagent 分配明确任务：

  Agent 1 → 子系统 A：读入口文件 + 核心数据结构 + 对外接口
  Agent 2 → 子系统 B：读入口文件 + 核心数据结构 + 对外接口
  Agent 3 → 子系统 C：...
  Agent 4 → 构建系统 + 配置体系：编译选项、宏定义、条件编译
  Agent 5 → 测试 + 文档：测试覆盖情况、已有文档质量

  每个 subagent 的 prompt 必须包含：
  - 全局骨架地图（让 subagent 知道自己在整体中的位置）
  - 明确的探索范围（目录路径）
  - 期望输出格式（模块小结模板）
  - 禁止读取的目录（其他 subagent 负责的区域）

Phase C — 主线程汇总
  1. 收集所有 subagent 的模块小结
  2. 串联子系统间的调用关系和数据流
  3. 识别跨子系统的共享组件和公共抽象
  4. 输出完整的架构笔记
```

**关键约束**：
- subagent 数量上限 **5 个** — 超过 5 个并行反而降低效率（上下文竞争 + 汇总负担）
- 每个 subagent **只探索分配给它的目录**，不要越界 — 避免重复读取
- subagent 用 **Sonnet**（`model: "sonnet"`）— 探索性任务不需要 Opus，节省资源
- 如果项目实在太大（> 10 个子系统），分两轮：第一轮 5 个高优先级子系统，第二轮剩余

## 策略 7：UI 交互型系统 — agent-browser 黑盒探索

当学习目标涉及 Web UI 交互（管理后台、SaaS 平台、可视化编辑器等），纯文件/API 无法摸清实际用法时，使用 agent-browser 进行黑盒测试：

```
适用场景判断：
  - 功能必须通过页面操作才能触发（拖拽、弹窗、多步表单）
  - API 文档缺失但 UI 可用
  - 需要理解 UI 交互流程和状态变化
  - 需要截图记录操作步骤供笔记使用
```

**探索流程**：

1. **安装 agent-browser**（如未安装）：
   ```bash
   npx skills add vercel-labs/agent-browser --skill agent-browser --agent claude-code -y
   ```

2. **登录目标系统**：
   - `agent-browser open <URL>` → `agent-browser snapshot -i` 获取页面元素
   - 如需登录 → 引导用户手动完成（AI 不代输密码），或用已有 cookie/token
   - 登录后 `agent-browser snapshot -i` 确认进入主界面

3. **系统性遍历 UI**：
   ```
   Step 1: 导航结构扫描
     → snapshot 获取侧边栏/顶部导航的所有菜单项
     → 识别 UI 框架（Ant Design .ant- / Element .el- / Arco .arco-）
     → 输出菜单树（页面地图）

   Step 2: 逐页面黑盒测试
     → 点击每个菜单项 → snapshot 记录页面布局
     → 识别页面上的可操作元素（按钮、表单、筛选器）
     → 用 Network 拦截观察每个操作触发了什么 API 调用
     → 记录：页面名 → 功能 → 触发的 API → 参数

   Step 3: 关键流程走通
     → 对核心业务流程（如：创建 → 编辑 → 发布）做端到端操作
     → 记录每一步的 UI 状态变化和后端 API 调用
     → 发现隐藏功能（右键菜单、快捷键、拖拽排序等）
   ```

4. **记录方式**：
   - 每个页面：`agent-browser snapshot -i` 获取结构化元素列表
   - 关键操作：记录操作步骤 + 对应 API（从 Network 拦截获取）
   - 输出到笔记时标注 `[UI 黑盒]`，与 API 实测区分

**安全约束**：
- **只做只读操作**（浏览、查看、搜索）— 不要点"删除""提交""发布"等不可逆按钮
- 如需测试写入操作 → 先截图确认按钮文案，询问用户是否允许
- 自主模式下 **完全跳过写入操作**，只记录"该按钮预期功能是 XX，未实测"
