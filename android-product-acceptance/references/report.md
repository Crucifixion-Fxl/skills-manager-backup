# 报告与复测格式

建议每次使用独立目录 `outputs/acceptance/<run-id>/`，不要覆盖旧包证据。

## run.json 最小字段

run_id、主机与设备时间、设备型号/OS/serial、APK 名称/hash/实际包名/版本、PRD 链接与读取时间、设计节点或缺口、账号标识（不含密码）、User ID 验证来源、执行状态、恢复位置、审批状态、前次 run/Issue 引用。

## 报告

1. 结论与覆盖范围：当前设备/Build/账号的证据，以及无法验证范围。
2. 用例表：ID、PRD 对应 AC、前置、步骤、预期、实际、功能状态、视觉状态、截图/运行数据依据。
3. 视觉对照表：页面/状态、模块、设计节点/局部图、实机图、对齐与居中、间距/留白、图片比例/裁切、文字与控件、视觉结论。不可仅附一张设计总览就声称完成视觉验收。
4. 问题草稿：ID、建议优先级、复现前置与步骤、预期/实际、业务影响、截图、证据范围、修复后的复测条件。根因未经证实不要猜。
5. 暂无法验证项：缺什么、最小补充条件、恢复位置。无事件数据不能写“0”或“未上报”。
6. 需人工决策：只列最终文案、规则等不能由 PRD 决定的项，以及具体 Issue 提交范围。

证据页用原始图片加 HTML/CSS 注释框，不篡改截图；相对路径可用于同目录 HTML，给用户的本地 Markdown 链接使用绝对路径。标注框按原始图坐标或比例定位。

## 复测对比

保留 issue_id、old_run、new_run、旧/新包版本与 hash、前置状态是否一致、新实际结果、证据和结论。缺少前置条件不能把复测判通过。成功修复的问题和未覆盖回归项分开列出。

## 已验证的流程实例（方法参考，不是当前运行证据）

Guest 支付 MVP 曾在 Pixel 6 上完成指定 APK 覆盖安装、退出后重新登录、核对邮箱、Me 入口、Paywall、Free Try、Coming soon、OK 返回 Me，并读到共享者昵称。PRD 要求单一家庭年付而 UI 出现个人套餐，因此可判套餐展示不符；弹窗声明无购买不能证明支付 API 未调用。该例展示如何区分明确缺陷和证据不足，不应把其账号、商品和规则套用到其他需求。

## 视觉问题证据要求

设计局部与实机局部并排展示，标明坐标/裁切范围和对应节点。每条问题说明预期对齐、实际偏移或异常留白、影响及复测条件。对于 Birds around you 等图例卡片，分别检查卡片容器和可见鸟类主体的居中、主体占比及上下左右留白；素材透明边缘不能仅靠 UI 控件边界判断。未量化时采用准确的定性描述，不编造像素值。

视觉未验、设计不清晰或状态不匹配时写“暂无法验证”及补充条件；功能通过不能覆盖视觉缺口。

### 图标与按钮逐元素表（必填）

| 页面/状态 | 元素及设计节点 | 图形/实心描边 | 画布与可见尺寸/归一化依据 | 前景/背景/边框颜色：设计 → 实测 | 对齐/间距 | 结论及原图位置 |
|---|---|---|---|---|---|---|

并列入口分别一行，同类 More、按钮不能抽一个代替全部。颜色注明来自设计属性/SVG还是截图采样；未测尺寸不能补猜测值。明确区分“功能通过”和“视觉通过”。

交付前将页面/状态元素清单与本表逐行核对，分别列出前景、背景、文字、边框适用项；报告填写“应查 N 项、已查 N 项、暂无法验证 N 项（列名与原因）”。数量来自真实清单，不凭截图数或点击次数推算。未填、缺证据及未进入状态不能默认为通过；整体颜色通过要求适用项完整且均通过。系统状态栏表另按界面/状态统计覆盖，不混入元素数量。

### 系统状态栏逐界面检查表（独立必填）

| 界面/账号状态 | 进入/返回/滚动/弹窗等已验状态 | 实际背景及明暗图标模式 | 时间文字 | 信号/Wi-Fi | 电量/通知 | 遮挡/模式残留 | 结论与顶部截图 |
|---|---|---|---|---|---|---|---|

本次范围内每个界面必须有一行，状态不同时拆行；无设计也检查可读性。不可见或背景冲突单独列缺陷，不能由其他视觉项通过抵消。全屏隐藏仅在预期如此时标不适用；缺证据填暂无法验证，不默认通过。用户报告但尚未复现的情况保留用户反馈来源和待复现状态。

## 多账号覆盖表

按账号状态列出独立账号标识、真实/虚拟设备及型号、权益与共享基线、已核验身份、登录/冷启动/状态变更路径、设计节点、功能结论、视觉结论与证据目录。无设备与有设备不能合并为同一行“已验收”；缺少账号状态必须显式列出，不遗漏。虚拟设备媒体能力与实体设备结果分开。
