# Android 产品走查

## Description

把“接收资料 → 建立验收标准 → 安装登录 → 走查取证 → 对照需求 → 问题报告 → 人工确认 → 提 Issue → 新包复测”作为可恢复工作流执行。用户提供输入后，直接推进已授权的可执行步骤，不把任务停在方案阶段。默认用已连接真机；只有用户同意替代时才改用模拟器或云平台，并明确证据来自何种设备。

## Rules

以下规则适用于资料读取、真机操作、账号状态、视觉验收、报告与复测各阶段。

## 输入与恢复

接收 PRD 链接、设计链接（可在 PRD 内）、APK 本地路径或下载地址、测试账号、目标环境。可选：设备序列号、User ID、具体验收范围、造数能力、Issue 项目和负责人、上轮报告。先检查会话与已有 run.json / 报告，复用已确认输入，避免重复询问。

缺少某项时继续不依赖它的工作：没有 Figma 可以先验功能；没有设备可以先拆用例；没有 Issue 目标可以先写草稿。登录验证码、USB 授权、解锁等确需用户操作的阻塞，应说明具体动作并保存恢复位置。

密码只在当前登录操作中使用，不写进 Skill、任务卡、脚本源码、命令日志、截图说明或报告。可使用当前会话提供的凭据或受控凭据机制；脚本不要将秘密作为命令行参数。User ID 来自输入时标注“用户提供”，查询确认后才标注已验证。

## 1. 读取依据并建立用例

- **所有飞书文档操作以 `feishu-auth` Skill 为入口，不使用飞书 MCP。** 读取该 Skill，使用当前支持的认证与 CLI 路径；不复制历史 Token。若与此用户明确指定路由不一致，遵循用户指令，在当前允许工具中完成操作。
- 读回 PRD 实际标题、正文、链接和图块。以当前指定 PRD 为范围；旧聊天中的产品或设计不能自动替代。检查“设计稿”是否指回 PRD 自身；取不到设计节点就记录缺口，不声称已读取 Figma。
- 有有效 Figma 时按当前 Figma Skill/工具规范读取节点和截图；鉴权失败核对实际身份，不能把浏览器登录账号当成 MCP 身份。没有节点时，PRD 图片只作有限视觉参考。
- 从验收标准拆出正向、反向、边界与账号前置条件。每个用例记录依据、前置、步骤、预期、证据需求；预期与观察分栏。PRD 未冻结的价格、昵称 fallback、历史插图文案或成功线列为待确认，不自行创造判定规则。
- 用例范围由当前需求决定，GuestPay 的套餐、共享条件等仅是历史实例，不能硬编码为通用验收标准。

## 2. 核验安装包与真机

执行前读 [Android 操作与证据规则](references/android.md)。查 APK 实际包名、入口 Activity、versionName、versionCode 和 SHA-256，不能根据文件名猜包名。用 `adb devices -l` 识别可用设备；多台且无明确目标时让用户选择，所有命令指定 `-s`。

保存主机时间、设备时间、型号、Android 版本、APK 信息与安装前版本。按授权使用 `install -r` 安装指定包，安装后读回版本。签名冲突、降级限制时保留数据，不自动卸载或 clear；记录所需处理。运行失败不报告为安装通过。

捕获系统/权限/Debug 提示，按当前任务需要处理。兼容性警告记录准确文本与影响，不推断其他 OS 或正式包必然有问题。截图若出现明显时间偏差，记录两端时间，为后续埋点归属保留依据。

## 3. 登录并验证账号状态

启动已核实 Activity，读取当前 UI 后再操作。若已登录指定账号，只验证登录态可复用；若任务要求完整登录闭环，或已有会话身份不符，通过 UI 退出并用指定账号登录。不要仅因进入首页就判定账号正确；在账户页核对邮箱或可验证标识。不要为登录测试重置密码或删除账号。

核验需求用到的状态：自有/共享设备、Admin 来源、订阅/家庭权益等。UI 可证明可见状态，权威后台查询可补充权益；不能因入口出现就反推全部准入条件成立。需要 QA 查询或造数时再读 `qatools` 等实际相关 Skill。仅凭走查授权不修改现存权益/共享关系；用户授权构造状态后记录原状态、变更与恢复方式。未覆盖的账号组合保留“暂无法验证”。

### 多账号状态矩阵（有条件分支时必做）

需求或设计涉及不同账号状态时，先建立“状态 → 独立测试账号 → 后台基线 → 预期页面/设计节点 → 用例 → 登录及截图证据”矩阵，并分别登录查验。至少覆盖本需求实际涉及的分支，例如无设备/有设备、单设备/多设备、自有/共享、免费/会员；不把所有示例机械扩成无关测试。

优先保留独立账号，不在同一账号上反复造数污染基线。已有用户授权创建测试状态时直接使用 QA 工具完成；权限或造数能力不足时明确对应分支“暂无法验证”，继续其他分支，不以单账号完成宣称整体验收完成。需要虚拟喂鸟器时核验型号与 bird 能力，不能用任意安防摄像头替代；只需设备状态时不要顺带创建 VIP、支付订阅或共享关系。

每次切换账号：正常退出 → 登录目标账号 → Account 核对身份 → 后台/设备列表确认状态 → 首次进入与冷启动分别验证 → 功能和设计布局对照。记录地区选择、WebView、页面滚动或其他本地缓存是否继承；新账号不代表全新安装，不能把缓存状态当成后台账号数据。

对于添加设备前后状态，还需区分“已有设备账号登录”与“原无设备账号完成绑定后即时刷新”；只有前者证据不能证明后者。虚拟设备可验证设备卡片、入口、排列和状态分支；没有实际媒体源时，直播连接/画面/回放标记暂无法验证，不把 Mock 绑定成功当成真机直播通过。不同账号的证据单独存放，报告按矩阵展示覆盖和缺口。

## 4. 逐项走查与取证

用“读取 UI / 截图 → 选择目标 → 操作 → 等待预期状态 → 再读取”的循环执行，不以固定坐标串或固定 sleep 宣称自动化稳定。优先当前 resource-id、content-desc 和边界；截图推断坐标时换算实际分辨率。遇到 loading、弹窗、网络异常先辨别，不立即判需求失败。相同无效动作至多重试两次，再记录阻塞与恢复点。

对每项需求检查内容、布局、交互、错误/空态和返回路径，按已有前置状态覆盖。保留原始截图与脱敏 UI 文本，命名包含运行及步骤；标注用 HTML 叠加框，原图不改动。截图可能包含账号等测试数据，提交外部前检查范围，密码/Token 屏幕不截图。辅助脚本会拒绝密码控件截图，但不能代替目视检查。

### 布局与设计稿对比（独立验收，不得省略）

功能可点击、内容数量正确，只能支持功能结论。**有可用设计稿时，必须逐页面、逐模块完成视觉对比，不能只看 Figma 概览后继续操作，也不能用 UI 树替代图片观察。** 先建立“页面/状态 → 设计 Frame/节点 → 实机截图”的对应关系，再分别记录功能与视觉结果。

- **读取足够清晰的设计**：对当前模块读取局部节点或高分辨率设计图。概览缩放后看不清对齐、边距时，继续获取局部清晰图；不要据此跳过检查。无法取得清晰设计时，标记具体模块“视觉暂无法验证”。
- **按同一状态比较**：尽量匹配账号、语言、文字长度、滚动位置及数据类型。记录实机分辨率/显示缩放与设计画板尺寸，以内容区域或同宽模块等比例对照；区分状态栏、安全区、Android 与 iOS 系统控件差异，不直接拿截图像素与设计单位相减。
- **逐模块检查**：整体布局及模块顺序；左右/上下居中、对齐基线；容器内边距、模块间距及留白；卡片宽高和间隔；图片可见主体的大小、位置、宽高比、缩放与裁切；文字字号、行高、换行/截断及图文距离；按钮尺寸、颜色、圆角、遮挡；横向列表首尾留白与露出下一卡的比例。
- **图标逐元素检查**：核对实际图形/资源、实心或描边、线宽、方向、画布尺寸与可见图形尺寸、对齐及文字间距，再分别核对前景色、圆形底色和透明度。More 等尾随图标不能因都是“向右”就判一致，实心三角与折线箭头须区分。照片/声音等并列入口逐个对照设计，再横向比较；设计规定同色时必须检查是否一致，不因功能正常而跳过。尺寸以同宽模块归一化，不能把 UI 点击区域当作图标可见尺寸。
- **按钮逐层检查**：分别检查容器填充、边框、文字、图标及图标底色的设计值与实测表现；“都是绿色”不构成通过。覆盖本次流程实际出现的默认、选中、禁用、按下/加载状态，未进入的状态明确未验证。可取得设计属性或 SVG 时保存颜色值；截图取色注明原图位置，避开抗锯齿边缘，不将截图色值直接宣称为代码 Token。
- **每个界面独立检查系统状态栏（信号条）可读性**：时间、信号、Wi-Fi、电量及通知图标与其背后实际背景逐项核对，文字/图标不能因同色、低对比、透明叠加或遮挡而不可见。没有设计稿也必须检查可读性，不能并入“整体布局正常”。为本次每个界面及实际经历的状态独立记录结果和顶部原图证据；包含进入、返回、滚动后，以及实际出现的弹窗、WebView、图片/视频沉浸态。检查页面切换是否遗留上一页的明暗图标模式；全屏按预期隐藏时写“不适用（全屏隐藏）”，同色导致看不见不能写不适用。未到达的界面写暂无法验证，不能用首页通过代表所有界面。
- **图片主体与留白必须单独看**：Image 控件居中不代表鸟类图例的可见主体居中。检查透明画布/素材自身留白，以及主体在卡片中的视觉中心、占比、四周空间。随机鸟种不必与设计为同一只鸟，但必须符合相同的图例布局规则；不能将偏移、异常空白或裁切一概归为素材不同。没有实际测量时，不猜根因或编造像素差。
- **记录对照证据**：每项视觉问题提供设计局部与实机局部并排对照，标明节点、页面状态、原图位置，用 HTML 叠加框/参考线标出偏差，并描述“预期/实际/影响”。保留原图，不能通过拉伸或裁切隐藏实际留白。未规定容差时不自设统一像素阈值；明显布局不符可记录为问题，细微差异注明测量和依据不足。
- **交付前检查覆盖**：每个有设计的已走查模块都要有视觉检查结果；功能通过而视觉未验的模块，整体不能写“通过”。尤其检查图片卡片等容易因内容已加载而被漏检的区域。
- **颜色验收交付门槛**：开始对比前列出本次页面/状态中的全部图标、按钮和其他有设计颜色的元素清单，为每个元素分列前景、背景、文字、边框及适用状态。交付前以清单逐行核对报告：每一适用项必须有“设计值/依据 → 实测值/观察 → 原图位置 → 结论”；不得合并为“整体颜色正常”，不得静默漏行。没有设计值、未采样或状态未进入时准确注明缺口；不可直接取色的图片/渐变以设计依据与局部图对比，不编造单一色值。存在缺行或证据缺口时，颜色验收不能写通过，应先补查可执行项，其余标暂无法验证。单列状态栏逐界面表执行同样的覆盖核对。最终报告列明已查数量、未查数量和未查项，而非仅声明“已仔细检查”。
- **用户指出漏检后回扫同类元素**：一个图标颜色或 More 箭头被指出后，检查本次范围内其余并列入口、同类尾随图标和按钮；更新逐元素表及原结论，不能只补被点名的一个位置。系统状态栏单列逐界面覆盖表，不以复测旧问题替代视觉全项检查。

支付类需求分开记录 UI、配置、当前 APK、运行调用和真实事件证据。Coming soon / No purchase was created 文案、没有收银台或 API 200 都不能单独证明“未发起支付”。假门需求可按授权点击试用；一旦出现真实支付流程即停止深入操作并取证，不能完成购买或订阅。

对明显失败收集最小复现与必要的有界复测；不要为了增加次数重复制造试用事件。日志只提取相关脱敏字段，避免将完整 logcat、应用数据目录或会话 Token 写入报告。

## 5. 输出待确认报告

按 [报告与复测格式](references/report.md) 输出到本次工作区独立运行目录：run.json、验收报告、原始截图和可视化证据页。脚本 [android_evidence.py](scripts/android_evidence.py) 可检查设备并采集脱敏 UI/截图，不会安装、点击、登录、造数或提交 Issue。

结果分为“通过 / 不通过 / 暂无法验证 / 不适用”，给出原因与证据层级。一个 UI 闭环完成不等于整个需求通过，更不等于无人值守稳定运行。最终说明已完成、确定问题、缺口、下一步；打开可审阅证据页。

**外部提交边界：默认在这里等待用户确认具体问题报告。** 不提前发开发消息、建 Issue 或修改外部需求文档；若本会话已明确批准具体提交范围则不用重复确认。生成本地报告不需要审批。

## 6. 已获确认后的提交与复测

确认后使用对应 Issue Skill，核对项目与负责人，先搜索去重再创建/补充，提交复现、预期/实际、Build 和截图，读回 Issue 编号、状态和负责人。消息发送须有明确授权；批准建 Issue 不自动授权群发通知。

新包到达后建立新 run，保留旧证据，核对新 hash/版本与账号前置，先复测已确认问题，再回归受影响主路径。关闭问题需当前新包证据和适用授权，不能根据“开发已修复”直接判通过。无需自行创建定时任务；只有用户要求持续调度时再接入自动化，沿用报告审批边界。


## Examples

### Good Example

用户提供 PRD、APK 并授权创建测试账号。按需求分别准备无设备和有设备账号，核对登录身份与后台状态，读取对应 Figma 节点，对照首屏及冷启动截图，记录图例居中和留白差异。报告确认后再提交 Issue，新包到达后分别复测。

### Bad Example

仅用一个账号看到页面可点击便宣布验收通过；忽略有设备分支和设计布局，把虚拟设备绑定成功当作直播通过，或未等产品确认就把问题发送给开发。
