01

定位与范围

用 .thesis 写一句话论点，用 .boundary-grid 做「范围内 / 范围外 / 待定」三分类，不要把这些结论淹没在段落里。

这份示例的唯一目的是证明 design-doc-style 的三份参考文件（tokens / diagram-language / mockup-components）拼在一起能跑，而不是描述某个真实系统。
范围内

视觉语言的四类组件：hero、决策表格、可交互 plate 图、UX mock 片段。

范围外

把整份文档做成独立的可探索图应用（那是 Archify 要解决的问题，不是这个 Skill 的目标）。

待定

是否需要给 plate 图加导出成图片的能力——目前没有需求，先不做。

提醒。这是示例文档；StepRef 是行内术语，不应被提示框排成独立色块。
背景说明。这一段故意保留较长的中文正文与行内 Scenario 术语，用于检查蓝色提示框是否仍保持深色实底、浅色正文和连续排版。
02

流程图（可交互）

节点数不多，但刻意演示"点节点展开细节"和"选中路径高亮追踪"这两个可选交互——不用 JS 时，下面每个细节块依然能独立点开。

接入 ingest

接收外部内容，做最基础的大小与格式过滤。这里只是示例文案，真实文档要写清楚输入来源、协议和限流规则。

校验 validate

依次检查格式、权限、配额；任一项不通过就走下面的失败分支。示例文案：真实文档要列出具体校验项和各自的失败错误码。

发布 publish

校验通过后对外可见。示例文案：真实文档要写清楚发布是否可回滚、生效延迟是多少。

失败 failed

等待人工处理后可重新提交回「接入」。示例文案：真实文档要写清楚谁负责处理、处理时限是多少。

03

决策记录

用 .doc-chip 标证据状态（已验证 / 待验证 / 未决），不要把这类元信息藏进表格正文里。

项状态说明
D1 · 校验失败是否允许跳过已定 · 不允许失败必须走人工分支，不设自动跳过（示例决策）。
D2 · 发布是否需要审批待定示例占位：真实文档这里要写清楚谁在等这个决策、卡在哪。
G1 · 大文件接入的限流值待验证示例占位：真实文档要写明验证方法和验证人。
