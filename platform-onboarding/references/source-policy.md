# 来源、版本与维护范围

## 开源或公开 API 平台

实例 owner 保存环境地址、部署版本探测方法、认证方法、Token 的申请/消费/撤销、subject 与资源权限探针，以及官方 Skill/CLI/API reference 的直接入口。业务调用查询部署版本对应的官方文档，不在 AddX 复制完整公开 API。AI 的已知知识用于定位资料，不能作为当前部署兼容性或写入授权证据。

优先顺序：可核验的厂商官方 Skill → 官方 CLI/API → 已有 AddX 业务契约 → 真实缺口的 OpenCLI adapter。部署定制、私有扩展、官方 API 缺失或平台 UI 独有能力单独记录。官方文档更新不会自动证明实例已经升级；获取不到部署版本时标记未知，并先做无副作用能力探测。

## 自建平台

内部 API 不公开，owner 必须提供发现入口和可操作契约：

| 内容 | 应保存的证据 |
|---|---|
| 源码 | repo 地址、服务/前端目录、路由/handler/OpenAPI 入口、研究 commit |
| 部署 | 环境和服务地址、部署 SHA 或镜像版本、与研究源码的一致性状态 |
| 认证 | Casdoor/飞书/Micro App 到目标平台的转换、Session 或平台 Token、identity/权限探针 |
| 操作 | 方法、路径、参数/body、角色/资源范围、错误、分页/导出、写入副作用 |
| 业务 | 状态机、审批/发布/生产门禁、回读/对账、回滚或清理办法 |
| 接入 | 原生 API 的调用方法、OpenCLI 覆盖缺口、owner Skill 使用入口 |

优先链接仓库内已有 OpenAPI/业务契约，不复制重复版本；没有规范时生成带源码 commit 和扫描入口的 reference。查全路由后对照前端菜单、角色和工作流，避免将底层端点数量等同于功能覆盖。源码不存在、角色不可访问、部署不一致时明确标记待验证。

## 更新与验收

认证、部署版本、源码接口/业务规则或 DOM 变化以及可复现失败触发有范围的刷新，不要求日常用户重新扫描全站。先定位 owner 和 reference，再核对受影响的契约。

默认用本地模拟服务、隔离数据库/测试资源覆盖 CRUD、权限拒绝、状态转换、结果回读、清理及结果未知；线上尽量只读。不为了展示覆盖率在生产创建或修改记录。真实线上写入必须在本次任务授权范围内并满足 owner 门禁。

分别记录 source-verified、fixture-verified、runtime-verified；每份证据包含候选版本、依赖/配置、环境、数据范围、执行时间、退出码和未验收能力。本地测试不升级为线上验收。写入返回未知时先回读/对账，不自动重放。
