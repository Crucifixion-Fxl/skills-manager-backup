# shopify-figma-component-delivery

## Description

本 Skill 编排已有的 Figma 读取、Shopify Theme 开发和浏览器验收能力，按“PRD 审批 -> 技术设计审批 -> 开发与运营配置说明 -> Draft 验证 -> 视觉差异决策 -> 最终验收 -> 代码提交授权”推进单个组件。

它不是新的 T1/T2/T3 工具接入 Skill，不复制 Figma MCP、Liquid、Shopify CLI 或浏览器工具文档。它只沉淀跨工具交付规则、人工审批门禁、证据格式和禁止越级的状态机。

默认结果是待用户审核的文档或未提交代码。除非用户逐项明确授权，否则不得写入 Draft theme、commit、push、创建 MR 或发布 Live theme。

## Rules

### Rule 1 - 输入、设计读取与事实优先级

初始最低输入：

| 输入 | 要求 |
|---|---|
| Figma 桌面端链接 | 必须是带 node-id 的组件或 Frame 链接 |
| Figma 移动端链接 | 必须是带 node-id 的组件或 Frame 链接 |
| 用户的需求理解 | 保留原意，拆成目标、行为、内容和约束 |
| 页面位置 | 已知时提供；未知可在 PRD 标记待确认 |

技术设计前必须补齐目标仓库、页面/模板位置、现有主题约束和拟使用的 Draft theme。信息不足但不影响产品讨论时，可以先写“待确认”的 PRD；不得把推测写成已确认需求。

读取 Figma 时必须：

1. 先加载 `figma:figma-design-to-code`。
2. 对桌面端和移动端目标节点分别调用 `get_design_context`，不得用截图代替设计上下文。
3. `get_metadata` 和 `get_screenshot` 仅用于定位、尺寸记录和视觉证据。
4. 记录文件、node-id、Frame 尺寸、读取时间、节点用途和证据截图。
5. 设计链接无 node-id、权限不足或节点过大超时时停止，要求有效节点链接或更小节点；不得仅凭模糊截图补写细节。

事实冲突按以下顺序处理：

1. 用户最新明确批准的决策和文档版本。
2. 用户明确描述的业务需求。
3. 指定 Figma 节点的设计事实和设计注释。
4. 目标主题现有设计系统、组件和技术约束。
5. Agent 推断。

任何冲突都要列出“需求说法 / 设计表现 / 建议 / 待用户决策”，不得静默选择。Figma 在审批后发生实质变化时，按变更请求回退到受影响的 PRD 或技术设计阶段。

### Rule 2 - 状态机与审批门禁

| 当前状态 | 可执行动作 | 进入下一状态所需的明确回复 |
|---|---|---|
| `INTAKE` | 读取需求与 Figma，起草 PRD | Agent 完成 PRD |
| `PRD_REVIEW_PENDING` | 只修改 PRD | 用户明确批准指定 PRD 版本 |
| `TECH_REVIEW_PENDING` | 只修改技术设计和 PRD 决策记录 | 用户明确批准指定技术设计版本及开发范围 |
| `DEVELOPMENT_AUTHORIZED` | 在批准范围内开发、测试；仅在已授权时更新指定 Draft | Agent 完成开发和全量视觉扫描 |
| `VISUAL_DECISION_PENDING` | 展示差异和方案，不得静默修复或接受 | 用户逐项决定修复、接受或改需求 |
| `FINAL_REVIEW_PENDING` | 提供最终证据包，不得提交代码 | 用户明确表示最终验收通过 |
| `SUBMISSION_DECISION_PENDING` | 只询问 Git 操作范围 | 用户分别授权 commit、push、MR 中的具体动作 |
| `COMPLETE` | 汇报实际完成范围 | 无 |

“继续”“处理一下”“提交代码”等对象不明确的回复不能自动跨门禁。Agent 必须用当前文档版本和下一动作复述授权范围并请求一句明确确认。

以下授权彼此独立：

| 授权 | 不自动包含 |
|---|---|
| PRD 通过 | 技术设计通过、开发、Draft 写入 |
| 技术设计通过 | Draft 写入，除非批准内容明确写出目标 Draft 和写入授权 |
| Draft 写入 | Live 发布、Git 提交 |
| 最终验收通过 | commit、push、创建 MR |
| commit | push、创建 MR |
| push | 创建 MR、合并、发布 |
| 创建 MR | 合并、部署、Live 发布 |

本 Skill 永不把 Draft 验证当作 Live 发布授权。Live 发布必须进入独立发布流程并重新确认。

### Rule 3 - PRD 阶段

进入 `INTAKE` 后读取 [PRD 模板](references/prd-template.md)，输出 `v0.1 待评审` PRD。PRD 必须做到：

1. 分开记录“用户原始理解”和“Agent 对需求的结构化理解”。
2. 说明业务目标、组件边界、页面位置、范围和非目标。
3. 用需求 ID 描述内容、交互、状态、异常和验收条件。
4. 列出桌面、移动及二者之间宽度的响应式规则。
5. 区分 Figma 明示、用户确认、现有主题约束和 Agent 建议。
6. 给出运营可配置项矩阵：字段、类型、默认值、约束、回退和响应式影响。
7. 给出代码固定项矩阵：布局规则、断点策略、语义结构、安全边界、最小/最大数量和不可配置原因。
8. 说明产品层面的实现思路，但不提前决定具体文件或编写代码。
9. 以 Given / When / Then 写可执行验收条件。
10. 显式列出待确认项、设计冲突和风险。

桌面和移动两张设计稿不等于所有宽度规则已经明确。PRD 必须说明中间宽度如何插值、何时换行/堆叠、内容顺序、图片裁切、可见性、容器宽度和断点来源。无法由设计确定时只能提出带理由的建议并等待确认。

当背景图片或大幅视觉媒体具有固定原始比例时，PRD 必须额外给出“背景媒体适配预案”，不得只写 `background-size: cover`。预案至少明确：

1. 图片属于装饰背景还是承载信息的内容图片；内容图片优先使用语义化 `picture/img`，不能仅因视觉位置而改成 CSS background。
2. 是否允许裁切。允许裁切时使用 `cover` 思路并定义焦点；必须完整展示时使用 `contain` 思路并定义留白颜色或延展背景；禁止直接拉伸变形。
3. 桌面与移动是否共用素材。若单一素材无法同时保留主体和安全内容区，应配置独立移动素材或经用户批准的降级方案。
4. 媒体容器在标准桌面、超宽屏、矮屏桌面、平板横/竖屏、窄屏手机和高长宽比手机下的高度、宽度、最大/最小边界和裁切方向。
5. 主体焦点、可裁切区和文字安全区；背景上的文案不得在任何目标比例下遮挡主体或落入低对比区域。
6. 对 `viewport width` 与 `viewport height` 分别敏感的规则。不能只按宽度断点推断短屏横屏和超宽屏行为。
7. 断点边界和极端比例的验收视口，以及素材缺失、加载失败和 Theme Editor 更换图片后的回退。

背景媒体适配决策按以下顺序：保持主体与信息完整 -> 保持文字可读和安全区 -> 保持布局稳定 -> 再追求设计稿中的裁切效果。若无法同时满足，必须在 PRD 中列为待确认设计取舍。

完成后只提交 PRD 审核摘要，并询问：“是否批准 PRD <版本>，进入技术设计？”不得同时输出技术设计或代码。

### Rule 4 - 技术设计阶段

只有 PRD 获得明确批准后，才能读取 [技术设计模板](references/technical-design-template.md) 并检查目标代码库。若仓库存在 `.codegraph/`，先用 CodeGraph 定位相关 section、snippet、asset、schema 和调用路径；否则再做最小范围搜索。

技术设计必须：

1. 锁定已批准 PRD 版本、目标仓库、分支/工作区、页面位置和现有实现基线。
2. 给出 section、snippet、asset、locale、template 等文件级改动计划。
3. 建立“PRD 需求 ID -> 实现位置 -> 配置字段 -> 测试 -> 证据”的追踪矩阵。
4. 描述 Liquid 渲染模型、Theme Editor schema、block 数量边界、默认值、空值回退和向后兼容。
5. 描述容器、Grid/Flex、层叠、定位、断点、图片裁切、字体和中间宽度行为。
6. 说明交互状态、键盘行为、无 JS 回退、section 重载生命周期和 reduced-motion 策略。
7. 说明性能预算和实现策略，不只写“性能良好”。
8. 说明可访问性、SEO、语义结构、焦点、alt、对比度和触控目标。
9. 列出单元/静态检查、Theme Editor、浏览器、响应式、视觉和性能验收矩阵。
10. 写清 Draft theme 名称/ID、预览入口、远端漂移检查和回退方式。
11. 记录未决风险、依赖、假设和不在本次范围的事项。

固定比例背景媒体的技术设计还必须说明：渲染原语（CSS background 或 `picture/img`）、原始素材比例、容器比例/高度公式、`cover` 或 `contain` 的选择依据、`background-position/object-position` 焦点、桌面/移动 source 切换、超宽/矮屏与横屏 media query、最大/最小高度、稳定占位和禁止拉伸规则。不得用一个未经验证的固定高度覆盖所有屏幕比例。

性能设计至少覆盖：

| 维度 | 要求 |
|---|---|
| Liquid/HTML | 优先服务端渲染和语义 HTML，不为纯布局引入 JS |
| CSS/JS | 组件作用域加载；不得无依据增加全局资源或第三方脚本 |
| 图片/视频 | 正确尺寸、宽高或 aspect-ratio、srcset/sizes、格式、裁切与回退 |
| 首屏资源 | 只有确认属于 LCP 候选的首屏媒体才禁止 lazy-load；非首屏默认延迟加载 |
| CLS | 为媒体和动态内容预留稳定空间 |
| 测量 | 定义同条件前后对比、运行次数、取中位数和可接受预算；Lab 与 Field 证据分开 |

技术设计完成后询问：“是否批准技术设计 <版本> 并授权开发？如需写入 Draft，请同时确认目标 Draft theme <名称/ID>。”未获明确批准不得改代码。

### Rule 5 - 开发与 Draft 规则

开发前必须读取相关项目文档、现有实现、调用方和测试，并确认 working tree 未出现无法归属的变更。发现意外改动立即停止，请用户决定。复用用户指定的分支/工作区，不自行 commit、切分支或创建 MR。

实现必须：

1. 只修改技术设计批准的文件和必要的需求级变更记录。
2. 复用主题已有 token、布局、snippet 和交互模式。
3. 保持 schema ID 稳定、命名表达业务意图，并校验外部输入和配置边界。
4. 不为像素匹配引入无依据的绝对定位、全局 CSS、重复资源或重型 JS。
5. 不通过放宽测试假设、删除断言或隐藏错误来换取通过。
6. 在对应项目 `变更记录/` 中使用一份需求级记录覆盖代码、文档、行为、验证、风险和下一步。
7. 只执行已在技术设计中获批的验证；未执行的项目必须标记“未验证”。

开发完成后、开始最终视觉交付前，必须读取 [运营配置说明模板](references/operations-configuration-guide-template.md)，根据实际 Theme Editor 配置生成一份面向运营同事的配置说明。该文档属于组件交付物，不是技术设计的附录。

运营配置说明必须：

1. 使用运营在 Theme Editor 中看到的字段名称和顺序，覆盖全部可配置项；不得记录不存在的配置，也不得漏掉实际字段。
2. 用简单语言说明“它会改变页面上的什么”“什么时候需要修改”“推荐怎么填”“填错会发生什么”和“如何恢复默认”。
3. 避免大量技术术语。不得直接用 `schema`、`Liquid`、`CSS`、`padding`、`object-fit`、`breakpoint` 等词解释操作；必要概念要翻译成“配置面板”“组件上下留白”“图片显示区域”“屏幕宽度范围”等运营语言。
4. 将文字内容、图片、链接、文字大小、颜色、对齐等高频内容放在“常用配置”，打开文档即可看到。
5. 将组件内外间距、上下留白、图片焦点、遮罩强度、不同设备单独设置、最小/最大高度等低频或高影响选项放在“进阶配置”，并使用可展开区域，默认收起。
6. 对有关联的选项说明显示条件，例如“开启按钮后才会出现按钮文字和链接”。
7. 对桌面和移动效果有差异的配置分别说明，不得让运营猜测是否共用。
8. 提供推荐值、允许范围、示例和注意事项；不要求运营理解代码单位。必须出现数值时，同时解释数值变大或变小的可见效果。
9. 说明预览、保存和生效边界，明确 Draft 预览不等于 Live 发布。
10. 配置说明完成后用实际 Draft Theme Editor 逐项核对字段名称、分组、默认值、条件显示和结果；文档与实际不一致视为交付缺陷。

只有技术设计审批明确包含 Draft 写入，才能操作 Shopify：

1. 重新查询主题角色、目标 Draft theme 身份和 `processing` 状态。
2. 确认目标不是 Live，且不会覆盖他人的共享 Draft 或远端未合并变化。
3. 发现远端漂移时停止，先由用户决定拉取、换 Draft 或建立新基线。
4. 只更新批准的专用 Draft；保存 theme 名称、ID 和 preview URL。
5. 写入后重新读取或对比远端源，区分“上传成功”“浏览器功能通过”“视觉验收通过”。
6. 永不在本阶段发布 Live。

### Rule 6 - 全量视觉 QA 与差异决策

开发和 Draft 预览就绪后读取 [视觉 QA 与交付模板](references/visual-qa-handoff-template.md)。先重新获取当前 Figma 上下文和截图，确认设计未漂移，再进行全量扫描。

全量扫描至少覆盖：

| 覆盖面 | 检查内容 |
|---|---|
| 设计基准 | 桌面 Frame 尺寸、移动 Frame 尺寸 |
| 响应式 | 已批准的所有区间；断点前、断点、断点后 |
| 屏幕比例 | 标准、超宽、矮屏、平板横/竖屏、窄屏和高长宽比手机 |
| 内容 | 默认、最短、最长、缺失媒体、最大/最小 block |
| 交互 | 默认、hover、focus、active、disabled、打开/关闭等适用状态 |
| Theme Editor | 添加、删除、重排、配置更新和 section 重载 |
| 运营配置说明 | 字段、分组、默认值、条件显示、示例和实际效果一致 |
| 视觉 | 结构、顺序、尺寸、间距、对齐、字体、颜色、圆角、阴影、裁切、层级 |
| 功能 | 链接、按钮、媒体、键盘、触控和降级 |
| 性能 | 技术设计中的预算；与视觉结论分开报告 |

截图前等待字体、关键媒体和页面稳定；使用与 Figma Frame 一致的 viewport。每个基准保存一张 Figma 设计截图和一张实现截图，必要时生成并排图或透明叠图。自动像素差异只能辅助定位，不能代替语义、交互和响应式判断。

固定比例背景媒体除 Figma 基准尺寸外，必须在技术设计批准的极端比例视口下检查：主体是否被错误裁切、文字是否离开安全区、背景是否露底或被拉伸、容器是否产生异常空白/溢出、焦点是否连续跳变。若使用运营可替换图片，还要至少用一张比例不同于默认素材的图片验证约束和回退。

发现任何不一致时：

1. 创建 `VQA-001` 起的差异清单。
2. 每项包含需求 ID、视口、严重级别、期望、实际、Figma 截图、实现截图、建议方案和影响。
3. 严重级别使用 `Blocker / Major / Minor / Accepted-candidate`，不得因“看起来差不多”自动降级。
4. 停在 `VISUAL_DECISION_PENDING`，请用户逐项选择“修复 / 接受差异 / 修改需求”。
5. 用户接受差异时，将决定同步到 PRD、技术设计和变更记录，形成批准偏差。
6. 用户要求修复时回到开发，只修改确认项；修复后重测该项并执行必要回归，再重新提交差异清单。
7. 不得一边等待用户决定，一边继续修复未批准项。

没有未决差异时进入 `FINAL_REVIEW_PENDING`。

### Rule 7 - 最终证据包与代码提交确认

最终证据包必须包含：

| 交付项 | 内容 |
|---|---|
| 组件信息 | 正式名称、用途、页面位置 |
| 审批基线 | PRD 版本、技术设计版本、Figma 节点 |
| Draft | theme 名称、ID、preview URL；明确不是 Live |
| 运营配置说明 | 面向运营的文档路径/链接；常用配置直接展示，进阶配置默认收起 |
| 桌面证据 | 一张最终 Figma 截图 + 一张同 viewport 的实现截图 |
| 移动证据 | 一张最终 Figma 截图 + 一张同 viewport 的实现截图 |
| 差异结论 | 无差异或已批准偏差 ID |
| 验证 | 功能、响应式、Theme Editor、静态检查、性能结果 |
| 代码状态 | 变更文件、未验证项、是否未 commit/未 push |
| 风险 | 剩余风险和下一步 |

差异评审期间可以附加问题截图；最终交付只保留一组桌面和一组移动主证据，避免用大量截图掩盖结论。

用户明确表示最终验收通过后，进入 `SUBMISSION_DECISION_PENDING`，只询问：

“最终验收已通过。是否授权代码操作？请分别确认：1. commit；2. push；3. 创建 MR。未明确授权的动作不会执行。”

不得把“提交代码”自动解释为 commit + push + MR，也不得把任何 Git 授权解释为合并、部署或 Live 发布。

### Rule 8 - 文档、证据与安全

优先沿用项目现有目录和命名。没有现成约定时可使用：

| 产物 | 建议位置 |
|---|---|
| PRD | `~/projects/docs/<项目>/<组件名>-PRD.md` |
| 技术设计 | `~/projects/docs/<项目>/<组件名>-技术设计.md` |
| 视觉验收 | `~/projects/docs/<项目>/验收证据/<组件名>/视觉验收.md` |
| 变更记录 | `~/projects/docs/<项目>/变更记录/<日期>-<组件名>.md` |
| 运营配置说明 | `~/projects/docs/<项目>/<组件名>-运营配置说明.md` |

每次代码或项目文档变更只维护一份需求级变更记录，跨仓库时也用同一记录追踪职责、文件、行为、验证和剩余风险。

不得在 Skill、文档、截图文件名、命令参数或聊天中保存 token、密码、session cookie、preview secret 或私钥。认证只能通过当前环境批准的凭证机制无回显注入。

### Rule 9 - 必须停止的情况

出现以下任一情况必须停止并报告当前阶段、已有证据、阻塞点和最小下一步：

- Figma 节点无效、权限不足、桌面或移动基准缺失。
- 需求、Figma 和现有主题存在未决冲突。
- PRD 或技术设计未获明确批准。
- 仓库出现无法归属的变更。
- Draft theme 身份不明、是 Live、处于 processing 或存在远端漂移。
- 视觉差异尚未获得用户决策。
- 同方向修复两次仍失败。
- 操作需要超出已授权的 Draft、Git、MR、合并或发布范围。

## Examples

### Bad

```text
用户提供两条 Figma 链接和一句需求。
Agent 直接创建 Liquid section、上传主题、截图后说“已完成”。
问题：跳过 PRD/技术设计审批，未定义中间宽度，未区分运营配置与固定逻辑，也没有 Draft 写入授权。
```

```text
视觉核对发现移动端标题位置和图片裁切不一致。
Agent 自行按个人判断修改后继续交付。
问题：差异属于需求决策，必须给出对比截图和影响并等待用户选择。
```

```text
用户说“可以提交”。
Agent commit、push、创建 MR，并发布主题。
问题：四类动作是独立权限，且 Live 发布不属于本 Skill 的默认流程。
```

### Good

```text
Agent 分别读取桌面和移动节点，输出 PRD v0.1：
- 记录用户理解与 Agent 理解
- 给出响应式区间
- 列出 Theme Editor 配置矩阵和代码固定项
- 标注 3 个待确认问题
然后停在 PRD_REVIEW_PENDING，请用户批准指定版本。
```

```text
技术设计 v0.2 获批，并明确授权更新专用 Draft theme。
Agent 在批准文件范围内开发，上传 Draft 后按桌面、移动、断点边界和内容状态扫描。
发现 VQA-001 图片裁切为 Major，附 Figma/实现对比截图并停下。
用户选择修复后，Agent 只修 VQA-001，重测并重新提交证据。
```

```text
视觉扫描无未决差异。
Agent 提供组件名称、Draft theme 名称/ID/preview URL、桌面与移动设计/实现截图、测试和性能证据，并说明代码仍未 commit/未 push。
用户最终验收后，Agent 分别询问 commit、push、创建 MR 的授权。
```
