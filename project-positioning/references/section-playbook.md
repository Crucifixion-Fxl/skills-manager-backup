# 逐节写作手册（Section Playbook）

定位文档七段叙事弧的逐节模板。每节给出：读者问题、结构、写作要点、NoDB 范例摘录。范例来自 device-event-mesh 的 `docs/architecture/nodb-positioning.html`，写新文档时替换为目标项目的内容，不要照抄措辞。

---

## §1 Hero — 读者问题："这是什么？"

**结构：**

1. Wordmark / 项目名
2. 一句话定位（必须同时包含）：
   - 对象与规模（"面向百万到亿级 tenant、entity 与 edge stream"）
   - 保留什么 / 移走什么（"将应用状态保留在端侧数据库，将云端事实源限定为……"）
   - 量化目标（"目标降低同步数据基础设施成本 10X"）
3. 价值路径三联（Problem → Shift → Outcome）：每格一个短标签 + 一句加粗论断 + 一句解释
4. **名字护栏**（必须有）

**写作要点：**

- 一句话定位是全文压缩，写完全文后回头重写它。
- 价值路径三联的加粗句要能脱离上下文被引用，如 "Sync the event-level truth, not hot current state."
- 名字护栏直接处理最大误读：

> **NoDB means:** 不是"没有数据库"，而是不需要云端以 server-side database 作为同步事实源；端侧仍然使用 SQLite、IndexedDB、DuckDB……

**段间导航：** Hero 之后放一行 launch flow 路标（"痛点 → 转变 → 工作方式 → 场景 → 成本 → 开始使用"），告诉读者全文怎么走。

---

## §2 The Pain — 读者问题："为什么我要在乎？"

**结构：**

1. 核心痛点 callout：一段话点出结构性矛盾
2. 3–4 个痛点 tile，每个标题用 "X becomes Y" 句式
3. 收尾 "The opportunity" callout，把痛点反转为机会，引向下一节

**写作要点：**

- 痛点必须是**机制**：解释成本/复杂度为什么随规模复利放大，而不是罗列"贵、慢、复杂"。
- "X becomes Y" 标题范例：
  - "Tenant isolation becomes DB tax"（隔离的数据被迫共享中心库成本）
  - "Maintenance jobs becomes the workload"（维护任务本身成了主要负载）
  - "MQ becomes a detour, not a model"（补丁式架构没有改变事实源）
  - "System overhead compounds"（多套语义叠加，不只是付两次钱）
- 核心痛点 callout 范例结构："同步型产品经常把 A 当成 B，但在 {规模} 场景里，这个 B 很快变成 {税/复利成本}：{机制一句话}。"
- The opportunity 是 Pain 到 Shift 的铰链："当 {前提特征} 时，{现状的某个昂贵部分} 不必存在。"

---

## §3 The Shift — 读者问题："你们换了什么？"

**结构：**

1. 开篇定义转变的性质："关键转变不是'换一个 X 产品'，而是重新定义 {事实源/职责边界/所有权}"
2. 3 个职责分配 tile（谁保留什么）："Edge keeps the database / Cloud keeps the truth / Sync becomes replayable"
3. **Core model callout**：一句话说清整个模型，可独立引用

**写作要点：**

- Shift 的本质是职责重新分配，tile 标题统一用 "{角色} keeps/becomes {职责}" 句式。
- Core model 范例："所有 edge 写本地数据库；cloud 同步 event-level truth；每个 edge 再按 cursor 重建自己的数据库。"——主语齐全（谁）、动词具体（写/同步/重建）、没有形容词。

---

## §4 How It Works — 读者问题："它怎么运转？骗我的吧？"

**结构：**

1. 三层理解开篇：场景层（谁参与）→ 云端层（主链路）→ 规模层（扩展单元）
2. 场景图：所有参与的 edge/角色 + 中心系统的最小职责
3. 主链路：**≤3 个阶段**（如 Ingest → Compact → Read），一句话讲每个阶段
4. Zoom-in：单独放大承担扩展性的那个节点，讲 partition / lease / prefix 等扩展单元
5. 阶段表：每行 = 一个阶段，列 = **产品含义 + 成本含义**

**写作要点：**

- 主链路超过 3 个阶段说明抽象层次没选对——合并或者下沉到 zoom-in。
- "放大 X 节点后，实际扩展单元是 ……" 是 zoom-in 的标准开场。
- 双列表范例（Ingest 行）：
  - 产品含义："接收多端生成/修改的 event，完成鉴权、幂等与顺序追加，并按 hash 分到 partition。"
  - 成本含义："扩展单元是 partition：增加 partition / prefix，而不是扩中心数据库热分片。"
- 成本含义列回答的是"规模翻 10 倍时，什么东西变多、什么东西不变"。

---

## §5 Use Cases — 读者问题："我的场景能用吗？"

**结构：**

1. 开篇反向限定："适合的不是'所有 X'，而是 {特征列表} 的 Y"
2. 2–4 个场景 tile，每个 tile 两段：
   - **为什么适配**：场景的数据/行为特征如何命中系统模型
   - **配套能力**：哪些相邻能力*不归本系统管*、留在哪一层

**写作要点：**

- "配套能力"是这一节的灵魂——它防止读者把系统脑补成全家桶，也防止后续需求漂移。范例（Chat 场景）：
  - 为什么适配："message.sent、edit、delete、receipt 都是 event；每个端最终需要的是本地 conversation DB。"
  - 配套能力："presence、typing、push、长连接 fanout **留在实时层**；NoDB 负责 conversation state sync 和 history replay。"
- 每个场景的"为什么适配"必须落到系统模型的具体特征上（事件化、租户隔离、本地读），不能是"聊天也需要同步"这种同义反复。

---

## §6 价值论证（Cost/Value Thesis）— 读者问题："凭什么值？"

**结构：**

1. 开篇结构化解释标题数字："10X 不是'机器便宜一点'，而是把 {结构性成本} 移走"
2. **模型边界 callout**（必须有）："这是目标成本模型，不是审计结果。它假设 {前提 1、2、3}。"
3. before/after 对比（统一 scale）+ 逐模块表（列：成本项 / before / after / 变化原因）
4. 收尾标注："实际收益取决于 {fanout、保留期、读写比例……}"

**写作要点：**

- 未实测的容量/性能/收益数字一律按假设处理，显式写出模型边界——这是可信度的来源，不是示弱。
- 对比必须用同一把尺子：所有模块共享一个归一化 scale（如 Traditional 总分 100 / NoDB 总分 10），不要每个模块各自归一化——后者读者无法横向比较。
- **不归零的项如实保留**：范例中 Control plane 从 4 降到 1 而不是 0，并解释"控制面不会消失，但它不再管理中心热库分片"。全是零的对比表没有可信度。
- "变化原因"列写机制（"同步事实转为 oplog + objects，edge DB 承接查询状态"），不写形容词（"大幅优化"）。

---

## §7 Get Started — 读者问题："我明天能干什么？"

**结构：**

1. 开篇定义最小路径："最小采用路径不是先替换整套 X，而是从一个 {租户/对象/adapter} 开始，证明 {核心闭环}"
2. ≤4 步编号路径（每步一个动词开头的短标题）
3. 指向深入文档的 "Explore the implementation" callout（按阅读顺序排列链接）
4. **FAQ 表**：纠正分类错误
5. 收尾 "Start narrow" callout

**写作要点：**

- 4 步范例："Pick an edge DB → Capture events → Compact for reads → Replay locally"——每步是一个可验证的动作，不是一个章节标题。
- FAQ 的问题就是读者最可能的归类错误，答案统一句式：先"不是。"，再一句重述正确定位：

> Q: NoDB 是不是没有数据库？
> A: 不是。NoDB 的意思是 cloud source of truth 不需要 server-side database shards；edge 仍然使用真实数据库。

- 至少覆盖 3 类误读：名字字面误读、归类成相邻品类（"是不是 MQ？"）、能力窄化（"是不是只支持 X？"）。
- "不是。"句式只用于分类错误；**能力外扩类**问题（"能不能顺便做 X？"）改用边界句式："可以接，但 X 不归本系统管，留在 {层/系统}"——硬套"不是。"会答非所问。
- "Explore the implementation" 链接区仅在已有配套文档集时保留；新项目没有可链文档就整段省略，不要放占位符。
- 若用户明确要求与竞品/相邻系统正面对比，可在 §5 之后加一节对比表：对比维度用**职责边界**（事实源在哪、谁负责收敛、历史归谁），不要用功能打勾矩阵——定位文档比的是模型，不是 feature 数量。

## 输出格式

- 默认 Markdown，七段对应七个 `##` 章节。
- 目标文档集是 HTML 且已有统一视觉语言/样式系统时，跟随现有样式（如 device-event-mesh 的 `.dm-*` 图类 + 内联 CSS），不要另起炉灶。
- 图优先级：场景图（§4）> before/after 成本图（§6）> 主链路图（§4）。没有制图条件时用表格替代成本图，但统一 scale 原则不变。
- **篇幅预算**：全文 1500–3000 中文字为宜；§2/§4/§6 是重心，§1/§3/§7 每节 ≤200 字。受众偏管理层时压缩 §4 的 zoom-in、保留双列表；受众偏工程时反之。
- 落点：跟随目标项目文档集的现有约定（如 `docs/architecture/{name}-positioning.{md,html}`）；无约定时与用户确认。
