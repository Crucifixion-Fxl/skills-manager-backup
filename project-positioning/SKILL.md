# Project Positioning（项目定位文档）

定位文档不是功能清单，而是一篇**论证**：读者带着"这是什么？跟我有什么关系？是不是又一个 X？"的疑问进来，文档的每一节回答一个疑问，并主动拆除读者最可能产生的误读。本方法论提炼自 NoDB 定位文档的实战结构。

详细的逐节写法与范例参见 [references/section-playbook.md](references/section-playbook.md)。

## 何时用 / 何时不用

| 适用 | 不适用 |
|------|--------|
| 项目对外/对内的定位页、landing 页 | 接口文档、操作手册（用常规技术文档） |
| 向管理层/新人解释"这个系统为什么存在" | 架构设计文档（用 architect skill） |
| 澄清"我们 vs 竞品/相邻系统"的边界 | 单纯的 README 用法说明 |

## 叙事弧（七段，顺序固定）

```
Hero → The Pain → The Shift → How It Works → Use Cases → 价值论证 → Get Started
（是什么 → 为什么痛 → 转变是什么 → 怎么运转 → 用在哪 → 凭什么值 → 怎么开始）
```

每一节回答读者心里的一个问题。跳过 Pain 直接讲架构，读者不知道为什么要在乎；跳过反向定位，读者会把它归类成已知的东西然后失去兴趣。

## 六条核心纪律

1. **名字护栏（Name Guardrail）**：在 Hero 里就纠正项目名最可能引发的误读。格式：`X means: 不是"字面误读"，而是"真实含义"`。不要指望读者读到 FAQ 才被纠正——大部分读者读完 Hero 就走了。

2. **痛点写成机制，不写成抱怨**：每个痛点用 "X becomes Y" 句式命名（如 "Tenant isolation becomes DB tax"、"MQ becomes a detour, not a model"；中文文档可用"X 成了 Y"，与正文语言一致即可），正文解释这个机制如何随规模复利放大。"数据库很贵"是抱怨；"租户数据天然隔离，中心库却为所有租户维护索引和 DB jobs"是机制。

3. **反向定位与正向定位同等重要**：
   - Use Cases 一节必须以反向限定开头："适合的不是所有 X，而是满足 …… 特征的 Y"。
   - 每个 use case 写两段：**为什么适配**（模型与场景的契合点）+ **配套能力**（明确指出哪些相邻能力*不归本系统管*、留在哪一层）。这一段防止读者把系统脑补成全家桶。
   - FAQ 用"不是。……"句式逐条纠正分类错误（不是数据库？不是 MQ？只支持 X？），每条答案先否定误读、再重述正确定位。

4. **价值数字必须带模型边界**：未实测的容量/性能/成本收益是**目标模型，不是审计结果**——必须显式写出这句话，并列出模型成立的前提假设。Hero 里用"目标 X 倍"的措辞带出标题数字即可，完整边界声明放价值论证节。before/after 对比必须用同一把尺子（统一 scale，不要每个模块单独归一化）。不归零的成本项如实保留（"控制面不会消失，但它不再管理 X"）；系统把成本从一处**转移**到另一处时，after 侧的新增成本项（0 → N，如新引入的边缘节点运营）也要如实列出——全是降项的对比表和全是零的对比表一样没有可信度。结尾标注"实际收益取决于 ……"。

5. **主链路 ≤3 个阶段，扩展细节放 zoom-in**：How It Works 先给一条 ≤3 阶段的主链路（如 Ingest → Compact → Read），再单独放大其中承担扩展性的那个节点讲 partition / lease / 扩展单元。阶段表每行同时写**产品含义**和**成本含义**两列——定位文档的读者一半在乎体验，一半在乎账单。

6. **Get Started 是最小路径，不是迁移指南**：明确写"最小采用路径不是先替换整套 X，而是从一个 {租户/对象/adapter} 开始"，给 ≤4 步编号路径，结尾用 "Start narrow" 收束。

## 执行流程

### Step 0：先用 `grill-with-docs` 对齐定位问题

写 positioning doc 之前，先判断核心定位是否已经清楚。若**核心定位、目标读者、结构性痛点、命名、系统边界、主链路**任一项仍模糊，必须先使用 `grill-with-docs` 与用户逐问逐答，把关键术语和决策讨论清楚，再进入成文。

使用 `grill-with-docs` 时遵守两条规则：

1. 如果问题能从已有文档、`CONTEXT.md`、ADR、README 或代码路径回答，先读文档/代码，不要把可查事实重新丢给用户。
2. 如果问题需要产品/业务/架构取舍，由 `grill-with-docs` 一次只问一个问题，并给出推荐答案，直到定位文档所需的关键术语、边界和主链路都达成共识。

`grill-with-docs` 安装地址：`https://github.com/mattpocock/skills/tree/main/skills/engineering/grill-with-docs`。使用 skills CLI 时可从 `mattpocock/skills` 安装，例如：

```bash
npx -y skills add mattpocock/skills --agent claude-code --skill grill-with-docs
```

### Step 1：访谈提取原料

写之前先向用户收集（缺哪项问哪项，已在上下文里的不重复问）：

1. **名字与误读**：项目叫什么？听到名字的人最可能误以为它是什么？
2. **规模与对象**：为谁（tenant/团队/设备）？什么数量级？
3. **结构性痛点**：现状里哪个成本/复杂度随规模复利放大？机制是什么？
4. **转变**：移走了什么、保留了什么、重新定义了什么？能否用一句话说出 core model？
5. **主链路**：≤3 个阶段是什么？扩展单元是什么？
6. **场景**：2–4 个适配场景；每个场景里哪些相邻能力明确不做？
7. **价值主张**：标题数字（如 10X）是什么？成立前提是什么？哪些成本项不归零、哪些是新增？
8. **最小起步**：第一个落地切片是什么？

**原料不全 / 非交互场景**：用户一次性给了背景但缺关键项（常见缺：痛点机制、主链路、扩展单元）时，可以从已知材料推导补全，但推导出的机制细节必须与用户给定的事实区分——在交付时列出"以下内容是我推导的，请确认：……"，价值数字相关的推导直接在文中标注为假设。不要把发明的架构细节当事实写进定位文档。

### Step 2：按叙事弧成文

按 [references/section-playbook.md](references/section-playbook.md) 的逐节模板写。默认输出 Markdown；若目标文档集是 HTML（已有统一视觉语言/样式系统），跟随现有样式而不是另起炉灶。

### Step 3：自检清单

交付前逐项核对：

- [ ] Hero 内有名字护栏，且一句话定位包含：对象规模 + 保留什么/移走什么 + 量化目标
- [ ] 每个痛点是 "X becomes Y" 机制，不是形容词抱怨
- [ ] 有一句可独立引用的 core model（主语齐全、动词具体、没有形容词）
- [ ] 主链路 ≤3 阶段；扩展性细节在 zoom-in 里而不是混在主链路里
- [ ] 阶段表有"产品含义 + 成本含义"双列
- [ ] Use Cases 以"适合的不是所有……"开头；每个场景都有"配套能力"段指明不做的部分
- [ ] 价值数字标注"目标模型，不是审计结果"+ 前提假设 + "实际收益取决于……"
- [ ] before/after 用统一 scale；不归零的项如实保留，after 新增的项如实列出
- [ ] FAQ 用"不是。……"纠正至少 3 个最可能的分类错误
- [ ] Get Started 是最小切片路径（≤4 步），不是全量迁移指南

## 示例

### ❌ Bad — 功能清单式定位

> 本系统支持高性能事件摄取、灵活的压缩策略、多种存储后端、完善的监控告警……

问题：没有回答"为什么存在"；读者无法区分它和任何同类系统；没有边界，像什么都能干。

### ✅ Good — 论证式定位

> 租户数据天然隔离，传统同步架构却让所有租户一起承担中心 DB、索引、DB jobs 和 MQ 绕行成本（Pain，机制）。NoDB 把云端事实源限定为 event-level oplog + sync objects + cursor（Shift）。NoDB 不是"没有数据库"——端侧仍然使用 SQLite/IndexedDB（名字护栏）。目标降低同步基础设施成本 10X——这是目标成本模型，不是审计结果（价值边界）。
