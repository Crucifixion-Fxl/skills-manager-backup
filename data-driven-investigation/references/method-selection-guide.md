# Method Selection Guide — 3 路找方法详细流程

> SKILL.md Step 5 的详细指引：**不要只查目录**，要走 3 路并行再合流。

## 为什么要 3 路

- **目录**滞后于业界最新方法（学术论文、社区博客、各行业 best practice 不会自动进目录）
- **独立思考**能把问题映射到更本质的模式（相邻领域通常已有成熟解法）
- **WebSearch** 可发现近年新兴方法或被验证过的 trade-off 讨论

单走一路的风险：
- 只查目录 → 方法锁定，陷入"我的锤子我最熟"
- 只靠思考 → 重新造轮子
- 只靠 WebSearch → 被花哨新方法误导，忽略数据适配

## 路径 A：查 [method-catalog.md](method-catalog.md)

**做什么**：对照问题类型（Descriptive / Diagnostic / Predictive / Prescriptive / EDA / CDA / Anomaly）+ 数据特征（样本量 / 时间结构 / 维度），挑 1-3 个候选。

**时间**：5-10 分钟。

**产出**：3 个候选方法 + 每个的最小样本要求 + 已知局限。

## 路径 B：独立思考 5 个问题

**做什么**：强迫自己跳出目录，从更本质的视角审视问题。

### Q1: 如果我完全不懂统计，直觉会怎么做？

常识方法往往就是好方法。典型例子：
- "看看同款设备/用户的平均水平" → cohort 相对比较
- "看看最近的趋势" → 时序
- "按时间分段对比" → DiD 雏形
- "挑几个典型案例看看" → case study / outlier inspection

**Why**：常识方法**可解释性高**，业务方容易接受；且往往正是"被专业化了的统计学"的本源（如 t-test 就是"两组均值比较"的正式化）。

### Q2: 这个问题如果换一个领域会怎么解？

把你的业务问题抽象成"<做诊断|做预测|做归因|做分层>"，然后想其他领域同样模式是怎么做的：

| 抽象模式 | 医学做法 | 金融做法 | 质检做法 | 电商做法 |
|---|---|---|---|---|
| 诊断异常个体 | 差异表达基因 / biomarker | 欺诈检测 | 缺陷检测 | 异常订单识别 |
| 分层干预效应 | 亚组分析 | 信用分群 | 批次分组 | 用户分群投放 |
| 变点检测 | 疫情爆发点 | 市场动荡 | 生产线异常 | 流量突变 |
| 归因多因素 | 流行病学回归 | 风险因子分析 | 故障树 | 营销归因 |

如果别的领域有 30 年成熟方法（如医学的亚组分析），就直接移植，不要重新发明。

### Q3: 如果我想证伪这个假设，数据应该长什么样？

**反向设计**。不是"哪些数据支持假设"，而是"哪些数据**推翻**假设"。

例子：假设 "X 产品异常率高"：
- 支持证据：X 的异常率显著 > cohort
- 证伪证据：X 的异常率 <= cohort，**且** X 在 cohort 里有充分样本

反向设计避免**确认偏差**：你一开始就知道该看什么指标，而不是看到什么说什么。

### Q4: 这个问题的 90/10 版本是什么？

90% 效果 / 10% 成本的方法永远应该先跑一次：
- **A/B test 太重？** → 先跑观察性 DiD 拿方向
- **时序建模太复杂？** → 先 SMA/EWMA 看趋势
- **ML 模型太贵？** → 先 rule-based 基线

**Why**：快速拿到粗结果能验证方向，避免在复杂方法上白投资源。

### Q5: 每个候选方法**会在什么情况下失败**？

对每个候选预演失败模式：
- Cohort 异常：**cohort 样本 < 50** 时失败
- z-score：**分布极度偏斜**时失败
- A/B test：**随机化被污染**（比如 ops 误把实验组切到对照组）时失败
- DiD：**parallel trends 不成立**时失败

**预演失败模式**让你在 Step 6 分析一跑就知道出错；且指导 Step 5 的"备选方案"怎么写。

## 路径 C：WebSearch 最新实践

**何时必须搜**：
- 拿不准方法适用性
- 不确定有没有更好方法
- 想借鉴相邻领域成熟做法
- 需要理论依据支持决策

**Query 模板**：

| 你要什么 | Query |
|---|---|
| 了解业界最新方法 | `"<问题类型> detection 2026 methodology"` |
| 领域对标 | `"how to detect <X> in <domain>"` |
| 候选方法局限 | `"<method name> limitations alternatives"` |
| 数据特征适配 | `"<data characteristic> analysis techniques"` |
| 学术 vs 工程 | `"<method> in practice production deployment"` |

**可信度分层（重要）**：

| 来源 | 可信度 | 注意 |
|---|---|---|
| arXiv / peer-reviewed | 高 | 学术，要看是否 validated |
| Wikipedia | 高 | 基础概念 |
| 厂商 blog（Google, Meta, Netflix 等）| 中高 | 有偏，但实践价值高 |
| Stack Overflow 高赞答 | 中 | 检查是否过时 |
| 个人博客 / Medium | 中 | 看作者背景 |
| LLM 生成 tutorial | 低 | 容易胡编 |
| 无日期社区回答 | 低 | 方法过时风险 |

**记录要求**：每次 WebSearch 都在 04-findings.md 或 method-pick 段注明 URL。

## 合流：3 路候选如何收敛

把 A/B/C 三条路的候选合并，按 5 维打分：

| 维度 | 权重 | 打分标准 |
|---|---|---|
| **数据适配度** | 30% | 满足最小样本 / 分布假设 / 字段可用性（Step 3/4 已确定）|
| **实现复杂度** | 20% | SQL < Python script < ML pipeline < 自定义 infra |
| **可解释性** | 20% | 业务方能否无需统计背景理解结论 |
| **已知局限严重度** | 20% | 局限是否会误导生产决策 |
| **有无 reference 实现** | 10% | 有 reference（SQL 模板 / 开源库）的优先 |

**收敛规则**：
- 排名第一 = 主方法
- 排名第二 = 备选方案（写明"当 <条件> 时切换"）
- 明显不适合的候选 → 文档里短暂提及 + 排除理由

## 方法选型产出模板

```markdown
## 方法选型

**选择**: <主方法>
**理由**:
  - 数据特征 <X> 匹配该方法的前提
  - 候选方法 A/B/C 打分见下表
  - 选择 A 的决定性因素：<核心理由>

**打分对比**

| 方法 | 数据适配 | 复杂度 | 可解释性 | 局限严重 | reference | 总分 |
|---|---|---|---|---|---|---|
| A | 9 | 7 | 8 | 6 | 9 | 7.9 |
| B | 6 | 9 | 9 | 4 | 5 | 6.7 |
| C | 9 | 3 | 5 | 8 | 7 | 6.5 |

**备选方案（主方法失败时切换）**:
  - B: 当 <条件 X>（例如 cohort 样本 < 50）时切换到 B
  - C: 当 <条件 Y> 时切换到 C

**已知局限**:
  - 主方法 A 的已知局限：<局限 1 + 影响>
  - …

**参考**:
  - Catalog: [method-catalog.md](method-catalog.md#xxx)
  - WebSearch: [URL 1] / [URL 2]
  - 跨域借鉴: <医学亚组分析 / 金融欺诈检测>
```

## 核心纪律

1. **Step 5 必须走 3 路** — 漏任一路都算"方法锁定"
2. **记录 WebSearch URL** — 可信度评估自带
3. **预先写备选方案** — 切换不需要重新 brainstorm
4. **独立思考 ≠ 瞎想** — 用 5 个结构化问题（Q1-Q5）而不是直觉
