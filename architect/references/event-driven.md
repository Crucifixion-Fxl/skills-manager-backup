# Event-Driven Architecture — 决策卡

## 什么时候用

- 跨服务协调：A 完成后 B、C、D 都需要响应，但 A 不需要等它们完成
- 状态变更通知：设备上线、订单支付、固件升级完成等事件需要广播
- 削峰填谷：突发流量需要缓冲，下游按自己的速率消费
- 审计追踪：需要记录"发生了什么"的完整时间线

## 核心概念速查

| 概念 | 一句话解释 | 追问示例 |
|------|----------|---------|
| **Event Sourcing** | 不存最终状态，存所有变更事件，状态通过回放事件重建 | "需要知道'怎么到达当前状态'还是只需要'当前状态是什么'？" |
| **CQRS** | 读模型和写模型分离，各自优化 | "读和写的模式差异大吗？查询需要跨多个聚合拼装吗？" |
| **Saga / 编排 vs 协作** | 跨服务长事务的协调方式。编排：中心控制器。协作：各服务监听事件自行响应 | "这个流程有多少步？需要一个地方看到全局进度吗？" |
| **死信队列 (DLQ)** | 消费失败的消息去哪里 | "消费失败的事件怎么处理？丢弃？重试？人工介入？" |
| **幂等消费** | 同一事件被消费多次，结果不变 | "如果这个事件被重复投递了，会发生什么？" |

## 与本 skill 的关系

- Step 2 的"集成模式"追问中，同步 vs 异步的决策直接关联此模式
- US 中出现"通知"、"推送"、"异步"、"最终一致"时，引用此卡评估

## 什么时候不用

- 强一致性要求：转账等操作需要立即确认结果，事件驱动的最终一致不满足
- 简单的请求-响应：A 调 B 取结果，没有广播需求，同步调用更简单
- 调试复杂度不可接受：事件驱动让问题追踪变难，团队没有分布式追踪基础设施时慎用
