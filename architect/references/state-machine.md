# State Machine — 决策卡

## 什么时候用

- 实体有明确的生命周期：设备（离线→在线→升级中→在线）、订单（待支付→已支付→已发货→已完成）
- 状态转换有规则：不是所有状态都能到达所有状态（已取消的订单不能变成已发货）
- 并发状态变更：多个请求可能同时尝试改变同一实体的状态
- Bug 频发在状态相关逻辑：隐式状态管理（一堆 if/else）导致非法状态出现

## 核心概念速查

| 概念 | 一句话解释 | 追问示例 |
|------|----------|---------|
| **State** | 实体在某一时刻的状态 | "这个实体有哪些可能的状态？画得出完整列表吗？" |
| **Transition** | 从一个状态到另一个状态的变化 | "从状态 A 可以到哪些状态？不能到哪些？" |
| **Guard Condition** | 转换发生的前提条件 | "什么条件满足时才允许这个转换？" |
| **Side Effect** | 转换发生时的附带操作 | "状态变了之后需要通知谁？触发什么？" |
| **并发控制** | 两个请求同时改状态怎么办 | "如果两个请求同时触发不同的转换，谁赢？" |

## 设计检查清单

1. **所有状态是否穷举？** 画状态图，确认没有遗漏
2. **非法转换怎么处理？** 静默忽略？报错？记日志？
3. **终态是否可逆？** 已取消/已删除是否真的不可逆？
4. **超时状态怎么处理？** 升级中超过 30 分钟没响应→自动回滚？

## 什么时候不用

- 实体只有两个状态（active/inactive）：用布尔值就够了
- 状态转换没有规则：任何状态都能到任何状态，不需要状态机
- 状态由外部系统完全控制：本系统只是镜像展示，没有转换逻辑
