# DDD (Domain-Driven Design) — 决策卡

## 什么时候用

- 业务术语混乱：同一个概念在不同团队/模块里叫法不同（"订单"vs"工单"vs"请求"）
- 服务边界不清：不确定哪些逻辑应该放在一起、哪些应该分开
- 多团队协作：需要在团队间建立共同语言，减少沟通歧义
- 业务规则复杂：核心域有大量业务逻辑，不是简单的 CRUD

## 核心概念速查

| 概念 | 一句话解释 | 追问示例 |
|------|----------|---------|
| **Ubiquitous Language** | 业务和技术共用同一套术语，消灭翻译层 | "这个概念在产品侧叫什么？代码里叫什么？两者一致吗？" |
| **Bounded Context** | 一个术语只在一个上下文里有明确含义，跨上下文需要翻译 | "这两个模块说的'用户'是同一个概念吗？" |
| **Aggregate** | 一组必须保持一致性的对象，通过 Aggregate Root 访问 | "这次操作必须同时改哪些数据才能保持一致？" |
| **Domain Event** | 业务上有意义的事情发生了 | "这个操作完成后，谁需要知道？" |
| **Anti-Corruption Layer** | 防止外部模型污染本域模型 | "接入这个外部系统后，我们的模型需要迁就它吗？" |

## 与本 skill 的关系

- `domain-model.html` 就是 Ubiquitous Language 的落地文件
- Step 2 的边界划分追问本质上就是 Bounded Context 识别
- Step 4 的模块设计中，Aggregate 定义决定了事务边界

## 什么时候不用

- 简单 CRUD 应用，业务逻辑很薄
- 原型/MVP 阶段，业务模型还在快速变化，过早固化 context 边界反而阻碍探索
- 团队只有 1-2 人，沟通成本本来就低
