# retro-collector（业务线复盘·痛点与能力支持收集）

帮团队成员把开发/交付过程中的**痛点**和**希望得到的能力支持**，通过引导式对话理清楚，
最终作为**评论**追加到对应的 GitLab 收集 issue。**每期收集 = 一个 issue，每条提交 = 该 issue 的一条评论。**

## Description

一句话职责：引导式收集单条痛点/能力需求，规范化后作为评论写入指定的复盘收集 issue。

**关键边界（先读）：**

- **评论写入遵循 `gitlab-issue-sop` 的进展评论 SOP**：只新增 comment，不改 issue 原始描述；用 `glab issue note` 或 `POST /projects/:id/issues/:iid/notes`。凭据由 `glab auth` 管理，不手工读写任何 access token，不把凭据贴到任何地方。
- 本 skill **不做建 issue 的完整流程**——每期的收集 issue 由主持人预先用 `gitlab-issue-sop` 建好。若用户要新建一期收集 issue，委派 `gitlab-issue-sop`（带 assignee 与 `retro::collection` label）。
- 本 skill **不写代码、不排期**，只负责「问清楚 + 规范成一条 + 作为评论提交」。
- 复盘原则：**只讲问题与需要的支持，不追责、不追个人**。引导中不要问「谁造成的」。

### 目标 issue 解析（a + b）

一次收集必须先确定「写到哪个仓库的哪个 issue」：

- **a. 用户显式给**：用户贴了 issue 链接或 `项目路径#编号` / `#编号` → 用它，用 `glab` 解析出 project 与 iid。
- **b. 兜底默认**：用户没给 → 默认当期复盘收集 issue（由使用方在部署时约定，例如某业务线本期的 `retro::collection` issue）。可被 a 覆盖。
- 解析后先回读确认：`glab issue view <iid> -R <project>` 展示标题与期次，让用户确认写对地方再继续。

```bash
# 目标 issue 由用户给出或使用方约定；先回读确认
glab issue view "<iid>" -R "<group>/<project>"
```

### 引导式收集（一问一答）

带着**具体切入口**引导，不要甩一个空模板让人填。默认从下面四个问题切入，一次聚焦一条；
用户答完哪个就顺着追问细节，缺字段才追问，不要一次问全部。

四个引导切入口：

1. **阻塞交付效率的问题是什么？**（什么反复拖慢你、让你等/返工）
2. **造成需求延期的原因是什么？**（依赖谁/等什么、方案反复、历史技术债、资源被占……只讲客观事实与模式）
3. **有什么 AI 工具或方法可以提高效率？**（想用但没有、或用着不顺的 AI/agent 能力）
4. **希望得到什么能力/平台/规范支持？**（谁/什么平台/工具/规范来解决）

顺着答案追问，补全这几项（缺才问，能从上下文推断就别追问）：一句话标题、具体描述、发生频率（几乎每次/经常/偶尔）、影响（时间/返工/质量/无法验收…）、涉及产品线、关联需求或 issue（可选）、期望的支持、参与角色（只提出/配合验证/牵头推动）、提交人署名。

一次可收集多条：一条收敛完，问「还有吗」，有就继续下一条。

### 评论格式（遵循 gitlab-issue-sop 进展评论风格）

整理成如下 markdown 一条，**先展示给用户确认，再提交**：

```markdown
### 痛点 / 能力支持 · <一句话标题>

**类型**：痛点 / 能力支持需求
**描述**：<客观事实与场景>
**切入口**：交付效率阻塞 / 需求延期原因 / AI 提效 / 能力支持
**频率**：几乎每次 / 经常 / 偶尔
**影响**：<损失了什么>
**产品线**：<产品线 / 通用 / 不确定>
**关联需求/issue**：<如有>
**期望的支持**：<谁/平台/工具/规范>
**参与角色**：只提出 / 配合验证 / 牵头推动
**提交人**：<署名> · <YYYY-MM-DD>
```

### 提交（作为 issue 评论）

用户确认后，用 glab 追加评论（不改描述）：

```bash
glab issue note <iid> -R <group>/<project> --message "<上面整理好的 markdown>"
```

提交后回读确认已写入（`glab issue view <iid> -R <group>/<project> -c`），把评论链接反馈给用户。

### 执行顺序

1. 确定目标 issue（a 用户给 / b 兜底默认），回读标题让用户确认。
2. 引导式收集：从四个切入口挑一个开场，顺着追问补全字段；讲问题不讲责任。
3. 整理成一条，按评论格式展示，请用户确认（可改）。
4. 提交为评论（`glab issue note`），回读确认，给出评论链接。
5. 问「还有其他要提的吗」，有则回到第 2 步。

## Rules

1. **永远新增 comment，不改 issue 原始描述**。
2. **凭据由 `glab auth` 管理**，不手工读写任何 access token，不外泄凭据。
3. **提交前必须让用户确认整理后的内容**，不擅自提交。
4. 引导中**不问「谁造成的」**——追责属 PIR，不在收集范围。
5. 目标 issue 不确定时**先确认再写**，不猜仓库、不猜 iid。
6. 建**新一期收集 issue** 时委派 `gitlab-issue-sop`（带 assignee + `retro::collection`），本 skill 不自造建 issue 流程。

## Examples

### ✅ Good

```
用户：提个痛点
Agent：好，先确认记到哪个收集单——用当期默认收集 issue 可以吗？（回读标题让用户确认）
      然后引导：先说说最近阻塞你交付效率的问题，或造成需求延期的原因？
用户：模型类需求老是上线后才发现额度不够被迫回滚
Agent：（追问频率/影响/期望支持，整理成规范一条，展示给用户确认）
      确认后 → glab issue note <iid> -R <project> --message "### 痛点 · ..."
      → 回读确认，给出评论链接
```

### ❌ Bad

```
用户：提个痛点
Agent：直接编辑 issue 描述把这条痛点追加进去
# ❌ 违反 SOP：进展/收集内容必须走 comment，不能改原始描述
# ❌ 未确认目标 issue、未让用户确认内容就写入
# ✅ 正确：确认目标 issue → 引导收集 → 用户确认 → glab issue note 追加评论
```
