# retro-prep 信号识别与判定边界

## 业务与证据先行

按业务能力读取目标/承诺、交付、实际使用效果/反馈、差距与有效做法。工程活动只作证据索引。
结论分事实、原因假设、技术债候选、待确认决议、未知；每项带来源、时间、版本/环境及支持范围。

## MR 信号：产生核查问题，不直接定因

| 信号 | 候选核查方向 | 必须排除 / 补齐 |
|---|---|---|
| fix/调整/优化标题占比 | 用户问题在哪些场景反复出现？ | 晋级、回补、独立优化、例行维护；不能把关键词比叫返工率 |
| 同功能多个MR | 一项业务切片经过哪些阶段？ | 主需求/子切片/跨端关系与发布谱系；不能按MR数算需求或成果 |
| 重复标题 | 是否同改动不同分支/环境？ | 差异内容和来源关系；标题相同不证明重复开发 |
| 作者集中度 | 能力支持与交接是否充足？ | 作者不代表全部贡献；需真实阻塞/资源证据，百分比不自动定风险或绩效 |
| 发布后持续修复 | 哪种用户影响或边界尚未闭环？ | 确切部署/首次出现时间、缺陷证据与修复范围；合并后不等于上线后 |
| feat/fix数量关系 | 哪些工作是需求、修复、技术债？ | 分类定义与去重口径；不能推导“没有前进”或需求质量差 |

需要返工率时先定义返工、业务切片单位、分母/窗口及原因证据；缺任一项写不可计算。
仅为定位候选可以披露原始关键词命中数，但必须附非成果/非返工率的边界。

## Issues 与时间线

- 需求、当前缺陷、工程修复、长期欠账、待验收、历史总纲、流程台账分别识别；标签缺失/冲突不补造分类。
- P0/P1/open/blocked只表示台账信号，不能认定为当前线上事故或全部发布阻断。
- 正文、最新实质评论与MR/验收记录按时间/版本对账；不能仅复制正文或机械以最新评论定事实。
- 陈旧计划日期与closed/状态标签矛盾列待校准，不默认是假延期、不自动改状态或关闭。
- 跨仓依赖保留消费方契约与已知交接；无法访问明确coverage缺口，不解释为没有工作。

## 周报

核验authors映射、alias与实际目录，记录可用周次/采集时间，匹配有歧义则停止身份归因。

| 内容 | 允许使用方式 |
|---|---|
| 本人已确认红黄或返工自述 | 和Issue/MR交叉印证；仍需排除不同任务/周期 |
| AI草稿、建议红黄、awaiting review | 待核线索，不写成本人状态、承诺或已确认归因 |
| 跳过个人补充、目录无近期报告 | 记录覆盖缺口；不推断没工作或不配合 |
| 工作方法摩擦片段 | 注明生成/确认状态、场景与测量口径；不外推总工时 |

## 技术债确认

候选需同时描述长期结构/能力欠账、当前存在证据、持续维护/交付/可靠性成本，以及偿还方案与代价。
是否为债、当前是否仍存在、优先级和处理决议由责任主体确认；会前只能输出候选，不能补写会议决定。

- 当前bug：先定义复现、修复与验收；如背后有长期欠账，另列债候选并关联，不重复算工作量。
- 新需求：属于新增能力，不因尚未实现就叫债；长期兼容/演进成本另证。
- 待验收：补实际场景/证据，不因未通过或未执行就叫债。
- 台账/owner/计划混乱：通常是流程问题；没有技术能力欠账证据不改称技术债。
- open技术类Issue或旧设计要求：可能已交付/被替代，必须核验当前实现与回执后确认。

## 原因假设分类

A资源/交接、B跨团队依赖、C技术方案/模型、D历史技术债、E流程、F需求跨度/边界。
分类只帮助组织问题；不强制每类有问题，不用作者比例、fix数量或标签推导原因。每个假设写支持证据、反证/未知和下一步核验。
讨论结束另记经确认原因与技术债决议，不用会前假设冒充结论。
