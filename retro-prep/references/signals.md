# retro-prep 信号识别与归因分类

## MR 信号（用 glab 拉 merged MR 后本地分析）

| 信号 | 怎么算 | 说明什么 |
|-|-|-|
| fix/调整占比高 | 标题匹配 `fix/hotfix/修复/回滚/调整/优化` 的比例 | 返工重、需求边界不清 |
| 功能关键词聚类 | 按 paywall/识别/推送/订阅 等词分组计数 | 哪个功能被反复修改 |
| 重复标题 | 去掉 `[staging]/[master]` 前缀后同名 ≥2 | 同一改动双主线/双环境各做一遍 |
| 作者集中度 | 单人 MR 占比 | 关键人资源风险（>70% 是红灯） |
| 上线后持续 fix | 某功能 feat 早、fix 延续到近期 | 需求边界上线后才被现实补全 |
| feat vs fix 比 | 窗口内 feat 数 vs fix 数 | fix 远多于 feat = 在填坑不是在前进 |

## issue 信号（拉 open+closed 全量）

- **不在 Base 看板的修复**（最易遗漏）：`type::bug`、标题含 `线上/500/崩溃/hotfix/error_code`、`[ops]/[infra]/nacos/rds/cloudfront/dns`、`refactor/技术债`。这些工程/运维/线上修复直接开在 GitLab，产品 Base 里没有 —— 必须单列成节，纳入交付全貌。
- 线上 P0/P1 bug：直接影响业务指标的（如「曝光缺失命中流失人群」「AB 曝光漏透传」）优先点出。
- 跨仓 bug：同一业务链路的 bug 可能在 customer-care / marketing-cms / gateway 等仓，别只看主仓。

## 周报信号（weekly-reports/software 仓）

- `authors.json`：研发中文名 → 周报用户名（如 房超=cfang、梅华锋=hmei）；`author_aliases.json` 处理别名。
- 读 `reports/<user>/<ISO-week>.html`，看「个人补充」段：
  - 状态 **红**：受阻/高风险/时间紧 —— 重点。
  - 状态 **黄**：待闭环/待重测。
  - 自述关键词：`返工/重做/重测/方向调整/按 X 方案重改/二次修复/扩大修复范围` —— 返工的一手证据，与 MR/issue 交叉印证。

## 归因分类（把返工/延期归到可动的模式）

固定六类，便于跨业务线横向对比：

| 类别 | 典型表现 |
|-|-|
| A 资源/人力冲突与错配 | 关键人（算法/后端/资深/CR）被占、责任人标错、离职交接、新人不熟、单人扛整条线 |
| B 跨需求/跨团队依赖 | 前置大改造、跨仓依赖、等产测/文案/后端发版 |
| C 技术方案 / 模型·LLM | 模型慢、额度/成本、连带回滚 |
| D 历史技术债与返工 | 历史 bug 依赖他人修、完成后跑不通需二次开发 |
| E 流程问题 | CR 过不了、评审延期、等测试资源、staging/master 分叉、线上配置事故 |
| F 需求本身跨度大 / 边界不清 | 大需求缺里程碑、需求边界上线后才补全（多语言/多机型/多区域/匿名/真机） |

每个归因项配一个**可动的抓手**（如：需求立项加边界清单评审、关键人护航+节点错峰、能力抽出独立可测、校准 Base 台账等），写进「归因与抓手」表。

## 常见陷阱（务必规避）

1. 把「是否延期」formula 或预计完成日直接当结论 → 先核对是不是数据陈旧的假延期。
2. 只看产品 Base → 漏掉大量工程 issue，低估工作量。
3. 只看主仓 → 漏掉跨仓交付。
4. 不标出处 → 结论不可核对、会上被质疑就塌。
5. 把复盘写成追责 → 下次没人说真话。
