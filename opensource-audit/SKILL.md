# 开源审查 Skill

## Description

引导 AI Agent 完成内部项目开源前的审查与脱敏全流程。通过系统化的扫描、分类、脱敏和验证，确保零敏感信息泄露。

适用场景：准备将内部项目公开到 GitHub/GitLab 等开源平台前的安全审查。

## 触发条件

以下任一说法触发本 Skill：

- "开源审查" / "准备开源"
- "开源脱敏" / "帮我脱敏这个项目"
- "sanitize for open source" / "audit for open sourcing"
- "这个项目可以开源吗" / "检查一下能不能公开"
- 在技术博客、Stack Overflow、社交媒体、会议演讲等公开渠道发布包含内部代码的内容（等同于开源）

## 审查流程

**严格按顺序执行，不得跳过任何阶段。** 每个阶段的发现必须提交给用户确认后再进入下一阶段。

---

### 阶段 1：资产盘点

**目标**：理解项目全貌，对每个文件/模块分类。

1. 列出项目所有文件（排除 `.git/` 和构建产物）
2. 阅读关键文件，理解项目的目的、架构和依赖
3. 将每个文件/模块分为三类：

| 分类 | 含义 | 处理方式 |
|------|------|---------|
| **CLEAN** | 可直接开源 | 无需修改 |
| **NEEDS_SCRUB** | 包含内部信息，但概念/方法论通用 | 脱敏后开源 |
| **INTERNAL_ONLY** | 太公司化，无法有意义地脱敏 | 删除或排除 |

4. 将分类表提交给用户确认，等待批准后再继续。

**输出格式**：

```
| 文件/模块 | 分类 | 原因 |
|-----------|------|------|
| src/core.py | CLEAN | 纯算法，无内部引用 |
| config/deploy.yaml | NEEDS_SCRUB | 包含内部集群端点 |
| scripts/internal-sync.sh | INTERNAL_ONLY | 仅同步内部服务 |
```

---

### 阶段 2：安全扫描

**目标**：找出代码库中所有敏感信息。

对以下 13 个类别逐一扫描。搜索所有文件（不只是代码——包括文档、配置、注释）。

#### 2.1 内部域名和 URL

```bash
# 替换为你公司实际的内部域名
grep -rn "\.your-company\.com\|\.internal\.com" . --include='*' | grep -v ".git/"
```

查找：内部服务 URL、API 端点、CDN 域名、管理后台、监控面板。

#### 2.2 云账户标识

```bash
# AWS 12 位账户 ID
grep -rn "[0-9]\{12\}" . --include='*' | grep -v ".git/"
```

查找：AWS 账户 ID、GCP 项目 ID、腾讯云账户 ID、Azure 订阅 ID。

#### 2.3 暴露部署拓扑的云区域

查找硬编码的云区域（如 `us-east-1`、`cn-north-1`、`ap-southeast-1`），这些会暴露公司的部署布局。

**需要判断**：文档中的通用示例区域可以接受；实际部署配置中的区域必须参数化。

#### 2.4 公司和员工名称

搜索公司名、创始人名、员工名和内部联系人（任何语言）。

#### 2.5 产品和品牌名称

搜索内部或专有的产品名、品牌名、代号和商标。

#### 2.6 业务领域术语

搜索暴露公司行业或产品领域的业务特定术语（当项目本身应该是领域无关的通用工具时）。例如：
- 硬件/IoT 术语（如果项目应该通用）
- 嵌入到通用工具中的行业术语
- 内部功能名或项目代号

#### 2.7 支付和金融平台

搜索对特定支付处理商、计费系统或金融服务商的引用（这些是公司的机密选型）。

#### 2.8 内部工具和平台

搜索对仅内部使用的工具和平台的引用：功能开关系统、分析/埋点平台、内部面板、CI/CD 特有引用、内部包仓库。

#### 2.9 数据基础设施

搜索：内部数仓表名、数据管道配置、BI 面板引用、ETL 任务名。

#### 2.10 产品标识符

搜索市场产品 ID（如 Amazon ASIN `B0[A-Z0-9]{8}`）、内部 SKU、产品代号。

#### 2.11 IP 地址和网段

```bash
grep -rn "[0-9]\{1,3\}\.[0-9]\{1,3\}\.[0-9]\{1,3\}\.[0-9]\{1,3\}" . | grep -v ".git/\|0\.0\.0\.0\|127\.0\.0\.1"
```

查找：内部网络地址、VPN 端点、堡垒机 IP。

#### 2.12 内部仓库路径

搜索内部 Git 仓库路径、组织名或代码组织结构。

#### 2.13 人员姓名和联系方式

搜索作者名、邮箱（特别是内部域名）、即时通讯 ID 等 PII。

**阶段 2 输出格式**：

```
## 安全扫描结果

### 内部域名（X 处发现）
- file.py:42: `api.internal.example.com/v1/devices`
- config.yaml:15: `cdn.internal.example.com`

### 云账户 ID（X 处发现）
- deploy.tf:8: `account_id = "123456789012"`

...（继续所有类别）

### 总结
发现总数：N
受影响文件：M
```

### 阶段 3：脱敏处理

**目标**：将所有敏感信息替换为安全的通用替代。

| 发现类型 | 替换策略 | 示例 |
|---------|---------|------|
| 内部 URL/域名 | `example.com` | `api.example.com` |
| 云账户 ID | `<account-id>` | `account_id = "<account-id>"` |
| 云区域 | `<region>` 或 `<your-region>` | `region = "<your-region>"` |
| 公司名称 | 通用描述或 `<your-company>` | |
| 员工姓名 | 删除或替换为 `<author>` | |
| 产品名称 | 通用等价物 | `智能摄像头` → `IoT 设备` |
| 业务术语 | 通用等价物 | 领域特定 → 领域无关 |
| 支付平台 | `支付平台` 或 `<payment-provider>` | |
| 内部工具 | 通用描述 | `功能开关服务` |
| 数据设施 | `<table-name>`、`<dashboard-id>` | |
| 产品 ID | `<product-id>` | |
| IP 地址 | `<ip-address>` | |
| 内部仓库 | `your-org/your-repo` | |

**规则**：

1. **修改前先提交给用户确认。** 展示 diff 风格的变更预览。
2. **替换，不要删除。** 直接删除会破坏上下文。使用有意义的占位符。
3. **保持功能完整。** 脱敏后的代码/配置仍然应该语法正确、逻辑连贯。
4. **删除 INTERNAL_ONLY 文件**（在用户确认后）。

### 阶段 4：模板化改造

**目标**：将包含大量基础设施细节的文件转为可配置模板，让用户能适配自己的环境。

当文件包含有价值的方法论但与特定基础设施紧密耦合时：

1. **保留方法论、模式和规则** — 这才是真正的价值
2. **将所有具体基础设施细节提取到 `## Setup` 配置段**
3. **使用清晰的占位符变量**，让用户在初始使用时填入

**示例**：

改造前（内部版）：
```yaml
cluster: prod-sg-eks-01
endpoint: https://monitoring.internal.example.com
alert_channel: "#ops-alerts"
```

改造后（模板版）：
```yaml
## Setup
# 使用前请填入你的基础设施信息：
cluster: <your-cluster-name>
endpoint: <your-monitoring-endpoint>
alert_channel: "<your-alert-channel>"
```

**判断标准**：方法论有复用价值 → 模板化；纯内部流程无通用价值 → 删除。

### 阶段 5：开源标准检查

**目标**：确保项目符合开源社区标准。

逐项检查，缺失的文件按需创建：

- [ ] **README.md** — 清晰的项目描述、安装、使用和示例。双语项目需有语言切换器。
- [ ] **LICENSE** — 推荐 Apache-2.0。必须是标准、未修改的许可文本。
- [ ] **.gitignore** — 适合项目技术栈。排除构建产物、IDE 文件和环境文件。
- [ ] **CONTRIBUTING.md** — 如何贡献、代码规范、PR 流程。
- [ ] **CODE_OF_CONDUCT.md** — Contributor Covenant 或等效文件。
- [ ] **SECURITY.md** — 如何报告安全漏洞（不通过公开 issue）。
- [ ] **无超大文件** — 规范文档不超过合理限制（如 500 行）。
- [ ] **无断开引用** — 所有内部链接和文件引用都能正确解析。
- [ ] **无残留内部引用** — 再次检查 README 和文档中没有引用内部系统。

**如果是 Agent Skills 仓库**：
- [ ] 所有文件遵循 Agent Skills Specification 格式
- [ ] 无 SKILL.md 超过 500 行
- [ ] frontmatter（`name`、`description`）存在且准确

### 阶段 6：侵权风险审查

**目标**：确保项目不侵犯第三方知识产权。

#### 6.1 License 兼容性

扫描所有依赖的许可证，确认与项目许可证（通常为 Apache-2.0）兼容：

```bash
# 检查依赖的 license（根据技术栈选择）
# Node.js
npx license-checker --summary 2>/dev/null
# Python
pip-licenses --format=table 2>/dev/null
# Go
go-licenses csv ./... 2>/dev/null
```

**不兼容的常见 License**：

| 项目 License | 不兼容的依赖 License | 风险 |
|-------------|-------------------|------|
| Apache-2.0 | GPL-2.0（不含 "or later"） | 高 — 传染性，不可混用 |
| Apache-2.0 | AGPL-3.0 | 高 — 网络传染性 |
| Apache-2.0 | SSPL | 高 — 不是 OSI 认证开源 |
| Apache-2.0 | CC-BY-NC | 中 — 禁止商用 |

**兼容的 License**：MIT、BSD-2/3、ISC、Unlicense、CC0

#### 6.2 第三方代码复制检测

```bash
# 搜索代码中的 copyright header
grep -rn "Copyright\|All rights reserved\|Licensed under\|SPDX-License" . --include='*' | grep -v ".git/\|LICENSE\|node_modules\|vendor"
```

检查：
- 是否有从其他开源项目复制的代码段（尤其是带 copyright header 的）
- 复制的代码 license 是否与项目兼容
- 是否缺少必要的归属声明（Attribution）

如果发现第三方代码：
- 兼容 license → 在 `THIRD_PARTY_NOTICES.md` 中注明归属
- 不兼容 license → 必须重写或删除

#### 6.3 第三方文档/内容引用

检查文档中是否有：
- 大段引用他人文章或博客（可能侵犯版权）
- 复制的图表、架构图（需注明出处）
- 翻译的外文内容（翻译也受版权保护）

#### 6.4 商标风险

检查项目名、模块名、Skill 名：
- 是否与知名产品/公司商标冲突
- 是否使用了受保护的品牌名称
- README 中提及第三方产品时是否加了 TM/® 标记（通常不需要，但不能暗示官方关联）

#### 6.5 专利风险标记

提醒用户关注以下领域（AI 不做法律判断，仅标记）：
- 涉及特定算法实现（如视频编解码、压缩算法、加密方法）
- 涉及 UI 交互专利（如特定手势、导航模式）
- 建议用户在发布前咨询法律顾问

### 阶段 7：合规与出口管制

**目标**：确保项目符合适用法律法规。

#### 7.1 加密算法出口管制

```bash
# 搜索加密算法实现
grep -rn "AES\|RSA\|DES\|Blowfish\|ChaCha\|Salsa20\|ECDSA\|Ed25519\|SHA-256\|HMAC" . --include='*' | grep -v ".git/\|node_modules\|vendor\|LICENSE"
```

如果项目包含加密实现（不是调用标准库，而是自行实现）：
- 美国出口管制（EAR）可能适用
- 需要在 README 中声明加密功能
- 某些开源平台（如 GitHub）会要求填写出口管制分类

**注意**：调用标准库（如 OpenSSL、crypto）通常不构成出口管制风险，但自行实现加密算法需要注意。

#### 7.2 数据隐私合规

检查代码是否：
- 收集或处理个人数据（PII）— 姓名、邮箱、手机号、设备 ID
- 有用户追踪/分析功能
- 涉及跨境数据传输

如有以上情况，建议在 README 中增加 Privacy 章节说明。

#### 7.3 地域限制逻辑

```bash
# 搜索国家/地域限制
grep -rn "sanction\|embargo\|blacklist\|block.*country\|restricted.*region" . --include='*' | grep -v ".git/"
```

检查是否有针对特定国家的限制逻辑（制裁国家列表、IP 地理位置限制等）。这类逻辑在开源项目中可能引发争议。

---

### 阶段 8：代码质量门禁

**目标**：确保开源代码的质量达到社区标准。

#### 8.1 调试代码残留

```bash
grep -rn "console\.log\|print(\|debugger\|pdb\.set_trace\|binding\.pry\|System\.out\.print\|fmt\.Print" . --include='*' | grep -v ".git/\|node_modules\|test\|spec\|vendor"
```

区分：生产代码中的调试语句（必须清理） vs 测试代码中的输出（可保留）。

#### 8.2 TODO/FIXME/HACK 标记

```bash
grep -rn "TODO\|FIXME\|HACK\|XXX\|WORKAROUND" . --include='*' | grep -v ".git/\|node_modules\|vendor"
```

对每个标记判断：
- 已完成但未清理 → 删除标记
- 已知问题但可接受 → 转为 GitHub Issue
- 技术债但不影响功能 → 保留并在 README 中说明

#### 8.3 硬编码配置

检查硬编码的：
- 端口号（应可配置）
- 超时值（应可配置）
- 文件路径（应相对路径或可配置）
- 魔法数字（应有常量定义和注释）

#### 8.4 死代码

检查：
- 大段被注释掉的代码（应删除，git 历史有记录）
- 未引用的函数/类/文件
- 永远为 false 的条件分支

#### 8.5 敏感注释

```bash
grep -rn "ugly\|stupid\|wtf\|shit\|fuck\|hate\|suck\|crap\|damn" . --include='*' -i | grep -v ".git/\|node_modules\|vendor"
```

检查注释中的：
- 不专业语言（脏话、抱怨）
- 针对个人的评论
- 内部讨论（如"老板要求"、"赶工期"）
- 任何不适合公开的观点

---

### 阶段 9：最终验证

**目标**：绝对确认所有维度均通过审查。

最后一次运行完整扫描：

```bash
# 基于阶段 2 发现的所有模式构造 grep
grep -rn \
  "PATTERN_1\|PATTERN_2\|PATTERN_3" \
  . --include='*' | grep -v ".git/"
```

从所有审查阶段的发现动态构造扫描。覆盖：

**信息安全（阶段 2）**：内部域名、公司/品牌名、产品名、业务术语、内部工具名、产品 ID

**侵权风险（阶段 6）**：未归属的第三方 copyright、不兼容 license 的依赖

**合规（阶段 7）**：自行实现的加密算法、PII 收集逻辑、地域限制代码

**代码质量（阶段 8）**：调试代码残留、不专业注释、硬编码配置

**结果必须为零匹配**（排除通用上下文中的明确误报，如标准许可证文件中出现的常见词汇）。

如果仍有匹配：
1. 提交给用户
2. 修复每一处
3. 重新扫描
4. 重复直到干净

**只有最终扫描通过后，项目才能被声明为可开源。**

---

## 规则

1. **绝不跳过最终验证扫描。** 这是最后一道防线。
2. **修改前必须提交给用户确认。** 用户必须批准后才能修改。
3. **展示修改内容和原因。** 每批修改都要说清楚改了什么、为什么改。
4. **有价值的方法论优先模板化，不要删除。**
5. **用有意义的等价替换。** 业务特定示例应变为通用等价物，保持文档的教学价值。
6. **本 Skill 文件本身不得包含任何公司特定信息。** 必须完全通用、可安全分发。
7. **开源前必须完成审批。** 任何代码开源须先提交 [代码开源审批流](https://applink.feishu.cn/T95dQntGpJxG)，审批通过后方可执行后续流程。在公开渠道（博客、Stack Overflow、社交媒体、会议）发布内部代码等同于开源，须走同一审批流程。

## 社会责任规则

编写或脱敏开源项目文档时：

- **不使用替代/裁员相关语言。** 开源工具增强人的能力，不替代人。
- **正面表述知识价值**：专业知识沉淀 + AI 放大，不是替代专业能力。
- **不使用监控语言。** 不将监控工具表述为考勤或员工监视。
- **尊重贡献者。** 所有文档应将贡献者视为值得尊重的专业人员。

## 常见问题

| 问题 | 解决方案 |
|------|---------|
| Grep 发现太多误报 | 缩小模式范围；排除已知安全目录；使用文件类型过滤 |
| 文件在 NEEDS_SCRUB 和 INTERNAL_ONLY 之间难以判断 | 问用户——有疑问时展示权衡取舍 |
| 脱敏后功能损坏 | 确保占位符语法正确；添加 Setup 说明 |
| 最终扫描发现新问题 | 不走捷径——修复并重新扫描 |
| 项目 git 历史中有敏感数据 | 警告用户：脱敏文件不会清理 git 历史。建议用 `git filter-repo` 或创建全新仓库 |
