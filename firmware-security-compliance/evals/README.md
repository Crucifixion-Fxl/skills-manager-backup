# 固件安全审查行为评测

`evals.json` 使用仓库 `schema_version: 1` 与版本化 contract，包含 17 个离线合成案例、76 条断言。每例直接内嵌所需源码/配置/记录片段，并提供对照实现，不依赖真实项目、凭据、设备或网络。

验证目标：每次产品固件提交都按目标版本核验应具备的安全基线，即使本次 diff 未触碰安全文件，也要报告已证实的历史缺失与未核验项；同时正确区分版本与依赖，承认已完成的局部措施，避免把随机 token、ADB 主机认证、CORS、SHA-256、历史提交或 CI 配置扩大解释。

保留的案例 1–10 覆盖版本、会话、凭据缓存、协议/授权、OTA 与流程边界；追加的案例 11–17 覆盖缺失实现与新增实现的对照、缺证据时不能判定基线通过，以及受限 CI 与已授权本地审查的取证边界：

| 案例 | 基线缺口与对照 |
|------|----------------|
| 11 | 无关业务 diff 仍须追到 BSP、UART 共用凭据/一机一密、ADB 默认与权限策略、RNDIS HTTP；对照实际构建中完成的措施 |
| 12 | 产品要求禁用 USB/RNDIS HTTP 时，已有认证仍不满足禁用要求；对照移除构建/启动路径 |
| 13 | 只有未知密码哈希不能证明弱口令或共用口令，也不能判凭据基线通过；对照新增个性化、发行与验证证据 |
| 14 | 完全缺少实际载荷摘要检查；对照将已认证摘要与真正写入的内容绑定 |
| 15 | 凭据/请求正文进入持久日志和诊断导出；对照从日志入口实施字段白名单 |
| 16 | 恢复出厂擦除不全、断电恢复复活凭据、已认证接口无路径边界；对照撤销/恢复协议和受限路径操作 |
| 17 | 受限 CI 的 diff 与路径状态不足以证明未修改的安全实现；保留全基线待核验与 diff 已确认问题，对照已授权本地完整证据 |

产品基线状态与 MR 合并结论必须分别评分：基线未满足/未核验要如实保留，MR 仍沿现有存量分级和 RL-06 例外判断，不把所有历史缺口一律改为阻断。合成案例不能用于证明任何真实旧版本曾存在或已修复相同问题，截图也不能替代目标版本证据。

## 结构验证

在仓库根目录运行：

```bash
uv run python scripts/validate.py --skill skills/firmware-security-compliance
```

这条命令检查 skill 和评测契约结构，不运行模型行为评测、固件测试或实机验证。JSON 解析成功及结构检查通过不能表述为“17 个案例全部通过”或“76 条断言全部通过”。

## 行为评测

每个案例使用新会话加载待测 skill、该例 `setup` 和 `prompt`，让模型仅依据内嵌冻结证据作只读分析，再逐条检查 `assertions`。`expected_output` 与 `assertions` 供评测者使用，不放入被测模型的输入。不得联网、接入设备、运行伪代码、构造利用或修改外部系统。

比较修改前后版本时，分别记录实际使用的 skill 提交、模型/配置、输出和逐条评分。未执行的案例标为未运行；只有实际输出满足所有断言才能记为该例通过。结果应保存在评测运行目录，不把假定的通过结果预写进本套件。
