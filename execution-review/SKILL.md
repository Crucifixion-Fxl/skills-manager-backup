# 执行复查 (Execution Review)

## Description

任务执行出现预期偏差时的结构化复查。核心问题：

> **为什么我以为能一次做对的事情，实际上反复了 N 次？**

每次返工都有一个隐含的错误假设。找到这个假设，比修复具体 bug 更有价值。

### 何时触发

- 用户反复纠正后任务终于完成时
- 一个任务中同类问题反复出现（修了 A 又冒出 B，B 和 A 是同一类）
- 实际耗时 > 预期耗时的 2 倍以上
- 方案中途推翻重来
- 用户说"怎么又是这种问题"、"为什么这么久"

### 不适用

- 任务顺利完成，无偏差
- 偏差来自需求变更（那是需求管理问题，不是执行问题）

## Rules

1. **触发即执行**：满足触发条件时必须执行，不能跳过
2. **事实优先**：从对话记录、git log、debug log 中提取事实，不依赖记忆
3. **不美化**："我当时以为"要写真实想法，不是事后合理化
4. **不遗漏**：小意外也要列出，小意外往往暴露大假设
5. **改进必须可执行**：输出具体动作，不能是"下次注意"
6. **改进必须关联假设**：每个改进关联到具体的假设编号
7. **只分析自己可控的部分**：不甩锅，外因分析不产生改进

## 执行步骤

### Phase 1: 还原事实

列出所有"意外"——每一个让你停下来、回头、改方向的时刻。

```markdown
| # | 意外事件 | 我当时以为 | 实际情况 | 处理方式 | 浪费时间 |
```

**关键列是"我当时以为"**——这是错误假设的直接证据。

### Phase 2: 归因——错误假设分类

将每个意外归入以下 4 类错误假设：

| 假设类型 | 含义 | 例子 |
|----------|------|------|
| **认知盲区** | 不知道自己不知道 | "我不知道 Android GATT 操作必须串行化" |
| **过度信任** | 知道但假设它没问题 | "仿真跑通了所以真机应该也行" |
| **简化假设** | 知道有复杂性但低估了 | "跨线程回调应该不难处理" |
| **遗漏检查** | 知道该检查但忘了/跳过了 | "忘了检查 JNI 函数名" |

统计：
```markdown
| 假设类型 | 次数 | 占比 |
```

### Phase 3: 找模式

**Q1: 同一类假设是否反复出现？**
> 如果"过度信任"占了 60%，说明系统性地高估了上一阶段的验证覆盖度。

**Q2: 这些错误假设在什么时候就可以被打破？**

| 时刻 | 含义 |
|------|------|
| **规划时** | 开始做之前多想一步就能发现 |
| **编码时** | 写代码时检查一下就能发现 |
| **静态审查时** | 不运行代码，人工比对就能发现 |
| **自动化测试时** | 跑测试能发现 |
| **手动测试时** | 必须实际运行/操作才能发现 |

计算 **可提前发现率** = (规划+编码+静态审查+自动化测试) / 总数

**Q3: 有没有一个上游动作，做了就能同时消除多个意外？**

### Phase 4: 输出改进

```markdown
### 立即（下次同类任务前必须做）
- [ ] <具体动作>  ← 消除假设 #X, #Y

### 工具化（本迭代内）
- [ ] <自动化检查/脚本/CI job>  ← 消除假设类型 <类型>

### 认知更新（写入知识库）
- [ ] <新认知>  ← 填补认知盲区 #Z
```

约束：
- 每个改进关联具体假设编号
- "立即"类不超过 5 条
- 能消除 3+ 个假设的改进优先级最高

### Phase 5: 一句话总结

> **因为我假设了 [X]，但实际上 [Y]，导致 [Z 个返工]。下次通过 [具体动作] 可以提前发现。**

## Examples

### ❌ Bad — 没有分析假设，只列问题

```markdown
## 复盘
1. JNI 函数名错了 → 改了
2. UUID 写错了 → 改了
3. 回调线程不对 → 改了
总结：下次注意细节。
```

问题：没有分析"我当时以为什么"，"下次注意"不可执行，同类问题一定重现。

### ✅ Good — 分析错误假设，输出可执行改进

```markdown
## 复盘：Flutter BLE 集成

> 因为假设了"仿真通过等于集成通过"，但实际上仿真不覆盖构建/线程/数据层，
> 导致 20 次返工。下次通过集成前 10 分钟常量比对可消除 55% 的问题。

## 意外事件清单
| # | 意外 | 我当时以为 | 实际情况 | 浪费时间 |
|---|------|-----------|---------|---------|
| 1 | JNI 函数名不匹配 | 包名改了 JNI 会自动同步 | JNI 是手写的 C 函数名 | 30min |
| 2 | BLE UUID 错误 | FFF0/FFF1 是标准 UUID | 固件用的是自定义 6566/7777 | 45min |
| 3 | FFI 跨线程崩溃 | Pointer.fromFunction 能跨线程 | 只能在主线程用 | 60min |

## 错误假设分类
| 假设类型 | 次数 | 占比 |
|----------|------|------|
| 过度信任 | 8 | 40% |
| 遗漏检查 | 6 | 30% |
| 认知盲区 | 4 | 20% |
| 简化假设 | 2 | 10% |
可提前发现率: 65%

## 改进措施
### 立即
- [ ] 集成前比对常量表（UUID/函数名/库名） ← 消除 #1, #2, #4, #7
### 工具化
- [ ] CI 加 grep 检查 JNI 函数名与 Kotlin 包名一致性 ← 消除"遗漏检查"类
### 认知更新
- [ ] Dart FFI 跨线程必须用 NativeCallable.listener ← 填补 #3
```

## 反模式

| 反模式 | 为什么有害 | 正确做法 |
|--------|----------|----------|
| "下次注意" | 记忆不可靠，同样的"注意"会忘 | 输出 checklist 或自动化检查 |
| "这个很特殊，不会再遇到" | 具体 bug 不会重现，但同类假设会 | 归类到假设类型，同类型一定会再犯 |
| 只分析最大的问题 | 小问题的假设类型和大问题可能相同 | 全部列出再归类 |
| 复盘变成甩锅 | 外因分析不产生改进 | 只分析自己可控的部分 |
| 文档写完就丢 | 改进没执行等于没复盘 | 改进变成 checklist/skill/CI job |

## 输出模板

```markdown
# 复盘：[一句话标题]

> 日期 / 任务范围
> 一句话总结：因为假设了 [X]，但实际 [Y]，导致 [N] 次返工。

## 意外事件清单
| # | 意外 | 我当时以为 | 实际情况 | 浪费时间 |

## 错误假设分类
| 假设类型 | 次数 | 占比 |
可提前发现率: X%

## 模式分析
- 高频假设类型: ...
- 上游消除动作: ...

## 改进措施
### 立即
### 工具化
### 认知更新
```
