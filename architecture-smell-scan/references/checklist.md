# 架构坏味道速查（AI 摘要）

> 正本：`public/dev-standards/architecture/architecture-smells.html`。本文件是给 AI 的摘要，改规则先改正本再同步这里。编号永久不变：M = 单仓内，X = 服务间。分组与正本一致：A 对照正本 · B 结构问题 · C 演化信号 · D 服务间 · E 命名。

脚本给出的是**候选**（超过怀疑线），AI 复核后才上报：核证据 → 排误报 → 排序 → 合并同根因 → 写第一步。

## 尺子（Balanced Coupling）——排序用，不是上报门槛

| 维度 | 低 | 高 |
|---|---|---|
| 强度 | 只经公开接口 / ports / 契约 | 伸进对方内部（import 对方 repository、内部包、私有结构） |
| 距离 | 同一模块内部 | 跨层、跨 Component、跨仓、跨服务 |
| 易变性 | 被依赖方几乎不改 | 被依赖方近期天天改（看 `modules[].churn`） |

- A 组证据成立就报，不因「强度低」删掉。
- 尺子用于：排优先级；M07 / M08 降噪（两边都几乎不改的降级）；排除 M02 误报（经公开接口的调用）。
- 没有依赖边的编号（M09、M11 隐性耦合、M12、M14、M17、M18、M19）不适用尺子。

## B · 结构问题

| 编号 | 名称 | 脚本候选条件 | 复核要点 / 别误报 |
|---|---|---|---|
| M06 | 模块循环依赖 | 强连通分量 ≥ 2 个模块 | 找环里「最不该存在」的那条边（常是底座 → 业务、下层 → 上层、契约类型头放错模块）；大环用贪心拆边找第一步 |
| M07 | 不稳定依赖 | I(被依赖) − I(依赖方) ≥ 0.2，I = 出度 ÷（入度 + 出度） | 两边都几乎不改 → 降级；常与 M04 同根因 |
| M08 | 枢纽模块 | 入度 ≥ 3 且出度 ≥ 5 | 出度常来自放错地方的装配代码 |
| M09 | 上帝模块 | 占已归入模块有效代码 > 30%，且模块 ≥ 4 个 | 仓本就围绕它建且内部清晰 → 写忽略名单 |
| M10 | 能力分散 | 无脚本候选；AI 按概念比对包名 / 类型名 | 刻意的防腐层、各模块的 DTO 转换 |
| M17 | 重复代码 | 模块重复率 ≥ 5%（合并重叠区间后的重复行 ÷ 物理行），或两模块间重复 ≥ 50 行（jscpd ≥ 10 行且 ≥ 70 token） | 跨模块优先；生成代码、测试数据、刻意独立的适配代码不算；S07 管 MR 新引入的重复 |
| M18 | 超长文件 | 单个文件有效代码 ≥ 1000 行（去掉空行和注释；测试、生成代码、未归入模块的文件不计）；指纹 = `编号||文件路径`（不含模块，调模块地图不影响对比） | 生成物、协议 / 寄存器表、内嵌数据表不算；看文件里是否装着几块职责（按 include、函数前缀分块）——是就给出拆成哪几个文件、各归哪个模块；和 M19 叠在同一文件 = 热点文件；S05 管 MR 里的过大的类 |

## C · 演化信号

| 编号 | 名称 | 脚本候选条件 | 复核要点 |
|---|---|---|---|
| M11 | 模块变更耦合 | 共改 ≥ 5 次且耦合度 ≥ 50%（共改 ÷ 两者中改得少的一方）；无依赖关系 = 隐性耦合 | 契约 / 生成代码、客户端库与其守护进程的协议同步；> 50 文件的批量提交已排除 |
| M12 | 模块缺陷热点 | fix 类提交 ≥ 5 次，占比 ≥ 40%，且比全仓 fix 基线（`summary.repo_fix_ratio`）高 10 个百分点以上 | 放大镜：和其他编号叠在同一模块时优先；按下方「M12 / M19 复核要点」过一遍；证据是 fix 提交的 sha + 标题 |
| M19 | 文件缺陷热点 | 改到该文件的 fix 提交 ≥ 10 次（只算现存、已归入模块的代码文件；不看占比，占比和全仓基线只作参考）；指纹 = `编号||文件路径`（不含模块，调模块地图不影响对比） | 和 M18 叠在同一文件 = 热点文件，最先修；和所在模块的 M12 / M08 同根因时合并；按下方「M12 / M19 复核要点」过一遍；证据是最近 5 次 fix 的 sha + 标题 |

### M12 / M19 复核要点

脚本只数 fix 次数；AI 用 `raw.json` 的 `commits`（日期、标题、文件）和 `git -C "$REPO" show --stat --end-of-options <sha>`（只读；sha 只能含 0-9a-f，证据里的 10 位短 sha 可直接用，否则不执行）看清是什么样的 fix：

1. **清告警的不算**：标题是清 sonar / quality gate / lint / clang-tidy / 编译告警的 fix 不算修 bug，占多数时降级或不报。
2. **集中爆发 ≠ 慢性**：fix 集中在一两天或同一个 MR 里 → 一次爆发，不上主榜；分散在很多天的才是反复修。同一个 MR：`git -C "$REPO" log --merges --ancestry-path --end-of-options <sha>..HEAD` 最早的那条合并提交，或查 GitLab MR。
3. **接线热点 ≠ 缺陷源头**：次数多、每次只改几行 → 别处修 bug 顺带改接线（入口 main 之类），和所在模块的耦合 / 环合并，第一步写拆文件、改注册表；每次改动量大的才是缺陷源头。
4. **同一机制修 ≥ 3 次 → 设计复盘**：第一步写「做一次设计复盘」，不写「再修一次」。
5. **救火状态与并发**：fix 远多于 feat 的模块标「救火状态」；fix 标题多是 race / harden / guard 的，归到并发 / 状态机问题，和 M10 一起看。

另外：cherry-pick 重复的 fix 只算一次（脚本不去重，复核时扣除）；子模块指针变更（按 `.gitmodules` 里的路径数 `commits`）单独计数，写进报告概况。

## E · 命名（只看模块 / Component / 公开接口 / 领域词）

| 编号 | 名称 | 脚本候选条件 | 规范依据 | 复核要点 / 别误报 |
|---|---|---|---|---|
| M14 | 模块名不表达职责 | 模块名或目录名在空洞名清单（common / util / base / core / manager / shared …），`canonical: true` 的不报 | 命名规范总纲「名字要能体现定位」；app-layering 把 Foundation 伞名判为「与 base / common 同病：太泛」；没登记的缩写不存在（命名规范 §1.1） | 读内容判断名实是否相符；未登记的缩写由 AI 判断；符合规范的 util、Go 的 internal / cmd 不算；M16 优先于 M14 |
| M15 | 一物多名 | 无脚本候选；AI 聚类各模块公开接口的类型名 / 包名 | 命名规范「一物多名」；统一语言（domain-model.md） | 限界上下文之间有文档映射的不同叫法 |
| M16 | 名字与正本不一致 | 无脚本候选；AI 对照 | App 层名 ADR-0006、固件层名 ADR-0005；「仓名 = System 名」；catalog 的 source-location 指向的目录存在且与模块地图一致 | 规范写明的过渡期别名（addx-things product → application）；命名规范不要求目录名等于 Component 名 |

## 不扫什么

生成代码、vendor / 第三方代码、测试代码（其 import 不计入模块依赖）、符号链接与超过 2MB 的文件、一次改动超过 50 个文件的提交、函数 / 类写法、变量与函数命名。文件级只看 M18（超长）和 M19（fix 多）两个信号。

## 规范缺口（遇到时在报告里注明，不要自行发明规则）

- 后端服务内部分层没有公司级定义 → 以仓内书面文档为准，没有就不查 M01。
- 后端 common / util 纪律、模块循环依赖没有正本条款 → 仍按 M04 / M06 报，依据写「结构原则（ADP / SDP）」。
- Component 按「发布单元」还是「业务边界」划分，Catalog 建模参考与 service-catalog-onboarding 说法冲突。
- 链路追踪 service.name 与 catalog 实体的对应关系未定义（影响 X01）。
