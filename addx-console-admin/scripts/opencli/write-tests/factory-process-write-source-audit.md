# Factory production-process/custom-plan write audit

OFFLINE_VERIFIED_ONLY / NOT_LIVE_ACCEPTED. Eight fixture tests pass. No live API/browser/credentials, business writes, publication or deployment were used. No write CLI is registered and no executable payload is generated.

Custom save defaults publish=true and sets status1 before calling publication. Its transaction annotation is commented out. ID-null inserts without a demonstrated factory/model unique check; nonnull ID updates without verifying target existence, source manufacturer/model/plan ownership or expected version. Arbitrary rebindings can leave original factory runtime state while publishing a new scope. Draft status0 and timestamps do not prove safe lifecycle/CAS or full configuration validity.

Factory list is an assembled default/custom view, with model-key maps that assume unique custom rows. A null custom row is not saved configuration. Editor/view paths cache modelProducePlan in localStorage, and editing later reads cached or default content, rather than an exact fresh saved detail. Empty-process warnings do not necessarily block saving. Factory list publish button is currently commented out due prior production coverage concern; hidden UI does not establish a server permission rule, and save-and-publish remains possible.

Custom publication returns early if the factory has no default-plan association, even if a custom override exists. It selects first matching custom row among duplicates and can skip empty configuration. PCBA publication includes derivatives/client-display mappings. Runtime replacement disables old active rows matching the generated model tuple PLUS planDetailId, then inserts new rows; a changed plan ID can leave old runtime rows unmatched. Async same-class transactional annotation effectiveness and atomic rollback/status/readback are unproven. A published DB flag is not runtime materialization proof.

Default plan publishing recalculates every associated factory and that factory's entire plan/override runtime set, with additional release configuration effects. Default factory registration removes association rows through explicit tombstones, then publishes changed factories after the separate save transaction. Removing the last default link can trigger empty-link early return rather than clearing old runtime state. UI useDefaultPlan is not a custom override deletion contract. No custom delete/restore-default handler exists in the reviewed controller; process section removal is local config editing, not whole custom row deletion.

The pure helper binds edit fixtures to exact ID/manufacturer/model/default-plan tuple, distinguishes creation from a default view, refuses cached observations/raw config/publish/proof/submit fields and summarizes unresolved runtime/scope boundaries only. It does not treat list metadata as full raw state or authorization. Default publish, custom publish, factory unlink and absent custom delete/restore-default stay unavailable for execution.

Required before any writer: fresh authoritative custom target/full raw configuration and exact create absence, caller/deployment permission, immutable owner tuple, process/art/manual-generation rules, all derived/client-model mappings, old/new runtime plan scope, all associated factories for default publish, server uniqueness/version/CAS, transaction/rollback/last-link cleanup and DB/runtime readback. No actual writes or independent runtime readback were tested.

Generic method suggestion: separate default view from saved override; refuse cached editor state as authoritative; keep create/edit ownership tuples immutable even if server permits reassignment; trace model publication through derived/client scopes and plan-ID matching; test last-link removal and early-return paths; distinguish association unlink/disabled runtime from custom delete; require runtime readback rather than trusting a source publish flag.
