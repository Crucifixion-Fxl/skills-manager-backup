# Component-group and file-type planning

Two non-browser commands execute native Console read preconditions when invoked with an authorized private token. This implementation was tested only with synthetic injected responses; no live request, credential, submission or readback was performed. `--mode dry-run` is the only supported mode. Any submit mode fails before reading the changes file or invoking identity/HTTP. Neither command claims full-site writing readiness.

`component-group-write --action create|edit --changes-file <business JSON>` is deliberately narrow. Creation accepts `componentGroupCode`, `componentGroupName`, `iconId`, optional `remark`, and creates a proposed custom group with zero parameters, no related business/workstations. Editing accepts existing `id`, `componentGroupName`, optional `remark`/`iconId`. It retains the observed code/business/workstation IDs in the proposed payload, rejects association/parameter changes, and requires an observed parameter count of zero plus an empty/null active parameter detail. Unknown icons, target mismatch, duplicate code/name, complex parameters and unknown field shapes fail closed. Release is fixed false and cannot be supplied in input.

Native reads are identity, complete bounded unfiltered group list (20/page, maximum 100 pages, stable total/unique IDs), then group detail. Creation reads detail with ID 0 for global icon/options: pinned service SELECTs the nonexistent ID and returns options without initialization. Actual deployment/permission and this read have not been live verified. Only selected group metadata/IDs are emitted; parameter definitions/values, icon URLs and complete response objects are excluded.

Observed emptiness is NOT proof that hidden mappings are absent. Source detail filters deleted parameters, while save checks current-version mappings without that filter. The `/param` API uses the released version, so it does not prove the current version. Parameter changes advance the version; unchanged workstation IDs are not visibly copied into that new version by the source save flow. `parameterMappingProof` explicitly records this unresolved state. Retaining IDs in the candidate payload is not a guarantee that saving preserves all relationships. Submit remains disabled pending a trustworthy full current-mapping contract.

Source group save always updates operator/time and persists the group row, even if metadata is unchanged. Parameter/workstation relationships have separate versioned inserts and parameter upserts. Complex components, supplier/model-type mappings, nested parameters, and full group association editing remain unimplemented.

`file-type-write --action create|edit --changes-file <business JSON>` reads the complete file-type list. Create JSON is `{code,name}` and requires absent code. Edit JSON is `{name}` plus `--target-code <existing code>`; the code disabled by the UI is retained. Duplicate names are allowed by this contract. Creation codes follow the UI letters/digits/underscore/hyphen rule and 50-character limit; names must be nonblank and at most 50.

The file-type DAO uses SQL `REPLACE INTO`, not UPDATE. Editing can delete/reinsert the existing row, including on an unchanged name. Trigger/foreign-key effects are unverified; source interface gives no atomic compare-and-swap. The server mistakenly checks code twice instead of checking name, so the adapter validates the name independently. File-type list uses SELECT only; no implicit business initialization was found.

Both commands expose selected before/proposed values, diff and hash with unknown deployment/action permission and `submissionImplemented:false`. Future submissions require actual deployment and action permissions, explicit business authorization, trustworthy complete mappings, race/partial-failure handling, and post-write readback. Ordinary proof strings do not enable submission.
