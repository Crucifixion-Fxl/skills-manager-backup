# Minimum firmware native candidate plans

`minimum-firmware-write` defaults to `--action template --mode dry-run`. Template reads neither userdata nor credentials/network and supplies examples. Create/edit require explicit bounded business JSON; firmware version is never defaulted in a plan.

Create JSON: `{"modelNo":"EXISTING_PCBA_MODEL","firmwareId":"1.2.3"}`. Edit JSON additionally requires `"expectedCurrentFirmware":"1.2.3"`, explicitly matching the observed current value. Unknown fields/actions, credential/context/metadata/operator/release controls, missing fields and noncanonical firmware versions reject. Versions follow backend exact three decimal components 0..99; leading-zero multi-digit components are invalid. Models use exact bounded safe identifiers. Edit cannot create an absent row; create cannot edit an existing row. The model key is the observed target, not a rename operation.

Native read-before-plan: identity; full unfiltered `/factory/firmware/list` pages20 (max100 pages, stable total, no duplicate models, exact completeness); `/device/model/listByType` modelType0 PCBA options. The pinned services execute SELECT and DTO conversions only in these read methods, with no implicit initialization or refresh found. A malformed legacy row blocks the entire candidate snapshot rather than silently dropping it. PCBA options provide only modelNo/modelType; publication/lifecycle/manufacturer eligibility and action permission are unproven.

Backend `/factory/firmware/save` is **upsert**, despite distinct UI create/edit. It sets firmware_id AND internal version. Insert defaults: type='kernal',size=1,md5='1',path='1',encrypted=1; these are database placeholders, not uploaded asset metadata. It always inserts operator/content firmware_log, including unchanged values. Reviewed save method invokes no build/release/S3 operation. Do not infer downstream manufacturing effects, DB triggers or deployment agreement from this method alone. Current list hides internal metadata and database unique-key definition. No atomic expected-value/CAS condition exists, and complete paged snapshots are not atomic transactions.

Every submit/non-dry-run rejects before input/native identity/HTTP. Neither a proof string nor a release flag enables submission. `expectedCurrentFirmware` protects candidate planning against stale userdata, not real future writes. Plan records version direction and unchanged-but-audit-insert effects, selected diff/hash, hidden state, unknown deployment/action permission and submissionImplemented=false. These commands do not establish real write acceptance or complete Console capability.
