# validators/

确定性校验脚本。每个回答 **一个** 问题，退出 0 = PASS，退出 1 = FAIL（带精确错误信息），退出 2 = 依赖缺失。

## workflow 何时跑

workflow 每个 step 的 `[validate]` 块都跑。validator 红了 workflow **必须** 停下来，把错误原文丢给用户，**不要** "理解一下"、**不要** "局部修一下"、**不要** "下一步再试"。

## 为什么要有 validator

LLM 读 workflow prose 还是会跳步、拼错路径、从老例子里继承 conflictPolicy。validator 不管 workflow 写得多严都能抓住这些。两层防：

1. workflow 让 LLM 更守规矩
2. validator 兜住 LLM 仍然会犯的错

两个都要。skill 自带一小组初始 check；新失败模式被观测到后再加。

## 实现语言

Python 3 + PyYAML。`validate.sh` 是 bash 聚合器，调多个 Python check；输入必须是普通 YAML 或 Helm/Kustomize 已渲染输出。Review 把文件复制到临时目录时必须显式传 `--repo-context app|k8s|argocd-apps|crossplane-infra`，因为临时路径不能证明来源仓；DEV/k8s 单组件渲染输出若用 `secret/cicd/*`，还要传 `--platform-source <真实组件根>`。未渲染的 Helm `templates/*.yaml` 不是合法输入，wrapper 会从 Helm 起始分隔符 `{{` 识别并 exit 2；已渲染字符串中的嵌套 JSON `}}` 不会误报。改用 yq 的旧版有多文档 / null 边界 bug，已弃。

`validate.sh` 始终是严格门禁。只有全目录已存在历史债务、且候选改动已经提交并保持 clean 时，才可用 `validate_delta.py` 做基线增量比较；它仍分别运行完整严格套件，不会忽略任何新问题。

## 历史债务的基线增量门禁

当 workflow 必须扫完整目录，而目标分支已有与本次无关的 validator 失败时，先提交候选改动并确保工作树干净，再显式绑定权威 GitLab repository 与目标 MR 分支：

```bash
python3 "$skill_root/validators/validate_delta.py" \
  --expected-origin https://gitlab.addx.ai/<group>/<repository>.git \
  --base-ref origin/<mr-target-branch> \
  [--repo-context app|k8s|argocd-apps|crossplane-infra] \
  <directory>
```

- `--base-ref` 只接受 concrete `origin/<mr-target-branch>` 语法；不能用本地 branch、SHA、`origin/HEAD` 或任意 ref。caller 的 remote-tracking ref 不作为信任来源。
- wrapper 先用 bounded inert parser 证明 caller 的唯一 local origin 等同 `--expected-origin`；任何 common/per-worktree `config.worktree`、`extensions.worktreeConfig`、include 或 URL rewrite 都 fail closed，且不会执行 Git config。随后选择该 identity 的 credential-free canonical SSH transport（literal SSH origin 原样使用；HTTPS identity 机械转换为同 host/project 的 `git@host:path.git`），禁用 system/global Git config、include redirect、replace ref、lazy fetch、credential helper/prompt、caller SSH config 与非声明 protocol，在 fresh bare repo fetch exact remote branch。remote target OID 固定后才计算 merge-base，并要求 merge-base 精确等于 fresh target（即 target 是 candidate 祖先）；否则 exit 2，候选必须 rebase/rebuild/rerun。
- base 与 candidate 使用 full committed index、只物化被扫 scope/platform 的 regular blob；committed `100644`/`100755` mode 保留在 inert index，但磁盘 blob 一律 `0644`，不运行 checkout hook、fsmonitor、filter 或仓库内 executable。20,000-file index write 有独立 16 MiB file-size headroom，Git stdout 仍受原 1 MiB logical cap。子进程环境只继承 private SSH/CA/temporary-directory 所需的 `HOME`、`SSH_AUTH_SOCK`、CA/TMP 变量，并固定 PATH/locale，同时强制 `PYTHONNOUSERSITE=1`，所以 inherited HOME 下的 `usercustomize.py` 不会执行；`BASH*`、`ENV`、`PYTHONPATH`、`PYTHONHOME`、loader 与其它 caller 环境不会进入 `validate.sh`。所有 Git 与严格套件都有 wall timeout 和聚合 stdout/stderr 上限；argparse help/error 与 delta 最终报告共享 65536-byte 上限，超限时只输出一次 UTF-8-safe truncation marker，exit status 不降级。
- base 的发现会作为债务打印；candidate 继承的同一 fingerprint 保持可见。validator 同时机械计算 fresh target→candidate 在所扫 scope 内的 changed paths：每个 carried debt path/object 必须完全位于 candidate write set 之外；carried finding 的 path 一旦被 candidate 改动，无论 object 是否相同都作为 overlap debt exit 1，必须先修复。仅 `check_vault_paths.py` 已知 field breadcrumb 中的数字列表下标（例如 `.spec.data[0].remoteRef.key`）归一化为 `[*]`；文件名、对象/Vault key 与其他文本保持精确。相同 fingerprint 的数量也参与比较，新增重复违规仍是 candidate-only finding 并一定 exit 1。
- 输出中的 exact remote target SHA、trusted merge-base 与 candidate SHA 都必须纳入 MR evidence；MR HEAD 或 target branch SHA 变化时必须重跑。
- remote proof、base scope、平台 source、Python/YAML 依赖或严格输出任一不可用/不可解析时 exit 2，绝不降级成通过。
- 这不是 allowlist：不得按应用、文件或规则添加忽略项；干净目录仍直接运行严格 `validate.sh`。

`check_vault_paths.py` 从 `references/vault-paths/rules.yaml` 读 pattern——yaml 里加新 platform / 改 regex 自动扩展 validator 覆盖，不用动 Python。

共享 Database 的完整 producer 身份检查使用
`validate.sh --repo-context app --database-inventory <target-DatabaseList.json> <single-target-render-dir>`，
向 `check_db_resource_contracts.py --inventory` 传递准确目标的完整库存。普通目录扫描只做候选内
检查，不能当成跨仓唯一性证明。库存来源、时效、并行候选协调及迁移边界见
[producer 身份门禁](../references/shared-middleware/README.md#producer-identity-gate)。

## 输出格式

- `PASS: <summary>` —— 成功行
- `FAIL: <file>: <object>: <reason>` —— 每条违规一行；可输出多条后再 exit 1
- 没有 warning。要么是规则要么不是。

## 怎么加新 check

1. 单一职责——一个脚本回答一个问题
2. manifest 检查输入是目录路径；部署目标等前置检查使用明确的结构化参数，不能混入 manifest 聚合器
3. 用 Python + PyYAML
4. 加一行到本文件的表
5. 若检查的是渲染 manifest，加入 `validate.sh` 聚合器；若检查 skill 自身结构，直接在 CI 调用，不能混进 manifest 校验
