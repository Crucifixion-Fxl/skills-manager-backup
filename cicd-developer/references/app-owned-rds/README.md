# New dedicated PostgreSQL RDS: platform-owned request

This is the first bounded route for [SRE #168](https://gitlab.addx.ai/issues/sre/dev/-/issues/168). It applies only to a **new** dedicated PostgreSQL 16 instance in `prod-us` / `us-eks-prod` (AWS account `302571458622`). The platform [design](https://gitlab.addx.ai/DEV/k8s/-/merge_requests/2921) and [inert API candidate](https://gitlab.addx.ai/DEV/k8s/-/merge_requests/2925) are not proof that the route is live. Existing instances require a separate credential and data migration. The named Encyclopedia admin exception remains tracked in [#167](https://gitlab.addx.ai/issues/sre/dev/-/issues/167).

## Gate before writing a request

Read the exact target from `references/data/env-keywords.yaml` and `references/data/clusters.yaml`, then run `validators/check_deployment_target.py --env-keyword prod-us`. Require `deployment_status: allowed`; that does not establish the following live capabilities. If any check is absent, ambiguous or fails, **STOP before writing or merging a request**, record an Ops Todo against [DEV/k8s #57](https://gitlab.addx.ai/DEV/k8s/-/issues/57), and do not fall back to the raw RDS administrator recipe.

1. On `us-eks-prod`, read the served `databases.platform.addx.io` XRD. Require a namespaced `platform.addx.io/v1alpha1 Database` with `metadata.name == spec.app`, an immutable app slug, and `enforcedCompositionRef` to `database-aws-dedicated-postgres.platform.addx.io`. Read that exact Composition and its revision, the pinned safe provider-sql package and the `function-go-templating` / `function-auto-ready` health. A source MR, Git tag or server dry-run alone does not pass this gate.
2. Identify exactly one synced, healthy **platform-owned** Argo CD Application whose k8s.git source is `clusters/aws-302571458622-us-prod/platform-apis/app-owned-rds` and whose destination is `crossplane-system`. Read its AppProject/source/destination permissions. App repositories, `app-runtime`, and `app-data-plane` must not control this source or destination. Verify Kubernetes RBAC and admission reject app-controlled reads or copies of the RDS administrator input and connection Secrets.
3. Require an accepted [#57](https://gitlab.addx.ai/DEV/k8s/-/issues/57) evidence receipt for the live Vault ACL and ESO Store: app-controlled `ExternalSecret`/`PushSecret` cannot read admin material or overwrite the platform's `prod/rds/application/<app>/password` source; the application can read only its delivered `prod/rds/application/<app>/database` connection. Require disposable-instance evidence for `IfNotExists` bootstrap, TLS `verify-full` with RDS CA, same-UID password rotation, Secret/Vault loss and recovery, and the DELETE guard. The shared `vault-backend` policy currently has broad access; do not infer isolation from a Vault path name.
4. The platform owner supplies a reviewed private RDS security-group ID and PostgreSQL 16 minor for this account/region. Verify its effective ingress and private subnet/NAT path. Query all `Database` requests in `crossplane-system`, the intended RDS identifier, and the intended Vault paths. Any existing app identity, database, RDS, connection value or conflicting ownership is a migration/collision **STOP**, not an adoption opportunity.

## Generate the reviewed Git changes

First prepare the app's AWS identity in `DEV/crossplane-infra/aws-302571458622-us-prod/`: use the existing `app-providerconfig.yaml.tmpl` and `rds-rolepolicy.yaml.tmpl` to create or extend its `crossplane-app-<app>` Role, `ClusterProviderConfig <app>` and RDS RolePolicy. Review and sync that separate IAM MR, then read back the exact live ProviderConfig and RolePolicy. The Composition's RDS Instance references `ClusterProviderConfig <app>`; an absent or broad/unreviewed identity blocks the request. Do not copy IAM objects into the application or k8s platform source.

The platform owner then writes `recipes/crossplane/app-owned-postgres-database-request.yaml.tmpl` as `clusters/aws-302571458622-us-prod/platform-apis/app-owned-rds/requests/<app>.yaml` in `DEV/k8s`, and adds that file to the platform `kustomization.yaml`. Set `metadata.name == spec.app == <app>`; `<app>` must match `^[a-z][a-z0-9-]*[a-z0-9]$` and be 2–30 characters. Use only the approved `engineVersion` and `securityGroupId`. Do not accept requested admin usernames/passwords, SQL grants, Vault paths, initial `dbName`, public access or arbitrary regions. The Composition derives the SQL database and application username. This is a separate, reviewed platform MR; merging it after the Application is active can create a billable RDS instance.

In the application repository, use `recipes/k8s/db-external-secret.yaml.tmpl` in the precise runtime overlay with `vault_remote_key=prod/rds/application/<app>/database` and the verified target `vault_css`. It reads only `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD` from the safe Access output. Keep the workload's existing Secret name when its source is identical; a name collision with another source is a STOP. Connect only the intended workload/container using the `shared SQL 容器消费连接信息` procedure in `workflows/add-rds.md`. Configure its database name as `<app>` and an app-owned schema with matching migration `search_path`; PostgreSQL 15+ does not grant ordinary users write access to `public` by default. Do not put any password value in Git or manually copy it. The administrator connection must never enter the application namespace or Vault connection path; the safe Access output `DB_PASSWORD` is deliberately delivered there through the reviewed Vault/ESO chain.

Render the platform directory with `kustomize build` and run its `check-render.py`. Run `python3 validators/check_repo_boundary.py <DEV/k8s repository root> --repo-context k8s` from this skill against the source tree: the request exception is accepted only at its exact repository-root-relative path with its closed field set. A standalone render directory does not prove that source path. Confirm the new render has exactly one requested `Database` in `crossplane-system`, no raw RDS `Instance` in an app namespace, and no administrator PushSecret. Render the application overlay, run the declared `validate.sh --repo-context app` and `check_workload_secret.py` against the actual workload and four keys. Record exact branch/MR revisions in #57 and the application work item. After reviewed GitOps sync, verify the request, Instance, safe SQL Database/Access, Vault connection, app ExternalSecret and app login. Connect with the actual app identity to prove no SUPERUSER/CREATEDB/CREATEROLE and successful creation/repeated migrations in its schema. Do not use a green Git or Argo CD status as a substitute for this runtime proof.

The current first slice does not cover MySQL, MariaDB, another prod region, existing-instance cutover, runtime/migration account separation, or full `PUBLIC` cross-database CONNECT isolation. Those requests need their own verified platform route or a named, reviewed exception; never label this route as general fleet readiness.
